# core/

Cross-cutting concerns: theming, environment config, error handling, the analytics wrapper, and any genuinely cross-feature Riverpod state (current user, auth state, feature flags from Remote Config) — per `docs/ENGINEERING_GUIDELINES.md`'s "State Management: Riverpod" section.

**Milestone F2:** `auth_state.dart` lands here — a thin `@riverpod` provider wrapping `FirebaseAuth.instance.authStateChanges()`, plus `isSignedIn`/`currentUid` convenience derived providers. Scoped deliberately narrow: raw Firebase Auth sign-in state only, not "has this user finished onboarding" (that needs the Firestore repository layer in `app/lib/data/`, still empty — see that directory's own README). Unverified like every Dart file in this repo so far: no Flutter toolchain has been available to run `flutter pub get` or `build_runner` (the generated `auth_state.g.dart` companion file doesn't exist yet).

**Milestone F3:** `theme/` lands here — `color_tokens.dart`, `spacing_tokens.dart`, `type_tokens.dart`, and `app_theme.dart`, hand-transcribed from `docs/DESIGN_SYSTEM.md` per Recommendation R3 (see `color_tokens.dart`'s file header for why "hand-transcribed" rather than the eventual Figma-generated pipeline §10 describes, and for the disclosed Fraunces-weight substitution). `app.dart` now builds its `MaterialApp` from `TCAppTheme.light()`/`.dark()` instead of a bare Material default. A first `StatusChip` widget landed in `widgets/` alongside it, since Recommendation R2's golden-test harness needs at least one real component to snapshot-test.

**Milestone F3 (continued):** `routing/app_router.dart` also lands here — a GoRouter route table covering every Foundation-scope screen in `docs/SCREEN_SPECIFICATIONS.md` (see that file's header for the precise in/out-of-scope screen list, matching `docs/IMPLEMENTATION_PLAN.md` section 1 and Recommendation R7). Every route renders a stub placeholder; no real screen widgets exist yet. `app.dart` now uses `MaterialApp.router` wired to `appRouter` instead of a `home:` placeholder. Deliberately not decided here: any nested `ShellRoute`/tab-bar navigation shell — that's left to whichever milestone builds Home's real navigation chrome.

**Milestone F3 (continued):** `offline/` lands here — Recommendation R1's `OfflineMutationQueue`, the single reusable abstraction every idempotency-keyed callable (Table creation, Crew creation, ratings, later payments) is meant to be built on, per `features/tables/README.md` and `features/crews/README.md`. `idempotency_key_store.dart` persists the mutationId -> idempotencyKey mapping in `SharedPreferences` (UUID v4, per `docs/API_SPEC.md` §2 and `functions/src/shared/index.ts`'s `isWellFormedIdempotencyKey`); `offline_mutation_queue.dart` is the `@riverpod` notifier wrapping it, gating attempts on `connectivity_plus`, keeping a persisted key reserved across *any* failure (not just connectivity — see the class's doc comment for why that's safe per `docs/DATABASE.md` §3.9's idempotency-key record semantics), and exposing a `reconnected` stream. Deliberately out of scope here: automatically replaying a failed call once back online — a closure can't survive an app restart, so re-invoking the call with the feature's own rehydrated draft data is left to the feature layer (F6/F7), not this generic queue.
