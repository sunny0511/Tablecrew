# data/

Repositories, Firestore/Cloud Functions client wrappers, and DTOs — the boundary layer where raw Firestore document maps get parsed into typed models, per `docs/ENGINEERING_GUIDELINES.md`'s "no `dynamic` unless interfacing with genuinely dynamic data" rule. Repositories are exposed as Riverpod providers so they're trivially overridable in tests.

**Corrected (Milestone F2):** still empty, and that's expected, not a gap — this note previously said "populated starting in Milestone F1," but F1 ("Core data layer & security rules") was Firestore schema/rules/seed-scripts only, per `docs/IMPLEMENTATION_PLAN.md`; it never included Flutter repository code, since no Flutter toolchain has been available to build/verify Dart against in this environment and no feature yet needs a repository to call. F2 kept the same boundary (its `core/auth_state.dart` reads only raw Firebase Auth state, deliberately not Firestore, precisely so it doesn't need a repository ahead of one existing). Real population starts once a feature actually needs to read/write Firestore data — concretely, Milestone F4 (Table/Crew Cloud Functions) is the first point a client-side repository wrapping those callables has anything to call, with feature-specific repositories following as each Milestone F5+ screen is built against them.
