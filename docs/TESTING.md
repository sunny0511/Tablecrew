# Testing Strategy

TableCrew ships a Flutter client and a Cloud Functions backend that together enforce safety-critical behavior (verification gating, no-show accountability, reporting/blocking — see `SECURITY.md`) alongside ordinary product logic (headcount capping, RSVP flows, Crew management). Our testing strategy is built around a simple principle: the cheaper and faster a test is to run, the more of them we should have, and the things that are hardest to get right by inspection (Firestore rules, business-logic edge cases) get the most deliberate test coverage regardless of layer.

## The Testing Pyramid

```
                    ▲
                   ╱ ╲        Manual QA + Beta (TestFlight / Play Console)
                  ╱   ╲       — exploratory, pre-release, small volume
                 ╱─────╲
                ╱       ╲     Integration / E2E (flutter integration_test)
               ╱         ╲    — key user journeys, real emulator backend
              ╱───────────╲
             ╱             ╲  Widget tests
            ╱               ╲ — component behavior, in isolation
           ╱─────────────────╲
          ╱                   ╲ Unit tests
         ╱                     ╲ — business logic, pure functions, providers
        ╱_______________________╲
```

**Unit tests** are the foundation and the largest layer by test count. They cover pure business logic with no Flutter widget tree and no real network dependency: Riverpod `Notifier`/`AsyncNotifier` classes (with repositories mocked/faked, per the Riverpod convention in `ENGINEERING_GUIDELINES.md`), headcount and capacity math, no-show threshold calculations, RSVP state transition logic, Cloud Functions business logic (TypeScript, tested with a standard Node test runner against faked Firestore/Auth inputs where the logic doesn't need the emulator). These run in milliseconds to low seconds, require no setup, and are what we run constantly during local development.

**Widget tests** cover Flutter UI components in isolation — does this widget render the right state for a given provider value, does tapping a button call the expected callback, does a form show a validation error for bad input. These use Flutter's `flutter_test` package with a `ProviderScope` overridden with fake providers, never a real backend. They're slower than unit tests but far faster than integration tests, and they catch the large class of "the widget doesn't handle the loading/error/empty state" bugs that unit tests on the underlying logic can't catch by themselves.

**Integration/end-to-end tests** use Flutter's `integration_test` package to drive the real app (or a close-to-real build) through complete user journeys against the **Firebase Emulator Suite** (Firestore, Auth, Functions, and Storage emulators running locally or in CI) rather than production or staging Firebase. This is the layer that answers "does creating a Table, having three people RSVP, and closing it actually work end-to-end," including real Firestore rules enforcement and real Cloud Functions execution — not mocked approximations of them. Because the emulator suite gives us a full, resettable, hermetic Firebase environment, we get integration-test confidence without ever touching real user data or racking up cloud costs for test runs, and without the flakiness of hitting real network-dependent cloud services in CI.

**Manual QA and beta testing** is the final layer before a release goes to real users at scale, covering the things automated tests structurally can't: does this feel right, does an unusual real device or real network condition surface something the emulator and simulators can't, does this actually solve the human problem it was meant to solve. Detailed below.

### Coverage Targets by Layer

- **Business logic / Cloud Functions unit tests: 85%+ line coverage**, enforced in CI as a soft gate (a PR that drops core business-logic coverage below this threshold requires explicit justification in review, not an automatic block — coverage percentage is a signal, not a goal to game with meaningless tests). This layer holds our highest bar because it's cheap to test thoroughly and because bugs here (a miscounted no-show threshold, a headcount cap off-by-one letting a 9th person into an 8-cap Table) are exactly the kind of silent, hard-to-notice-in-manual-QA bugs that automated tests are best at catching.
- **Widget tests: targeted, not blanket-percentage-driven.** We don't chase a coverage number for widgets — we require a widget test for every component with non-trivial conditional rendering logic (loading/error/empty/populated states, permission-gated UI) and skip tests for pure "layout with no logic" widgets, where a test would just re-assert the markup. Trying to hit a blanket 80% widget-test coverage number tends to produce brittle, low-value tests that mostly re-describe the widget tree rather than catch real bugs.
- **Integration/E2E tests: covers critical paths only, not exhaustive.** We maintain integration tests for the handful of journeys where a regression would be a genuine incident: sign-up + phone verification, Tier 2 identity verification flow, create Table → RSVP → confirm → rate, Crew creation and invite, report + block flow, no-show recording. We deliberately don't try to E2E-test every screen — these tests are the slowest and most maintenance-heavy in the pyramid, so we spend that budget only where the risk of an undetected regression is highest (notably, everything safety-related from `SECURITY.md`).
- **Firestore Rules tests: 100% of rules paths.** Every `allow`/`deny` branch in `firestore.rules` has at least one test asserting it behaves as intended — both a positive case (the access that should be allowed, is) and a negative case (the access that should be denied, is denied). Given that rules are our last line of defense per `SECURITY.md`, an untested rule is treated the same as an untested payment-processing code path: not acceptable to ship.

## Testing Firestore Security Rules

We use the `@firebase/rules-unit-testing` library against the Firestore emulator to test `firestore.rules` directly, independent of application code. Each test spins up an emulator instance, seeds it with documents via an admin-privileged bypass context, then asserts specific reads/writes succeed or fail when performed as a specific authenticated (or unauthenticated) user context — mirroring the concrete examples in `SECURITY.md` (e.g., "user A cannot read user B's phone number," "a non-host cannot change a Table's status field," "a user can create a report naming themselves but can never read any report, including their own").

Structure: `firestore/test/rules/` mirrors the collection structure in `firestore.rules`, one test file per collection (`users.rules.test.ts`, `tables.rules.test.ts`, `reports.rules.test.ts`, etc.). Every PR that modifies `firestore.rules` must include corresponding test changes in the same PR — CI enforces this is at least attempted by running the full rules test suite against the modified rules file and failing the build if coverage of new branches is absent (checked via the emulator's rules coverage report, which flags rules lines never exercised by any test). This is deliberately stricter than our general "coverage is a soft gate" philosophy elsewhere, because rules are uniquely unforgiving — a wrong rule doesn't fail loudly in production, it silently over- or under-exposes data.

## Test Data Management and Fixtures

We maintain a shared fixtures library (`functions/test/fixtures/` and mirrored Dart equivalents in `app/test/fixtures/`) providing factory functions for core entities — `buildTestUser()`, `buildTestTable()`, `buildTestCrew()`, `buildTestRsvp()` — with sensible defaults and named parameters for overriding just the fields relevant to a given test. This avoids two failure modes we've seen in other codebases: copy-pasted raw JSON fixtures that drift out of sync with the real schema in `DATABASE.md` as it evolves, and tests that each hand-roll a full user/Table object inline, burying the one or two fields that actually matter to the test under boilerplate.

For integration tests against the emulator, each test run seeds its own isolated data (via the fixtures library, through the emulator's admin bypass) and the emulator state is reset between test files (`firebase emulators:exec` wraps each test suite run) so tests never depend on ordering or leak state into each other. We do not maintain a persistent shared "test database" of hand-curated data — the cost of that drifting stale over time outweighs the convenience.

For manual QA and staging (see `DEPLOYMENT.md` for the staging environment), we maintain a small seed script (`scripts/seed_staging.ts`) that populates a realistic but synthetic set of users, Tables, and Crews, so staging is never empty and never contains real user data copied from production — consistent with "respect data like it's someone's actual life" from `VALUES.md`. Production data is never copied into staging or dev under any circumstance.

## Manual QA and Beta Testing

Automated tests are necessary but not sufficient before a release reaches all users — every release goes through a manual QA pass and a beta testing phase first.

**Manual QA**: before cutting a release candidate, the team runs a scripted smoke test covering the critical paths listed above on real devices (not just simulators/emulators) — at minimum one recent iOS device and one recent Android device, plus one older/lower-spec Android device given Android's hardware fragmentation, since performance and layout issues disproportionately surface there. The smoke test script lives alongside `TASKS.md` release checklists and is updated whenever a new critical path is added.

**Beta testing**: every release candidate goes to internal and external beta testers before public release, using platform-native tools rather than a custom solution — **TestFlight** for iOS and the **Play Console's internal testing track**, escalating to the **closed testing track** for a slightly wider beta group, for Android. We chose platform-native beta tooling over a third-party alternative because it's free, requires no additional integration work, and matches exactly the distribution mechanism (App Store / Play Store builds) the release will ultimately use — a bug specific to a TestFlight/Play-signed build is one we want surfaced in beta, not one we want a third-party tool to mask by using a differently-signed build. Internal beta (the founding team plus a handful of trusted early users) runs for 2–3 days on every release candidate; external beta (a wider group of opted-in real users) runs concurrently or immediately after for another 2-3 days for any release containing user-facing changes, longer for anything touching Discover or verification given the higher stakes of getting those wrong. Beta feedback and crash reports (via Crashlytics, per `FIREBASE.md`) are triaged daily during the beta window, and any SEV1/SEV2-class issue found in beta (per the severity classification in `SECURITY.md`) blocks promotion to production release regardless of how close the release is to its planned date.

## How Testing Gates CI/CD

Per `CI_CD.md`, no code reaches any deployed environment without passing the automated test layers first: lint, unit/widget tests, and Firestore rules tests all run on every pull request and must pass before merge is even allowed (branch protection on `main` enforces this — it is not a manual courtesy check). Integration/E2E tests against the emulator run on every merge to `main` (not on every PR, since they're the slowest layer — running them pre-merge on every push would create an unacceptably long PR feedback loop, so we accept the small risk of an integration-test failure surfacing post-merge on `main` rather than pre-merge on every branch, and treat any such failure as blocking for release). A release build is only produced from a `main` commit where the full test suite, including integration tests, is green. Manual QA and beta testing then gate the promotion from an internal release candidate to the staged public rollout described in `DEPLOYMENT.md` — automated tests answer "does it work as specified," beta testing answers "does it work as intended for real people," and we need both before we call a release done.

## Chaos and Incident-Response Drills (Game Days)

Everything above (unit, widget, integration, rules tests, manual QA, beta) answers "does the system behave correctly under normal and expected-edge-case conditions." None of it answers "what actually happens when a dependency we don't control fails, or when load arrives in a shape we didn't design for" — and for TableCrew specifically, two systems carry consequences severe enough that finding this out for the first time during a real incident is not acceptable: the trust & safety report pipeline (`SECURITY.md`) and the payments path (Stripe, `API_SPEC.md`).

We run a periodic game-day exercise against **staging**, never prod, using synthetic data (per the seed script above) so a drill can be run aggressively without any real-user consequence — quarterly at minimum, more often while the team and surface area are still changing quickly. Each game day picks one concrete failure scenario and the team responds to it as if it were real, using the actual on-call and severity process from `SECURITY.md`'s Incident Response section (not a tabletop discussion in the abstract) — the point is to test the process and tooling under pressure, not just to reason about it in a meeting. Scenarios we maintain and rotate through include:

- **Report queue flood**: a script generates a large burst of synthetic reports against staging in a short window, simulating a viral moment or coordinated abuse campaign, to validate that the surge-staffing protocol (`SECURITY.md`'s Incident Response section) actually triggers, that the reports queue's composite index (`DATABASE.md` §5) performs acceptably under load, and that on-call paging and the temporary-admission-tightening lever both work as designed rather than only on paper.
- **Stripe webhook outage or delay**: staging's Stripe test-mode webhooks are deliberately blocked or delayed to simulate Stripe-side degradation, validating that `splitPaymentStatus` (`DATABASE.md` §3.3) doesn't silently desync from reality, that a reconciliation/retry mechanism exists and actually catches up once webhooks resume, and that no user ends up double-charged or stuck because we assumed webhooks always arrive promptly.
- **Duress-signal surge or false-positive storm**: validates that a burst of duress signals (`SECURITY.md`'s In-Table Emergency and Duress Response section) all page correctly and don't silently rate-limit each other the way ordinary abuse-prevention rate limiting might for a lower-stakes action.
- **Firestore/Functions regional degradation**: simulates a Firebase outage or elevated latency in one environment to validate that the rollback procedures in `DEPLOYMENT.md` are actually exercised, not just documented.

Each game day produces the same blameless-postmortem artifact a real incident would (`SECURITY.md`), tracked in `TASKS.md`, specifically because a drill that surfaces a gap and then isn't followed up on is strictly worse than not running the drill at all — it creates false confidence that the gap was addressed.
