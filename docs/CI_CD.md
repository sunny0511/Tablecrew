# CI/CD Pipeline

This document describes the automated pipeline that takes a commit from a pull request to a running deployment, for both the Flutter client and the Cloud Functions backend. It's the mechanical implementation of the processes described in `TESTING.md` (what gets tested and when) and `DEPLOYMENT.md` (what gets deployed and when) — this document is about the plumbing that makes those processes actually happen on every push, without a human remembering to run anything by hand.

## Platform Choice: GitHub Actions

We use **GitHub Actions** as our CI/CD platform, with **Fastlane** handling mobile build/signing/store-upload automation and **Firebase App Distribution** for internal build distribution to testers.

We evaluated CircleCI and Bitrise, both credible alternatives with genuine strengths — Bitrise in particular is mobile-native and ships with a lot of Flutter/iOS/Android tooling pre-integrated. We chose GitHub Actions anyway for a few concrete reasons specific to a small, cost-conscious team already living in GitHub. First, cost: GitHub Actions is bundled with our existing GitHub plan and its usage-based pricing for a team our size is materially cheaper than paying for a separate CircleCI or Bitrise seat/credit allocation on top of a GitHub subscription we already have — for a founding-stage startup, avoiding a second billing relationship for something GitHub already includes is a real savings, not a rounding error. Second, GitHub-native integration: workflow triggers, PR status checks, branch protection rules, and required-review enforcement (per `ENGINEERING_GUIDELINES.md`'s PR process) all work natively with GitHub Actions with zero extra configuration or webhook plumbing, whereas a third-party CI requires wiring up status reporting back to GitHub and maintaining that integration. Third, one less vendor: our stack already spans Firebase, Stripe, and Algolia/Typesense — every additional vendor is an additional thing to configure, secure, and eventually migrate away from if it stops fitting, and GitHub Actions removes CI from that list entirely by piggybacking on infrastructure we're already committed to. Bitrise's mobile-specific conveniences are real, but Fastlane (which we'd want regardless of CI platform, since it's the standard for signing/store automation regardless of what triggers it) closes most of that gap — we get Bitrise's mobile automation benefits via Fastlane running inside GitHub Actions, without taking on Bitrise as a separate platform.

**Fastlane** handles everything platform-specific and fiddly about mobile releases: code signing (via `match`, which stores signing certificates and provisioning profiles encrypted in a private repo, avoiding the classic "certificate only exists on one engineer's laptop" failure mode), version/build number bumping, changelog/metadata upload, and the actual binary upload to App Store Connect and the Play Console. This is standard, widely-adopted tooling in the Flutter/iOS/Android ecosystem — we don't hand-roll signing or upload scripts, which is a well-trodden source of fragile, engineer-specific "works on my machine" release processes.

**Firebase App Distribution** distributes internal/beta builds to the team and early testers for builds that aren't yet ready for (or don't need) full TestFlight/Play Console beta tracks — e.g., a build for a specific feature under active development that a designer or founder wants to try immediately. It's zero additional cost since we're already fully committed to Firebase, and it integrates directly with our existing Firebase project structure (dev/staging, per `FIREBASE.md` and `DEPLOYMENT.md`). TestFlight and Play Console internal/closed tracks (per `TESTING.md`) remain the beta mechanism for actual release-candidate builds closer to production, since those need to exercise the real store-signed build path; App Distribution is for faster, lower-ceremony internal iteration.

## Pipeline Stages

The full pipeline, in order, with the understanding that later stages only run if earlier ones pass:

1. **Lint** — `dart format --set-exit-if-changed` and `dart analyze` (against the `very_good_analysis` ruleset, per `ENGINEERING_GUIDELINES.md`) for the Flutter app; ESLint + TypeScript compilation check for Cloud Functions. This stage is fast (seconds) and fails the build immediately on style or type violations, so an engineer gets that feedback before waiting on slower stages.
2. **Unit and widget tests** — `flutter test` for the Dart unit/widget suite, and the Node test runner for Cloud Functions unit tests (per `TESTING.md`), run in parallel jobs since they're independent of each other. Coverage reports are generated and the 85%+ business-logic threshold (per `TESTING.md`) is checked here.
3. **Firestore rules tests** — the Firestore emulator is started as a service container in the workflow, and the `@firebase/rules-unit-testing` suite (per `TESTING.md`) runs against it, including the rules-coverage check that flags any untested rule branch.
4. **Build** — `flutter build` for both platforms (a debug/profile build for PR validation; a signed release build only at the release-tag stage described below) and `tsc` compilation for Cloud Functions. This stage catches build-breaking issues (missing platform config, dependency incompatibilities) distinct from what unit tests catch.
5. **Integration tests** — `flutter test integration_test/` against the Firebase Emulator Suite running all needed emulators (Firestore, Auth, Functions, Storage) as service containers, exercising the critical user journeys named in `TESTING.md`. This is the slowest stage, so it runs on merge to `main`, not on every push to a PR branch (detailed below).
6. **Deploy to internal testers** — for Cloud Functions, this means deploying to the **dev** Firebase project automatically; for the mobile app, this means a Fastlane lane building and pushing to Firebase App Distribution for the internal team.
7. **Staged production rollout** — for Cloud Functions, an automatic deploy to **prod** on merge to `main` (continuous deployment, per `DEPLOYMENT.md`); for the mobile app, a Fastlane lane that builds, signs, and submits to App Store Connect / Play Console, entering the staged rollout percentage described in `DEPLOYMENT.md`, triggered only from a release tag, not from every merge to `main`.

## Branch-Triggered Behavior

- **On pull request (any push to a branch with an open PR against `main`)**: stages 1-4 run (lint, unit/widget tests, rules tests, build). This is intentionally the fast feedback loop — an engineer should get a full pass/fail signal within a few minutes of pushing, so PR review isn't blocked waiting on CI. Integration tests do not run per-PR-push because they're too slow to be part of the tight iteration loop; instead, a PR is allowed to merge once stages 1-4 are green and human review is approved, accepting the small residual risk that an integration-level regression surfaces only after merge.
- **On merge to `main`**: the full pipeline runs, stages 1-6 — including integration tests (now that the change is committed, we want the full-confidence signal) and deployment of Cloud Functions to prod (continuous deploy) plus a build push to Firebase App Distribution for internal testers. If integration tests fail post-merge, this is treated as a build-breaking event: the team is alerted immediately (not left to be discovered later) and fixing it takes priority over new work, since `main` failing its own integration suite means our "main is always releasable" trunk-based development premise (per `ENGINEERING_GUIDELINES.md`) is currently false.
- **On release tag** (a tag of the form `v1.4.0` cut from a `main` commit that has been through internal/external beta per `TESTING.md` and `DEPLOYMENT.md`): stage 7 runs — the Fastlane lane builds signed release binaries and submits them to App Store Connect and the Play Console, entering staged rollout. Release tags are created deliberately (a maintainer runs a `scripts/cut_release.sh` helper that tags the verified `main` commit) rather than automatically off every merge, since a mobile release is a considered event gated by the biweekly cadence and beta results in `DEPLOYMENT.md`, not something we want to trigger accidentally.

## Secrets Management

All secrets — Apple signing certificates and API keys (via `match`'s encrypted repo plus a GitHub Actions secret holding its decryption passphrase), Google Play service account JSON, Firebase service account keys for each environment (dev/staging/prod, per `FIREBASE.md`), Stripe API keys, Persona API keys (per `SECURITY.md`), Algolia/Typesense admin keys — live in **GitHub Actions encrypted secrets**, scoped per-environment using GitHub's environment protection rules so that, for instance, the prod Firebase service account key is only accessible to workflow runs targeting the prod deployment job, not to arbitrary PR-triggered jobs. This matters concretely: a PR from a branch (even an internal one) never has access to prod credentials, only dev-environment credentials, so a compromised or buggy PR-stage workflow cannot exfiltrate or misuse production secrets. Production-environment secret access in GitHub additionally requires the deploying job to run from `main` or a release tag, never from an arbitrary branch, enforced via GitHub's environment deployment branch rules.

Secrets are never written to logs (workflows use GitHub's secret-masking, and we additionally avoid `echo`-ing secret values in any custom script step) and are rotated on a schedule (quarterly at minimum) or immediately on suspected exposure, with rotation being a checklist item owned by whoever manages the relevant vendor relationship (e.g., the engineer who owns the Persona integration owns rotating its API key).

**Automated secret scanning, not just careful storage.** Storing secrets correctly (above) prevents a compromised CI job from exfiltrating them, but it does nothing to stop an engineer accidentally committing a live credential directly into a file — a Persona API key pasted into a test fixture, a Stripe key that turns out to be live rather than test-mode, a Firebase service account JSON dropped into a debug script. Every PR and every push to `main` runs an automated secret-scanning stage (GitHub's native secret scanning plus a `gitleaks` step in the pipeline as a second, configurable pattern-matching layer, since GitHub's built-in scanning covers well-known provider token formats but a custom `gitleaks` ruleset also catches our own vendor-specific key formats it doesn't natively recognize) as an early, fast pipeline stage. A detected credential fails the build immediately and blocks merge, and additionally triggers an automatic Slack alert to the team so the exposed credential can be rotated right away regardless of whether the PR is fixed or abandoned — a credential that touched Git history, even in a since-reverted commit, is treated as compromised and rotated, not merely removed from the latest commit.

## Deploy-Time Region and Jurisdiction Assertion

`LEGAL.md` §7 flags a real risk our environment strategy didn't previously guard against mechanically: as TableCrew expands into jurisdictions with data-localization expectations (India/DPDP, Brazil/LGPD, and eventually others), it's possible for a config or deploy error to point a build, a Cloud Function, or a Firestore project reference at the wrong regional project for a market with a residency requirement — an easy mistake to make by hand (a copy-pasted environment variable, a stale `.env` reference) and a serious one to make silently, since it wouldn't necessarily fail any functional test.

We add a lightweight, deploy-time safeguard rather than relying on manual review alone: each environment's deploy configuration declares its expected Firebase project ID and region as an explicit, checked-in value (not inferred from whatever credentials happen to be active), and a pre-deploy assertion step in the pipeline (part of stage 7, run before the actual `firebase deploy` / Fastlane submission) verifies that the resolved deployment target's project ID and region match the declared expected value for that environment and, where applicable, that any jurisdiction-specific Firestore project (per `DATABASE.md`'s `users.residencyRegion` field and `FIREBASE.md`'s regional-project guidance) is the one actually being targeted for a build tagged for that market. A mismatch fails the deploy job outright rather than proceeding with a warning — deliberately a hard gate, not an advisory one, given that the cost of catching this in CI is trivial compared to the cost of a data-localization violation discovered after the fact. This check is intentionally simple (a project-ID/region string comparison, not a general compliance engine) — it catches the "wrong project entirely" class of mistake, not a subtler in-region policy violation, which remains a legal-review responsibility per `LEGAL.md` §7's jurisdiction checklist.

## Build Time Optimization

CI feedback speed matters directly for how well trunk-based development (`ENGINEERING_GUIDELINES.md`) works — slow CI means longer-lived branches and bigger, riskier merges, which undermines the whole point of the strategy. We keep build times down with a few concrete practices: dependency caching (Gradle, CocoaPods, and pub caches are all persisted between workflow runs via GitHub Actions cache, so a routine PR build isn't re-fetching and re-resolving every dependency from scratch); parallelizing independent jobs (lint, Dart unit tests, and Cloud Functions unit tests run as separate concurrent jobs rather than sequential steps in one job, since they don't depend on each other); running platform builds (iOS/Android) only where actually needed for the stage in question — a PR validation build doesn't need a full signed release build, only a debug/profile build sufficient to catch build breakage; and reserving the genuinely slow stages (integration tests, full signed release builds) for merge-to-main and release-tag triggers respectively, rather than running them on every PR push, per the branch-triggered behavior above. As the test suite grows, we'll revisit test sharding (splitting the widget/unit test suite across parallel runners) once single-job runtime starts meaningfully exceeding our target of a sub-10-minute PR feedback loop.

## Cloud Functions Deploy vs. Mobile App Deploy

The two pipelines diverge sharply after the shared early stages (lint, unit tests), and every engineer should understand why: **Cloud Functions have no app-store review gate**, so a Cloud Functions change that passes CI deploys straight to prod on every merge to `main`, potentially many times a day, with the same rollback story described in `DEPLOYMENT.md` (redeploy the previous version, restoring service within minutes). This is possible because we, not a third-party reviewer, are the only gate on backend deploys — which is exactly why the automated test suite (especially Firestore rules tests and business-logic unit tests) has to be trustworthy enough to be the actual safety net, since there's no human app-store reviewer providing a second layer of scrutiny before the change reaches real users.

**The mobile app cannot follow this model no matter how good our CI is**, because Apple's and Google's review processes sit between "CI passed" and "users can install it," and because a binary already installed on a phone can't be remotely un-installed or force-reverted the way a Cloud Function redeploy instantly supersedes the previous version (see `DEPLOYMENT.md`'s rollback discussion). This is why the mobile pipeline includes stages the backend pipeline doesn't need — Fastlane-driven signing and store submission, staged rollout percentages, and a release-tag gate that deliberately decouples "code is ready" (true continuously, same as the backend) from "a new binary is being pushed to users" (true only on a deliberate, beta-tested, biweekly cadence). Engineers should think of Cloud Functions changes as low-ceremony and continuously shippable, and mobile client changes — anything in `app/lib/` — as needing to justify themselves against the biweekly train and, ideally, shipping behind a Remote Config flag (per `ENGINEERING_GUIDELINES.md` and `DEPLOYMENT.md`) so that even the slow-moving binary layer gets a fast, backend-speed rollback lever for the specific feature inside it.
