# Implementation Plan

**Status:** Living document, v1.0. **Owner:** Staff Engineer / Technical Lead role, TableCrew. **Related docs:** `docs/ROADMAP.md`, `docs/PRD.md`, `docs/FEATURES.md`, `docs/ARCHITECTURE.md`, `docs/DATABASE.md`, `docs/API_SPEC.md`, `docs/ENGINEERING_GUIDELINES.md`, `docs/TESTING.md`, `docs/CI_CD.md`, `docs/DEPLOYMENT.md`, `TASKS.md`, `docs/ARCHITECTURE_READINESS_REVIEW.md`.

## 0. Terminology note (read this first)

This document uses **"Foundation"** to mean the engineering bootstrap effort — repo scaffolding, infrastructure, core data layer, and the first working vertical slice of features — that delivers `docs/ROADMAP.md`'s **Phase 0** (single-city MVP, Crew-first only, Hyderabad). "Foundation" is an *engineering* phase name, not a new product-phase number: it does not replace or compete with `ROADMAP.md`'s Phase 0/1/2/3 naming, `TASKS.md`'s "Immediate next steps," or `docs/PRD.md`'s FR numbering. Where this document says "Milestone F3," it means "the third engineering milestone inside the Foundation effort" — not a new numbered product phase. This distinction matters because the knowledge base already has one real, previously-uncaught naming collision (documented in Section 2 below) between how different documents described "Phase 0's" own scope; this document is written to avoid adding a second one.

**Correction, 2026-08 (founder-directed re-scoping):** Foundation's milestone sequence no longer maps one-to-one onto "everything Foundation builds is Phase 0, everything Phase 1 builds happens after Foundation ships." Per founder direction, Discover — previously excluded from Foundation entirely and treated as pure Phase 1 work — is now **built** during Foundation (new Milestone F7, Section 4), because Discover is TableCrew's core competitive differentiator (existing tools already solve "coordinate with people you already know"; nothing solves "find meaningful conversation with people you don't") and validating it early, once Trust & Safety infrastructure (F6) is live and pressure-tested, is now a deliberate priority rather than something to defer until after the entire Crew-first product ships. This is a **build-timing** change, not a **launch-timing** change: `ROADMAP.md`'s Phase 0 exit criteria (Trust & Safety proven under real load, legal review of Discover's dating-/social-referral-service exposure) still gate when Discover actually goes live for real users, per `DEPLOYMENT.md`'s Remote Config flag lifecycle — Discover's code ships inside Foundation, defaulted off, the same way any other risky feature ships dark before its flag ramps. "Foundation delivers Phase 0" is therefore no longer strictly true in scope (Foundation now delivers a superset — Phase 0's full scope plus Discover's Foundation-buildable slice); it remains true in the sense that matters for launch — nothing Discover-related goes live to real users until Phase 0's own exit gate is met. See Section 4 for the concrete milestone changes and Section 2.4 for the reasoning in full.

Recurring Crews (`scheduleRecurringTable`, the Recurring Table Schedule screen) moves the other direction — out of Foundation, deferred to Phase 1 — the same treatment bill-splitting already received (Section 2.1).

## 1. Confirmed understanding of the architecture and plan

Every document in `docs/` was read or re-verified across three focused passes (engineering/infrastructure readiness, product-scope buildability, and open-blocker audit) before writing this plan, on top of the seven-dimension architecture readiness review already completed (`docs/ARCHITECTURE_READINESS_REVIEW.md`). What follows is the working model this plan is built on — stated explicitly so any error in it can be caught now, not discovered mid-sprint.

**Product model:** TableCrew is a platform for small-group real-world gatherings, built around three concepts — **Table** (the atomic gathering: lifecycle Proposed→Filling→Confirmed→Happened→Rated, terminal Cancelled reachable from Proposed/Filling/Confirmed; Closed/invite-only or Open/Discover-visible), **Crew** (a persistent friend group with recurring Tables and its own chat), and **Discover** (curated stranger-matching, safety-gated — see the 2026-08 correction above: now *built* during Foundation, still *launched* only at Phase 0's exit gate). Headcount is a hard 2–8 range with activity-dependent recommended defaults. RSVP states are exactly Going/Requested/Waitlisted/Not Going.

**Foundation build scope, precisely (2026-08 correction — see Section 0):** account creation and phone (Tier 1) verification, profile and interest selection, Crew creation with persistent chat (recurring-schedule automation excluded — see below), Closed-Table creation and full lifecycle, invites (Crew-member multi-select and private capped/expiring link-share — see Section 2's Screen 12 clarification), RSVP/waitlist, per-Table ephemeral chat, host-facing post-Table ratings, push notifications, the Trust & Safety reporting/blocking/duress pipeline (live from day one, per `ROADMAP.md`'s explicit rationale that this infrastructure must be pressure-tested on lower-stakes Crew disputes before Discover raises the stakes), and — new as of this correction — **Discover** (browse/search/filter, Open Tables, Tier 2 identity verification, Typesense-backed search), built once F6's Trust & Safety infrastructure is live, shipped behind a Remote Config flag defaulted off. **Explicitly not in Foundation scope:** bill-splitting/payments, venue partnerships, recurring-ritual automation (the Phase 2 Crew-nudge system, `docs/PRODUCT.md`), TableCrew+ subscription billing, and — moved out this pass — **recurring Crews** (`scheduleRecurringTable`, the auto-generating recurring-Table-series endpoint and its screen), deferred to Phase 1 alongside bill-splitting.

**Tech stack:** Flutter (Riverpod, GoRouter, Material 3 fully re-themed) client; Firebase (Firestore, Auth, Cloud Functions, FCM, Storage, App Check, Remote Config, Crashlytics, Analytics+BigQuery) backend; Typesense (Discover search — needed during Foundation as of this correction, see new Milestone F7 below); Stripe (payments — not needed until Phase 1); three fully separate Firebase projects (`tablecrew-dev`/`-staging`/`-prod`), Firestore pinned to the regional location `asia-south1` (Mumbai — decided this pass, Section 2).

**Engineering process:** monorepo (`app/` Flutter client + `functions/` Cloud Functions + `firestore/` rules/indexes), trunk-based development, GitHub Actions CI (lint → unit/widget tests → rules-emulator tests → build → integration tests → internal deploy → staged prod rollout), two-approver review for anything touching security rules or the Trust & Safety Functions directory, `@riverpod` code-gen-only state management, and a testing pyramid (unit/widget/rules-emulator/integration/manual-beta) with named tooling at every layer.

This model is internally consistent and buildable, with the corrections and open items in Section 2 accounted for.

## 2. Technical ambiguities and blockers found, and their resolution

Three verification passes (documented in full detail in this session; summarized here) found one genuine, previously-uncaught contradiction and several smaller gaps. All of the following are now resolved as of this document; nothing below is a silent unresolved gap in the plan that follows.

### 2.1 Resolved this pass

- **Bill-splitting Phase 0-vs-later contradiction (the single most consequential finding).** `docs/ROADMAP.md`, `docs/PRD.md`, and `docs/FEATURES.md` all previously scoped bill-splitting into Phase 0, while `TASKS.md`'s founder-confirmed build order sequenced payments after Discover. **Resolved per your direction: bill-splitting is deferred to Phase 1.** This removes Stripe/UPI payment-rail integration, the India merchant-account question, and the `splitRequests`/dispute flow entirely from Foundation's scope — a real scope reduction, not just a documentation fix. All three contradicting documents have been corrected.
- **Firebase production region.** Previously unstated beyond "a multi-region location matched to launch market" — but no India-inclusive multi-region Firestore location exists. **Decided: `asia-south1` (Mumbai), regional (not multi-region).** This is Foundation's literal first infrastructure step (`TASKS.md` item 1) and was genuinely blocking until named. One real technical consequence worth restating here since it affects the DR posture engineers should build against from day one: a regional location does not have multi-region's cross-region failover property, so a full `asia-south1` outage takes Firestore down too, compounding with the already-known single-region Cloud Functions gap rather than providing independent protection against it. This is a disclosed, accepted risk (see `docs/ARCHITECTURE.md` §7–8), not something Foundation needs to solve — but it should inform on-call/incident-response expectations from launch, not be discovered during a real outage.
- **Three non-equivalent "Phase 0 definition of done" formulations** across `ROADMAP.md`, `PRD.md`, and `TASKS.md` were not contradictory so much as three different, unlabeled checkpoints. Reconciled into a single sequence (earliest smoke-test milestone → closed-beta exit criterion → actual Phase 0→1 advancement gate) documented in `docs/PRD.md` §8. Section 5's milestone plan below is built against the *earliest* of these (the smoke-test milestone), since that's what Foundation is actually building toward first.
- **Screen 12 (Invite & Share Sheet) ambiguity** on how a Crew-less host invites a specific known contact without weakening the Closed-Table privacy model — clarified: native-share the private, capped, expiring invite link to one specific contact. No new contact-picker UI needed; this is now stated explicitly rather than left implicit.

### 2.2 Real engineering gaps, not blocking, addressed by this plan's design (Section 4 recommendations)

- **No documented client-side architecture for the offline mutation queue / idempotency-key persistence** that multiple features (Table creation, Crew creation, ratings) independently need. Left unaddressed, this risks three different hand-rolled implementations. Addressed by Recommendation R1.
- **No golden/visual-regression test tooling named**, despite a highly-specific, opinionated design system. Addressed by Recommendation R2.
- **No Firestore→Material 3 `ColorScheme` slot-mapping decided** — the design tokens cover ~11 palette values, M3's `ColorScheme` has ~30 semantic slots. Addressed by Recommendation R3.
- **Typesense has no local/CI emulation story.** **Corrected 2026-08: this is now a real Foundation blocker**, not a deferred flag — Discover's new Milestone F7 (Section 4) needs Typesense provisioned and testable in CI before that milestone can close per this project's standing verification rule (no milestone is declared complete without real, not hand-reviewed, test execution). Resolving this is part of F7's own scope, not a pre-Foundation prerequisite to solve first.
- **No SDK/OS version floors, monorepo tool decision, or backfilled ADRs for already-made architectural decisions** (Riverpod-over-Bloc, Typesense-over-Algolia, trunk-based-over-Git-Flow, GitHub-Actions-over-alternatives, Persona-over-Stripe-Identity — five qualifying decisions per `ENGINEERING_GUIDELINES.md`'s own ADR-worthy criteria, currently zero exist). Addressed by Recommendation R4/R5.

### 2.3 Genuinely open — needs a human, not an engineering decision, and does not block Foundation

Persona's Aadhaar/India-ID coverage, the Indian entity structure, India DPDP Act consent-manager specifics, IT Rules 2021 review, ToS/Privacy Policy execution, general-liability insurance binding, and trademark clearance are all real, tracked, open items (`TASKS.md`, `docs/LEGAL.md`) that gate **public launch**, not the ability to write and test code. None require an engineering decision, and — with the exception of ToS/Privacy Policy, which must be in force before any real user data is collected, even in closed beta — none block Foundation's engineering work. They are not repeated in full here; see `docs/ARCHITECTURE_READINESS_REVIEW.md` and `TASKS.md` for the complete list and classification.

**Correction, 2026-08:** Persona's Aadhaar/India-ID coverage now matters earlier than "before Phase 1 launch," since new Milestone F7 builds the real Tier 2/Persona integration during Foundation. It still doesn't block *writing and testing* that integration — Persona's sandbox/test mode is sufficient to build and verify `completeIdentityVerification` end to end without real Aadhaar coverage confirmed — but it remains a hard gate on ever flipping Discover's Remote Config flag on for real Hyderabad users, so confirming coverage directly with Persona should move up the founder's priority list rather than stay a background item to resolve "sometime before Phase 1."

### 2.4 Re-scoping Discover into Foundation, and recurring Crews out (2026-08, founder-directed)

Founder direction, given after Milestone F4 shipped: pull Discover forward into Foundation (new Milestone F7, right after F6's Trust & Safety infrastructure), and defer recurring Crews (`scheduleRecurringTable`) out of Foundation into Phase 1.

**Reasoning, as given:** Discover is TableCrew's actual competitive advantage. Coordinating gatherings with people you already know is a real problem, but not an undifferentiated one — WhatsApp groups, calendars, and generic messaging apps already solve a meaningful chunk of it. The differentiated, harder-to-replicate value is helping someone new to Hyderabad, or anyone looking to expand their circle, find a meaningful conversation with people they don't already know. That's the hypothesis most worth validating early, and the right time to validate it is once — not before — the Trust & Safety foundation (F6) is live, matching `ROADMAP.md`'s own pre-existing rationale for why Discover was sequenced after safety infrastructure in the first place. This re-scoping doesn't change *that* rationale; it changes *when relative to Foundation's other milestones* the resulting Discover build happens.

**What this required resolving, not just reordering:** Discover cannot be built in isolation — `docs/SECURITY.md`'s Tier 2-gates-Discover rule and `docs/ARCHITECTURE.md`'s Typesense-backed search design mean pulling Discover forward necessarily pulls Tier 2 identity verification and Typesense infrastructure forward with it; building Discover without either would mean shipping code that violates this project's own safety-gating principle (`docs/VALUES.md`'s "Safety is a feature, not a department") or simply doesn't function (Discover's search has no other backing store). Both are now explicitly in new Milestone F7's scope, not treated as separate later decisions.

**What this did *not* require changing:** `ROADMAP.md`'s Phase 0 product-launch scope and exit criteria (Trust & Safety proven under real load, Discover's legal/statute review) are unchanged — see the Section 0 correction above for the build-vs-launch distinction that keeps this consistent. Discover ships inside Foundation's binary, behind a Remote Config flag defaulted off, the same mechanism `docs/DEPLOYMENT.md`'s Feature Flag Lifecycle already specifies for any risky feature — this re-scoping is an application of that existing mechanism, not an exception to it.

**Recurring Crews' move to Phase 1** gets the identical treatment `docs/IMPLEMENTATION_PLAN.md` §2.1 already gave bill-splitting: a real scope reduction (not a documentation-only change), removing `scheduleRecurringTable` and Screen 26 (Recurring Table Schedule Setup) from what the Crew-management milestone (now F8, Section 4) needs to build. This also resolves a pre-existing, previously-uncaught contradiction: `docs/FEATURES.md`'s "Won't (v1)" framing of "Recurring Table series (auto-generated weekly instances)" already treated this as out of v1 scope, while `docs/PRD.md`'s FR-T14c and `docs/API_SPEC.md`'s `scheduleRecurringTable` endpoint spec described it as something actively being built — this correction settles the contradiction in favor of "real feature, just not in Foundation" (see the corresponding `docs/FEATURES.md` fix).

**Documents touched by this correction, and why:** `docs/ROADMAP.md` (Phase 0/1 build-vs-launch clarification), `docs/PRD.md` (FR-T14c phase tag, Discover FR cross-reference), `docs/FEATURES.md` (recurring-Table contradiction fix), `docs/SECURITY.md` (Persona/Aadhaar urgency), `TASKS.md` (build-order reconciliation, ADR-staleness disclosure). `docs/adr/0002-typesense-over-algolia.md` and `docs/adr/0005-persona-over-stripe-identity.md` both contain now-stale "not in Foundation's critical path" claims; per `docs/ENGINEERING_GUIDELINES.md`'s ADR-immutability policy these need superseding ADRs rather than in-place edits — **flagged as a disclosed follow-up, not done in this pass** (see `TASKS.md`).

## 3. Recommended improvements before implementation begins

- **R1 — Adopt a single client-side offline-mutation abstraction now, before the second feature needs it.** A `core/` Riverpod provider (e.g., `OfflineMutationQueue`) that generates and persists an idempotency key locally, attempts the call, and retries with the same key on reconnect — wrapped once, reused by every idempotent callable's repository method (Table creation, Crew creation, ratings, and later payments). Building this ad hoc inside the first feature that needs it (Create Table) risks two more slightly-different reimplementations by the time Crew creation and ratings are built by different people.
- **R2 — Add golden/visual-regression testing to the widget-test layer now.** `docs/DESIGN_SYSTEM.md` is unusually specific and opinionated (a distinctive warm palette chosen specifically to read as "not a dating app," a deliberate type pairing, a no-spinner skeleton-pulse convention) and itself names "engineering hard-codes a close-enough value" as a known drift risk, currently caught only by a quarterly manual audit. A lightweight golden-test suite for the core component library (buttons, cards, chips, RSVP status chips), run in CI, closes this gap cheaply and early, before dozens of screens have been built against undetected drift. **Corrected Milestone F3:** this recommendation originally named `golden_toolkit` as the tool; by the time F3 actually started, `golden_toolkit` was discontinued and `alchemist` (Very Good Ventures) had become the maintained standard that superseded it — F3 builds this suite on `alchemist` instead, same intent, different (current) tool.
- **R3 — Resolve the Material 3 `ColorScheme` slot-mapping as a documented, one-time decision, not an ad hoc per-screen judgment call.** Map TableCrew's named tokens to the M3 slots they obviously correspond to (primary→terracotta, error→brick, background/surface→the cream family) and derive the remaining ~19 unnamed slots via M3's standard tonal-palette generation from those seed colors — write the resulting mapping into the generated token file itself as the single reference, rather than leaving each engineer to independently decide what fills `tertiaryContainer`.
- **R4 — Backfill five ADRs for decisions already made and justified in prose**, per `ENGINEERING_GUIDELINES.md`'s own stated criteria: Riverpod-over-Bloc, Typesense-over-Algolia, trunk-based-over-Git-Flow, GitHub-Actions-over-alternatives, Persona-over-Stripe-Identity. This is low-effort (the justification prose already exists in `ARCHITECTURE.md`/`CI_CD.md`/`SECURITY.md`) and establishes the ADR discipline from commit one rather than after the guideline has already been silently skipped five times.
- **R5 — Pin initial SDK/tool versions and OS floors explicitly in the first scaffolding PR** (Flutter/Dart SDK, `go_router`, `riverpod_generator`, `very_good_analysis`, Firebase SDKs, Node version for Functions, iOS deployment target, Android `minSdkVersion`) rather than leaving them to accumulate implicitly across early PRs — `ENGINEERING_GUIDELINES.md` already mandates pinning exact versions as ongoing policy; this just makes the *initial* set a deliberate, reviewed choice instead of whatever each engineer's local toolchain happened to have installed.
- **R6 — Sequence Trust & Safety infrastructure alongside the core loop, not after it**, consistent with `ROADMAP.md`'s own stated rationale. Concretely: `reportUser`/`reportTable`/`blockUser`/`triggerDuressSignal`/`createLocationShare` and their UI (Screens 27–29) should land in the same milestone window as Create Table and Crew management, not as a final "safety pass" bolted on before launch — see Milestone F6 below.
- **R7 — Superseded, 2026-08 (see Section 2.4).** This recommendation originally said "defer Typesense infrastructure entirely; do not scaffold Discover-adjacent code paths during Foundation," reasoning that Screen 10's Open/Discover-visibility branch and Tier 2 verification interstitial were real but three milestones away from reachable. Founder direction has since pulled Discover into Foundation (new Milestone F7); Typesense and the Open/Discover-visibility path are now in-scope for F7, not deferred. Left here, struck through in substance, rather than deleted outright, so the original reasoning (correct at the time, for the plan as it stood then) isn't lost — R7's caution about not scaffolding a capability before its dependencies exist is exactly why F7 now builds Tier 2 verification and Typesense *alongside* Discover's UI, not ahead of or after it.
- **R8 — Produce an internal demo build at the close of every milestone, starting retroactively at F4 (founder-directed, 2026-08).** Every milestone closeout (the "Verify, document, commit" step every prior milestone has ended with) now also produces and distributes a build via Firebase App Distribution — the mechanism `docs/CI_CD.md` already names for internal/beta distribution (§"Platform Choice," stage 6) but that has never actually been exercised end to end in this project. Near-term, this is a manual step (`flutter build apk --debug` + `firebase appdistribution:distribute`, run by the founder, since neither Fastlane lanes nor a configured App Distribution tester group exist yet) rather than the fully-automated CI stage `CI_CD.md` designs — building that automation is separate, tracked work, not a prerequisite to starting the practice now. See `docs/DEPLOYMENT.md`'s new "Internal Demo Builds at Milestone Boundaries" section and `TASKS.md` for the concrete F4 catch-up build.

## 5. What happens after Foundation

Once F0–F9 ship and the earliest smoke-test milestone (`TASKS.md`: 3 Crews × 2 Tables in 6 weeks) is reached, the next checkpoint is the closed-beta exit criterion in `docs/PRD.md` §8, followed by `docs/ROADMAP.md`'s actual Phase 0→1 advancement gate. Discover ships as part of Foundation now (F7) but stays behind a Remote Config flag defaulted off through this entire sequence — reaching the smoke-test/closed-beta/Phase-0-exit checkpoints does not itself turn Discover on; that's a deliberate, separate ramp decision per `DEPLOYMENT.md`'s Feature Flag Lifecycle, made once Trust & Safety has real operating data from the Crew-first beta and Discover's legal review (state statute exposure, per `ROADMAP.md`) is cleared. Only once the Phase 0→1 gate is met does the remaining Phase 1 work begin — bill-splitting, recurring Crews, and TableCrew+ — which will need its own implementation plan at that time, informed by real Foundation-phase learnings rather than planned speculatively now.
