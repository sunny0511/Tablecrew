## 1. Purpose and Scope

This document describes the system architecture of TableCrew end to end: client, backend, third-party integrations, data flow, and the operational posture (scale, region, disaster recovery) that supports the product described in `docs/PRODUCT.md` and `PRD.md`. It is written so a new backend or mobile engineer can read it once and understand not just *what* we built but *why*, so they can extend it consistently rather than reinvent it.

Two architectural decisions anchor everything here and are treated as settled unless a migration trigger (Section 6) fires: **Flutter** for the client, **Firebase** for the backend. This document justifies both in depth, because "why not X" questions recur every time a new engineer joins, and because the justification directly shapes where we draw module boundaries (e.g., Cloud Functions organization, where Algolia sits, when we'd introduce Postgres).

Read the diagram as three planes:

1. **Client plane** — the Flutter app, talking directly to Firebase managed services wherever a security rule can safely authorize the operation (most reads, and writes that are naturally self-scoped, like a user editing their own profile).
2. **Serverless compute plane** — Cloud Functions, invoked either directly by the client (callable functions for actions with side effects or cross-document invariants) or indirectly by Firestore writes (triggers that fan out denormalized data, keep the search index in sync, send notifications).
3. **Managed third-party plane** — Typesense (search), Stripe (payments), all accessed *only* from Cloud Functions, never from the client, so that API keys/secrets never ship in the app binary and so that abuse-prone operations (charging a card, mutating a search index) pass through server-side validation first.

## 3. Why Flutter + Firebase (and why not the alternatives)

This is the most consequential decision in the codebase and the one most likely to be second-guessed by a new hire, so we lay out the reasoning in full rather than asserting it.

### 3.1 Constraints that drove the decision

- **Team size at founding:** 2-4 engineers expected to ship a cross-platform consumer app to both app stores within a quarter, then iterate weekly based on user feedback.
- **Product shape:** a mostly-CRUD, real-time-social app (profiles, gatherings, chat-adjacent features, RSVP state machines) with a genuinely hard sub-problem (Discover's geo+interest matching and trust/safety) rather than a computationally exotic core. This shape is exactly what serverless BaaS platforms are built for.
- **Time-to-market pressure:** gatherings apps live and die on network density in a city; the cost of shipping three months late is existential in a way that the cost of "using a slightly less flexible backend" is not, at this stage.
- **Uncertainty about product-market fit:** we expect to change the data model and add/cut features frequently in the first 12-18 months. Any architecture chosen now must optimize for cheap schema and feature iteration over long-run theoretical performance ceilings.

### 3.2 Flutter vs. native iOS/Android (Swift/Kotlin) vs. React Native

**Native (separate Swift and Kotlin codebases):** rejected. Two native codebases mean two implementations of every feature, every bugfix twice, and two teams' worth of platform expertise — infeasible for a 2-4 person founding engineering team. Native's advantages (best-in-class platform integration, marginally better perf on animation-heavy UI) don't matter for TableCrew's UI complexity, which is standard forms, lists, maps, and chat — well-trodden ground for cross-platform frameworks. We would only reconsider native if a specific feature required deep platform capability unavailable cross-platform (e.g., a novel ARKit-based experience), which is not on our roadmap.

**React Native:** the real alternative we weighed against Flutter. RN wins on "hire from a larger JS talent pool" and reuse of web engineering skill. Flutter wins on the axes that matter more for us:
- **Rendering consistency:** Flutter renders its own widget tree via Skia/Impeller rather than bridging to native UI components, so pixel-perfect, animation-heavy UI (RSVP status transitions, Table cards, chat bubbles) behaves identically on iOS and Android without platform-specific tuning. RN's reliance on native components (and historically, the JS bridge) has a longer tail of platform-specific bugs.
- **Performance predictability:** Flutter compiles to native ARM/x86 code (AOT) with no JS bridge in the hot path; this matters for map rendering and list scrolling on Discover, which is core to the product's most important screen.
- **Tooling and null-safety:** Dart's sound null safety and hot reload give a tighter edit-test loop than the RN/TypeScript combination in practice, and Dart's single-threaded-with-isolates model is simpler to reason about than RN's evolving new-architecture (Fabric/TurboModules) migration, which was still stabilizing when this decision was made and represented a moving-target risk for a small team that can't afford to chase framework churn.
- **First-party Firebase support:** `FlutterFire` is maintained by the Firebase team itself with parity across products (Auth, Firestore, Functions, Messaging, App Check, Remote Config, Crashlytics, Analytics, Storage) on a predictable release cadence. RN's Firebase bindings (`@react-native-firebase`) are excellent but third-party-maintained; first-party support reduces our exposure to breaking changes arriving unpatched.

Net: RN would have been a defensible choice; Flutter is the better one for a small team building a visually consistent, map- and list-heavy, Firebase-backed app, and it's the one we're committing to.

### 3.3 Firebase vs. a custom Node/Postgres backend from day one

This is the second load-bearing decision. A custom backend (e.g., Node/NestJS + Postgres + Redis on a container platform) would give us: full SQL relational modeling, complex joins for analytics, more backend engineering control, and no per-operation vendor pricing. We rejected it for day one for these reasons:

- **Time-to-market:** a custom backend means someone has to build and operate auth, session management, authorization middleware, database migrations, a real-time layer (websockets or polling) to replace Firestore's listeners, push notification plumbing, file upload/moderation infrastructure, and a deploy pipeline — all before writing a single line of Table-matching logic. Firebase gives us all of that as managed, pre-integrated infrastructure on day one, which for a team our size is the difference between shipping in one quarter and shipping in two-to-three.
- **Operational burden:** a 2-4 person engineering team cannot also be a 2-4 person SRE team. Firebase's managed scaling, backups (see Section 8), and multi-AZ durability remove an entire category of on-call burden that a self-hosted Postgres/Node stack would otherwise impose.
- **Real-time is native, not bolted on:** Firestore's client SDK gives us live-updating RSVP counts and Crew chat via listeners with offline cache and reconnection handled for us (Section 5). Building equivalent behavior against Postgres means standing up a websocket/pubsub layer (e.g., Postgres LISTEN/NOTIFY behind a socket server, or a separate service like Ably/Pusher) — solvable, but it's incremental infrastructure we get for free with Firestore.
- **Cost-of-ownership at our current scale:** Firebase's usage-based pricing is more expensive than a self-hosted Postgres box *per read/write at high volume*, but at pre-PMF and early-growth scale (thousands, then tens of thousands of MAU) the usage-based bill is small relative to the fully-loaded cost of the infrastructure engineering time a custom backend would consume. We are deliberately trading a higher marginal unit cost later for a much lower fixed engineering cost now — a trade that only makes sense because we expect (and plan for, Section 6) to graduate off pure-Firestore for the specific workloads where it stops being the cheaper option.

We do **not** claim Postgres is the wrong long-term choice for every workload — see Section 6 for exactly which workloads we expect to migrate, and under what trigger conditions. The point of this section is that "Firebase now, targeted Postgres later for specific hot spots" dominates "Postgres from day one" given our constraints.

### 3.4 Summary decision table

| Axis | Native (Swift+Kotlin) | React Native | **Flutter (chosen)** | Custom Node/Postgres | **Firebase (chosen)** |
|---|---|---|---|---|---|
| Team size fit (2-4 eng) | Poor — 2x build cost | Good | **Best** | Poor — needs SRE capacity | **Best** |
| Time-to-market | Slowest | Fast | **Fast** | Slowest | **Fastest** |
| Real-time features | Manual per platform | Manual (sockets) | Manual (sockets) | Manual (sockets/LISTEN) | **Native (Firestore listeners)** |
| Relational/complex analytics | N/A | N/A | N/A | **Best** | Weak (mitigated via BigQuery export) |
| Long-run marginal cost at huge scale | N/A | N/A | N/A | **Best** | Worse (mitigated by planned migration) |
| First-party Firebase integration | Good (native SDKs) | Good (3rd-party) | **Best (FlutterFire, 1st-party)** | N/A | N/A |

## 4. Client Architecture

### 4.1 App structure

The Flutter app is organized feature-first, not layer-first: `lib/features/{tables,crews,discover,ratings,trust_safety,payments,profile}/`, each containing its own `data/` (Firestore/Functions repositories), `domain/` (models, use-cases), and `presentation/` (widgets, screens, providers) sub-folders, plus a shared `lib/core/` for cross-cutting concerns (theming per `DESIGN_SYSTEM.md`, routing, the Firebase service wrappers, and error handling). This mirrors how Cloud Functions are organized by domain (Section 5.1), so a feature's client and server code are easy to find side by side conceptually even though they live in separate deploy artifacts.

### 4.2 State management: Riverpod (chosen) vs. Bloc, Provider, GetX

We standardize on **Riverpod** (specifically `flutter_riverpod` with code generation via `riverpod_generator`) as the app's sole state-management approach. Justification against the alternatives, evaluated against our actual constraints (small team, heavy reliance on async Firebase streams, need for testability without a UI harness):

- **vs. Provider:** Riverpod is the direct successor to Provider, written by the same author (Remi Rousselet) specifically to fix Provider's structural issues — Provider requires a `BuildContext` to read state, which couples business logic to the widget tree and makes providers hard to access from outside `build()` methods (e.g., inside Cloud Functions callback handlers or background isolates). Riverpod removes that coupling entirely: providers are declared as global, compile-time-safe objects and can be read anywhere. For an app whose core data (Tables, RSVPs, Crew chat) is delivered as continuous Firestore `Stream`s, Riverpod's `StreamProvider`/`AsyncNotifierProvider` primitives map directly onto "subscribe to this query, expose loading/data/error states" with almost no boilerplate — this is the single most common pattern in the app and Riverpod was built for exactly this.
- **vs. Bloc (flutter_bloc):** Bloc's explicit separation of events and states gives excellent auditability and is a legitimate choice for large teams that need strict conventions enforced across many contributors. For a founding team of 2-4 engineers, Bloc's ceremony (defining event classes, state classes, and a bloc/cubit per feature, then wiring `BlocProvider`/`BlocBuilder` in the tree) is more boilerplate than it buys us in return, and it does not have a first-class answer to "expose a Firestore stream as widget-consumable state" that's as direct as Riverpod's `StreamProvider` — you end up writing a Bloc that itself subscribes to the stream and re-emits states, which is an extra layer over what Riverpod gives natively. We would reconsider Bloc if the team grows past ~15 engineers and we need to enforce a stricter, more uniform pattern across many contributors simultaneously touching the same features; that is not our situation now.
- **vs. GetX:** GetX bundles state management, routing, and dependency injection into one package with very little boilerplate, which is attractive for speed, but it achieves that speed by relying on ambient/global mutable singletons and reflection-like patterns that are harder to unit test in isolation and have a well-documented history of app-wide side effects that are difficult to trace (state changes not going through a scoped, typed provider graph). Given that TableCrew's safety-sensitive logic (RSVP state transitions, block/report flows) needs to be easy to unit test with confidence, we avoid GetX's implicit-global-state model in favor of Riverpod's explicit, override-able provider graph, which lets us trivially substitute fake Firestore/Functions repositories in tests (`ProviderScope(overrides: [...])`).
- **Testability, concretely:** every data-access class (e.g., `TablesRepository`, `CrewsRepository`) is exposed via a Riverpod provider and consumed by domain-level providers (`AsyncNotifierProvider`) that hold UI-ready state. Widget tests and unit tests override the repository providers with fakes, so we test business logic (e.g., "a Table transitions from Filling to Confirmed once headcount is met") without touching real Firebase, and UI tests render against a `ProviderScope` with controlled fake state instead of live network calls.
- **Code generation:** we use `@riverpod` annotations (via `riverpod_generator`/`build_runner`) rather than hand-written `StateNotifierProvider` boilerplate, both for conciseness and because generated providers give us compile-time-checked `.family` parameterization (e.g., `tableProvider(tableId)`), which we use constantly (every Table detail screen, every Crew screen is parameterized by an ID).

### 4.3 Navigation

We use `go_router` for declarative, URL-based routing (important for deep links from push notifications — e.g., tapping an RSVP reminder push opens `/tables/{tableId}` directly — and for Firebase Dynamic Links successors used in invite flows). Route guards check Riverpod auth-state providers to redirect unauthenticated users to onboarding.

### 4.4 Client responsibilities vs. Cloud Functions responsibilities

A recurring design question is "should this logic live in the client or in a Cloud Function?" The rule we apply: **the client may read anything a security rule allows, and may write anything that is naturally self-scoped and doesn't require cross-document invariants; everything else goes through a callable function.** Concretely:

- Client-direct-to-Firestore (governed by Security Rules, see `DATABASE.md` §6): reading Table/Crew/Discover documents the user is authorized to see; a user editing their own profile fields; a user writing their own RSVP document's soft fields (e.g., toggling a "bringing a plus-one" note) that don't change Table capacity math.
- Must go through a Cloud Function: anything that touches headcount invariants (`requestSeat`, `confirmAttendee` — two users could race to fill the last seat, so this must be a transaction server-side), anything that mutates another user's data (host confirming an attendee), anything involving Stripe, anything that must fan out to the search index or send a push notification, and all Trust & Safety actions (reports must not be readable/writable by the reported user, which client-side rules alone make awkward to enforce alongside side effects like alerting the safety queue).

## 5. Backend Architecture: Cloud Functions Organization

### 5.1 Directory/module organization

Cloud Functions (Gen 2, Node.js/TypeScript runtime) are organized by product domain, mirroring the client's feature folders: `functions/src/{tables,crews,discover,ratings,trust_safety,payments,notifications,shared}/`. Each domain folder contains its callable functions, its Firestore trigger functions, and domain-specific helper modules. A `shared/` module holds cross-cutting concerns: the Firestore client wrapper, the Stripe SDK client, structured logging helpers, and shared validation (e.g., Zod schemas for request payloads, reused between callable input validation and internal helpers).

### 5.2 Callable (HTTPS callable) functions vs. Firestore-triggered functions — when to use each

This distinction is the backbone of backend design and is worth stating as an explicit rule rather than case-by-case judgment:

**Use an HTTPS callable function when:**
- The action is user-initiated and needs an immediate success/failure response the client must react to synchronously (e.g., `requestSeat` needs to tell the UI right away whether the seat was granted or the Table filled first).
- The operation must enforce an invariant across multiple documents atomically (Firestore transactions), such as incrementing a Table's `confirmedCount` and creating an RSVP document together, which must not be left to two independent client writes that could race or partially fail.
- The operation touches a paid third-party API with a secret (Stripe) or a search index (Typesense) that must never be reachable with client-supplied credentials.
- The operation requires authorization logic more complex than security rules can express cleanly (e.g., "only the Table host, or a Crew admin if this is a Crew-recurring Table, may cancel").

Full list of callables and contracts: `API_SPEC.md`.

**Use a Firestore-triggered function (`onDocumentCreated`/`onDocumentUpdated`/`onDocumentWritten`) when:**
- The side effect is a *reaction* to a state change rather than the primary action itself, and doesn't need to block the client's write from succeeding. Examples: when an RSVP document is created with status `confirmed`, a trigger increments the denormalized `confirmedCount` field on the parent Table (in cases where the count wasn't already updated transactionally by the callable that created it) and re-evaluates whether the Table should transition `Filling → Confirmed`; when a Table document's `status`, `location`, or `interestTag` changes, a trigger upserts the corresponding Typesense document (Section 5.4); when a Rating is written, a trigger recomputes the rated user's aggregate rating fields on their User document; when a Report is created, a trigger notifies the Trust & Safety on-call queue.
- The effect is fan-out to a system the original caller shouldn't have to wait on synchronously (search index sync, push notification dispatch, analytics event mirroring to BigQuery-adjacent collections) — decoupling these into triggers keeps callable latency low and keeps failure isolated (a Typesense hiccup should never fail a user's `createTable` call).
- We want the same side effect to happen consistently regardless of *how* a document was written (e.g., an admin correcting data in the Firebase console should still trigger the same denormalization fixups a normal client write would) — triggers guarantee this in a way that "the callable also updates the derived field" does not.

**Rule of thumb we tell new engineers:** if the client needs to know the outcome before moving on, it's a callable. If the "outcome" is really "something else in the system should now also be true," it's a trigger. Most features need both: a callable for the primary write plus one or more triggers for derived consequences.

### 5.3 Scheduled functions

Cloud Scheduler-triggered functions handle time-based logic that isn't a reaction to any single write: RSVP reminder pushes (T-24h and T-2h before a Table), Table-day-of nudges, Crew re-engagement prompts for Crews with no upcoming Table after N weeks, waitlist-to-confirmed promotion sweeps for Tables where a confirmed attendee cancelled, and marking Tables `Happened` once their scheduled time has passed (a lightweight sweep rather than requiring every client to do this locally). See `FIREBASE.md` §4 for the full messaging strategy these jobs drive.

### 5.4 Real-time features: how they actually work

TableCrew's "real-time" feel (live RSVP counts, Crew chat, live Table status) is implemented entirely via **Firestore's native real-time listeners** — there is no separate websocket infrastructure.

- **Live RSVP counts:** the Table detail screen holds a Riverpod `StreamProvider` subscribed to the Table document (`tables/{tableId}`) and, separately, to the RSVP subcollection query filtered to `status == confirmed`. Firestore pushes incremental updates to every subscribed client over a long-lived gRPC/WebChannel connection; the client SDK maintains a local cache so the UI updates optimistically the instant a local write is queued, then reconciles when the server confirms. This is why capacity-affecting writes are funneled through callables (Section 4.4/5.2): the client can still *display* an instant optimistic update, but the authoritative count and Table-status transition happen server-side inside a transaction, and every listening client converges to the same server-confirmed state within tens to a couple hundred milliseconds in the common case.
- **Crew chat:** implemented as a `messages` subcollection under each Crew document (`crews/{crewId}/messages/{messageId}`), ordered by server timestamp, with clients subscribing to the latest N messages via a listener (`orderBy('createdAt', descending: true).limit(50)`, paginated further back on scroll). This is intentionally *not* a bespoke chat service (e.g., not Stream Chat or Sendbird) at this stage: Crew chat is a lightweight, in-context feature (coordinating logistics for a Crew's Tables), not a general-purpose messaging product, and Firestore listeners handle its throughput (small groups, bursty-but-low-volume) comfortably. If Crew chat evolves into a heavier feature (typing indicators at scale, read receipts across large groups, media-rich threads), we would evaluate a dedicated chat provider at that point rather than over-building this from day one.
- **Presence/typing indicators**, where used, are implemented via Firestore documents with short TTL semantics (a `typing/{userId}` doc updated on keystroke, swept by a scheduled function or client-side staleness check) rather than Firebase Realtime Database, to avoid running two different real-time datastores. We accept slightly higher latency/cost than a purpose-built presence system (RTDB or a dedicated presence service) in exchange for one less system to operate; this is a deliberate, revisitable trade, not an oversight.

### 5.5 Discover: geo + interest matching architecture

Firestore has no native support for combined geospatial-radius + multi-field-equality + relevance-ranked queries — its `where` clauses support limited compound-range queries but not "within X km AND matches interest tag AND rank by proximity+recency," which is exactly Discover's core query. Two options exist for closing this gap: **Algolia** and **Typesense**. We recommend and use **Typesense** (self-hosted-option-capable, but we consume it as **Typesense Cloud**, a managed offering) for the following reasons:

- **Cost model at our stage:** Typesense Cloud's pricing is capacity-based (cluster size) rather than Algolia's dominant per-operation/per-record pricing model, which is significantly cheaper at our expected query volume once Discover search becomes a frequently-hit surface (every app open on the Discover tab is a search). Algolia's pricing is excellent at very low volume and at enterprise scale with a negotiated contract, but the middle band — a growing consumer app doing thousands of geo searches a day — is where Typesense's flat-capacity model wins on predictability and total cost.
- **Native geo-search primitives:** Typesense has first-class `geopoint` field types with radius and bounding-box filtering combined with standard filter/sort clauses in the same query, which maps directly onto "Tables within 5km, tag=hiking, sorted by start time" — the same feature set Algolia offers, but Typesense's query syntax for combining geo + facet filters + sort is simpler to construct dynamically from Flutter, which matters because Discover's filter UI (radius slider, interest chips, time window) needs to build these queries client-side (read-only, scoped API key) without a Cloud Function round-trip on every filter tweak.
- **Open-source core / avoids hard lock-in:** because Typesense is open-source at its core, we retain a credible self-hosting path if pricing or roadmap ever diverges from our needs, without a rewrite of index schema or query code — we'd point the same client at a self-hosted cluster. Algolia has no equivalent open-source escape hatch. This matters given our "Firebase now, evaluate targeted migrations later" posture (Section 6): we prefer every non-Firebase dependency to also have a low-lock-in exit.
- We explicitly considered Firestore-native geohash-based queries (e.g., using `geoflutterfire` with geohash range queries) as a zero-additional-vendor option, and rejected it as the primary mechanism: geohash range queries produce a superset of results near cell boundaries that must be filtered client-side, cannot combine cleanly with the interest-tag + freshness + capacity-remaining filtering Discover needs in one query, and have no relevance ranking. We still use Firestore as the document of record; Typesense is purely a derived, disposable search index.

**How the sync works (architecture):** Firestore remains the source of truth for every Table document. A Firestore-triggered function (`onDocumentWritten` on `tables/{tableId}`) fires whenever an Open Table's searchable fields change (location, interest tag, headcount/capacity remaining, status, start time) and upserts a corresponding document into the Typesense `tables` collection; when a Table leaves the Open/Discover-eligible state (closed, cancelled, full, or past its start time) the trigger deletes it from the index. Because the index is fully derived and rebuildable from Firestore, it requires no backup of its own (Section 8) — worst case we replay a backfill Cloud Function that scans eligible Tables and re-upserts them. The Flutter client queries Typesense directly using a search-only scoped API key (read-only, no write/admin scope, and scoped further with Typesense's built-in per-request filtering to prevent a client from querying fields it shouldn't) for low-latency, client-driven filter interaction, and only calls back into Firestore/Cloud Functions once the user acts on a result (e.g., `requestSeat`).

**Typesense Cloud availability (distinct from data loss):** the rebuildability story above answers "what if the index's data is wrong or lost," not "what if Typesense Cloud itself is unreachable" — a real outage class we owe an explicit answer to rather than leaving Discover's behavior during a third-party outage undocumented. The Flutter client's Typesense queries are wrapped with a short client-side timeout and circuit breaker; on repeated failure/timeout, the client falls back to calling the `searchTables` callable (`API_SPEC.md` §3.3) configured in a **degraded, Firestore-native mode**: it runs the composite-indexed Firestore query already maintained for exactly this purpose (`DATABASE.md` §5, "Discover fallback/secondary queries" — `visibility`/`status`/`startTime`), applies a coarse bounding-box prefilter on `location.geopoint` client-side or via a geohash range (accepting the false-positive-near-boundary imprecision noted in this section) instead of Typesense's native radius query, and drops relevance ranking entirely in favor of a simple recency/proximity sort. This is a **deliberate, disclosed degradation, not a silent one**: the client surfaces a "showing basic results while search is temporarily limited" state rather than pretending nothing changed, and the fallback path is explicitly load-tested and exercised in a game day (`DEPLOYMENT.md`) rather than left as untested code that only runs during a real incident. We accept that fallback search quality (no facet+geo+relevance combination) is materially worse than the primary path — this is a deliberate scope/cost trade given Discover-during-a-third-party-outage is a rare event, not a design gap we're unaware of.

## 6. Scalability Plan and Migration Triggers

Firebase/Firestore is not a permanent ceiling — it's the right *starting* architecture, and we plan explicitly for where it stops being the right one, so that migration is a deliberate scheduled evolution rather than a fire drill.

**What scales well on pure Firestore, likely indefinitely:** per-document and per-collection reads/writes at the access patterns TableCrew has (fetch a Table, list a user's RSVPs, list a Crew's members) scale horizontally by design — Firestore shards collections automatically and there's no single database server to outgrow for this kind of key-value/document access. We do not expect to need to move core Table/RSVP/Crew CRUD off Firestore at any scale we can currently foresee (low hundreds of thousands of MAU and beyond).

**Explicit migration triggers** — we treat any of the following, once it becomes true, as the signal to start a scoped (not full-rewrite) migration:

1. **Complex relational analytics and venue-partnership reporting outgrow BigQuery-export-and-query.** We already export Firestore/Analytics data to BigQuery (`FIREBASE.md` §on Analytics) for our own metrics dashboards. The trigger is when *operational* (not just analytical/offline) product features need real-time relational joins — e.g., a Venue Partner Portal that needs live, complex, multi-table joined queries (a venue's fill-rate trends joined against Crew demographics joined against repeat-visit cohorts, served interactively to a venue partner logging into a dashboard) that BigQuery's batch/interactive-but-not-transactional model and Firestore's join-less model both handle poorly. At that point we introduce a **dedicated Postgres service** (e.g., Cloud SQL or a managed Postgres), fed by a change-data-capture pipeline off Firestore (via the same trigger-function pattern already used for Typesense sync, or Firestore's native BigQuery export extension feeding a downstream ETL into Postgres), scoped *only* to the reporting/analytics domain — not a wholesale replacement of the operational Firestore data model.
2. **Search/matching logic outgrows what a hosted search index can express.** If Discover's matching evolves from "geo radius + interest tag filter" into something requiring heavier server-side ranking logic, ML-based recommendation scoring, or joins against relational venue/partner data at query time, we would introduce a small dedicated matching service (still fed by the same Firestore-as-source-of-truth pattern) rather than continuing to stretch Typesense's query language.
3. **Write contention on a single hot document.** Firestore document writes are rate-limited in practice to roughly one sustained write per second per document before contention/latency degrades (this is a real Firestore characteristic, not Firebase-specific hand-waving). If a single Table or Crew document becomes a genuine hotspot (e.g., a viral Open Table with hundreds of simultaneous `requestSeat` attempts), the fix is architectural sharding of the hot counter (distributed counter pattern: sub-collection of shard documents summed on read) — we would implement this targeted pattern for the specific hot-spot collection well before it would justify abandoning Firestore broadly. **Until that trigger fires, we still need to be honest about the interim failure mode:** `capacity.max` is product-bounded to 8 (corrected 2026-08 from an earlier 12 — see `PRODUCT.md`'s headcount correction and `DATABASE.md` §3.2), so sustained contention on a single Table document is inherently capped in a way a general marketplace counter wouldn't be, but a viral moment can still produce a burst of concurrent `requestSeat` transactions against one Table document that exceeds ~1 write/sec, causing Firestore to abort some transactions under contention rather than because the Table is actually full. `requestSeat` (`API_SPEC.md` §3.1) handles this with the Firestore client's built-in transaction auto-retry (bounded, with backoff) for `ABORTED` errors; if retries are exhausted under sustained contention, the callable returns a distinct, retryable error (`SEAT_REQUEST_CONTENTION`, not `TABLE_FULL`) so the client can distinguish "try again in a moment" from "this Table is genuinely full" and so we don't mislabel a transient contention failure as a capacity fact in product analytics.
4. **Sustained, predictable read/write volume where the marginal Firestore per-operation cost measurably exceeds the fully-loaded cost of operating equivalent infrastructure ourselves**, evaluated at a real quarterly cost review (see `FIREBASE.md` §cost management) — not a one-time spike, but a durable trend that survives query/index optimization and caching. This is a business/finance-triggered migration, not a technical-ceiling one, and is the least likely trigger to fire early given Section 3.3's reasoning.
5. **Compliance/data-residency requirements Firebase's regional configuration cannot satisfy** for a specific target market (Section 7) — e.g., a country requiring data to never leave a jurisdiction for which Firebase has no regional multi-region location — would force a per-region data-plane exception, most likely implemented as a regionally-isolated Firebase project (still Firebase, different region) rather than an off-Firebase migration; only a jurisdiction requiring a *specific certified provider* Firebase cannot offer would force a genuine platform migration for that region alone.

None of these are "Firebase failed"; they're "this specific workload outgrew the general-purpose tool, so give it a purpose-built one," exactly the way we already treat Typesense (purpose-built for search) as a deliberate complement to, not a replacement of, Firestore.

## 7. Multi-Region and Data Residency (Global-First)

Per `VALUES.md`'s global-first principle, data residency and internationalization are architectural decisions made now, not retrofitted later.

- **Firestore location:** each Firebase project's Firestore database is pinned to a specific multi-region or regional location at creation time and cannot be changed without a data migration, so region selection is a launch-market decision, not a runtime one. **Decided 2026-08 (closing a gap an implementation-readiness review found — this was previously unstated despite `TASKS.md` naming "found the Firebase project" as the literal first, blocking Phase 0 step): `tablecrew-prod`'s Firestore database is pinned to the regional location `asia-south1` (Mumbai), not a multi-region location.** As of this writing, Google Cloud does not offer a multi-region Firestore location covering India — the available multi-region options (`nam5`, `eur3`, `asia1`, etc.) either don't include India at all or don't provide the low-latency, data-in-country property that both user experience and India's data-residency expectations (`LEGAL.md` §11, DPDP Act) call for. A single-country regional location is therefore the correct choice for the Hyderabad launch, not a compromise — but it means the multi-region resilience properties described next do **not** apply to our actual production database, which is worth stating plainly rather than leaving the reader to assume otherwise from the general "multi-region" framing below. `tablecrew-dev` and `tablecrew-staging` are pinned to the same region for environment parity. This decision should be revisited only if Google adds an India-inclusive multi-region location, or when a future market (Phase 3+) makes a different region's data-residency requirements the binding constraint for a new, separate project.
- **What "multi-region Firestore" actually buys us, precisely stated:** a multi-region location (e.g., `nam5`, `eur3`) synchronously replicates every write across multiple independent Google Cloud regions before acknowledging it, and continues to serve both reads and writes if a single constituent region becomes unavailable — this is a genuine, real-time durability and availability property, not just "backups in more than one place," and we should describe it that way rather than either overstating it as full active-active multi-master (it isn't — there's no independent per-region write master with asynchronous cross-region reconciliation/conflict resolution the way a true multi-master database works; it's one logical database with synchronously replicated storage) or underselling it as mere cross-zone replication. **Critically, this guarantee is scoped to the Firestore data plane only.** Cloud Functions (Gen 2, built on Cloud Run) are deployed to a single specific region per function (we deploy to one region matched to our primary user base), and Firebase Auth, while a global control plane for identity, still depends on regional infrastructure for parts of the token-verification path. Because almost every capacity-, payment-, and Trust & Safety-critical write in this system is funneled through a callable Cloud Function by design (§4.4/§5.2) — not a direct client-to-Firestore write — **a regional outage affecting the Cloud Functions region takes the application down for all practical purposes even if the Firestore multi-region database itself is still healthy and serving traffic.** This is a real architectural gap, not a hypothetical: Firestore's multi-region resilience does not translate into application-level regional failover today, because the compute layer that gates every meaningful write is single-region. We accept this as the current posture; see the RPO/RTO statement in Section 8 and what a genuine active-active posture would require.
- **Project-per-region-cluster strategy for future international expansion:** rather than attempting a single global Firestore database (which Firestore's model doesn't support natively — a database lives in one location) to serve users worldwide with low latency and jurisdictional data residency simultaneously, we plan to stand up additional, isolated Firebase projects per major region/regulatory zone as we expand internationally (e.g., a separate project for an EU-resident user base once that market matters, satisfying residency expectations under regimes like GDPR that scrutinize cross-border transfer), with user records routed to the correct regional project at signup based on declared/detected residency. This mirrors how large consumer apps handle EU data residency without a full backend rewrite, and it is why our data model (`DATABASE.md`) avoids any hard-coded assumption that all Users live in one collection in one project.
- **i18n at the schema level:** user-facing strings that are data (not code), such as an interest tag's display label or a Venue's name, are modeled to support locale-appropriate rendering (i.e., we do not bake English-only assumptions like fixed string concatenation order into stored fields — see `DATABASE.md` field-level notes on `Venue.name`/`interestTag` handling), and all timestamps are stored as UTC (Firestore `Timestamp`) with locale/timezone conversion strictly a client presentation concern, never stored pre-converted.
- **Compliance surface:** App Check, Firestore Security Rules, and Cloud Functions authorization checks are the same across regions; what differs per region is data location and, where applicable, additional consent-capture fields on the User document for region-specific regulatory requirements (handled as additive schema fields, not per-region schema forks).

## 8. Disaster Recovery and Backup (Architecture-Level)

At the architecture level (operational detail — schedules, runbooks, RTO/RPO targets — lives in `DEPLOYMENT.md`):

- **Firestore** durability against *infrastructure* failure (a lost zone, or — for a multi-region location — a lost region) is handled by Google's synchronous replication within the configured location (Section 7). **For a genuine multi-region location, this gives an effective RPO ≈ 0 and RTO ≈ 0 at the data-plane level even through a full regional loss. Our actual production database does not have that property** — per Section 7's 2026-08 decision, `tablecrew-prod` uses the regional location `asia-south1` (Mumbai), not a multi-region location, because no India-inclusive multi-region option exists. A regional Firestore location still synchronously replicates across multiple zones *within* `asia-south1`, so RPO ≈ 0/RTO ≈ 0 holds against a lost zone, but **a full regional outage in `asia-south1` would take Firestore itself down, compounding with the pre-existing Cloud Functions single-region gap described below** rather than providing an independent layer of protection against it. This is a deliberate, disclosed risk acceptance consistent with launching in the only regional location that satisfies India's data-residency expectations, not an oversight — and it means the "genuine active-active DR posture" discussion two paragraphs down would, for us, require solving both a multi-region Firestore *and* a multi-region Cloud Functions problem simultaneously, not just the latter. On top of zone-level replication, we configure **scheduled Firestore managed exports** (via the Firestore export/import mechanism, orchestrated by a scheduled Cloud Function calling the Admin API, landing in a Cloud Storage bucket) as our point-in-time recoverability mechanism against **logical** failures — accidental mass deletion, a bad migration script, or a compromised credential — which infrastructure replication does not protect against (a bad delete replicates just as faithfully as a good write). For this failure class, our realistic **RPO is bounded by the export interval** (the exact cadence is set in `DEPLOYMENT.md`; given this data includes RSVP/payment-adjacent state, we recommend that cadence be no coarser than a few hours, not once daily, and `DEPLOYMENT.md` should state the chosen number explicitly rather than leaving it implicit), and our realistic **RTO is on the order of hours**, not minutes — recovering from a logical failure means running an Admin API import of the last good export into a (possibly new) database and re-pointing Cloud Functions/clients at it, which is an operational procedure with real setup and validation time, not an instantaneous failover.
- **The gap this section must be explicit about:** none of the above protects against a **regional outage in the single region our Cloud Functions are deployed to** (Section 7). In that scenario Firestore's own data plane may be fully healthy, but the application is still effectively down, because capacity/payment/Trust & Safety writes cannot reach a callable. Our current architecture has **no compute-layer regional failover** — RTO for "our Cloud Functions region is down" today is, honestly, "however long it takes Google to restore that region," which is outside our control and not bounded by anything we operate. A genuine active-active DR posture would additionally require: deploying Cloud Functions to at least two regions behind a health-checked router/load balancer, making App Check/rate-limit-counter state consistent across those regions, and handling cross-region idempotent retries so a failover mid-transaction doesn't double-process a payment or seat request. This is real, non-trivial engineering scope, and we treat it as explicitly out of scope until a stated trigger fires — e.g., a signed enterprise/Teams (B2B2C) contract with an availability SLA that a single-region compute layer cannot meet, or a realized regional outage that produces material, recurring revenue impact. Until then, single-region Cloud Functions with the DR posture described above is a deliberate, disclosed risk acceptance, not an oversight.
- **Cloud Storage** (photos) is configured with object versioning in the primary bucket so an accidental overwrite/delete is recoverable within the configured retention window, in addition to being logically reconstructable from the User/Table documents that reference it.
- **The Typesense index requires no independent backup strategy for data-loss purposes**, by design (Section 5.5) — it is fully and cheaply rebuildable from Firestore via a backfill function, so it is explicitly excluded from DR planning as a primary data store. This is distinct from Typesense Cloud *availability* (the service being reachable at all), which is addressed separately in Section 5.5 as a graceful-degradation concern for Discover, not a data-loss/DR concern.
- **Stripe** remains the system of record for payment and payout state; we do not attempt to reconstruct authoritative financial state from our own database and instead treat our Firestore payment-related documents (Section in `API_SPEC.md` §Payments) as a cache/mirror of Stripe state, reconciled via webhooks — this means a full Firestore restore is never a payments-correctness risk, only a UX-staleness one until reconciliation catches up.
- **Security rules and Cloud Functions source** are version-controlled and deployed via CI/CD (`CI_CD.md`), so "configuration disaster recovery" (a bad rules deploy locking out legitimate users, or a bad Function deploy) is recovered via rollback-to-last-known-good-deploy, not via any data restore.
