## 1. Purpose and Scope

This document describes, product by product, which Firebase services TableCrew uses, why each was chosen over alternatives, how it's configured conceptually (not literal `firebase.json`/config file contents — those live in the repo, not in prose docs), our environment (dev/staging/prod) strategy, and our cost-management posture. Read this alongside `ARCHITECTURE.md` (system-level rationale for Firebase generally) and `DATABASE.md`/`API_SPEC.md` (how Firestore and Cloud Functions are actually used).

## 2. Firebase Products in Use and Why

### 2.1 Firebase Auth — phone number + Sign in with Apple/Google

**We treat phone-number verification as the primary, default identity method**, with Sign in with Apple and Sign in with Google offered as fast-path alternatives that still require phone verification to be completed before a user can host or join a Table (not merely at account creation, enforced via `verification.phoneVerified` gating in `DATABASE.md` §3.1 and checked in relevant callables per `API_SPEC.md`).

**Why phone-first for a safety-sensitive, in-person product**, justified against the alternative of email/password or social-login-only:

- **Real-world accountability, not just an inbox.** TableCrew's entire premise is meeting strangers or near-strangers in person. A phone number is materially harder to mass-fabricate than an email address (email aliasing/disposable inboxes are trivial; SIM/phone-line acquisition has real friction and cost), and it's the credential most directly tied to a persistent, reachable real-world identity — which matters both for our own abuse-prevention signal (a phone number gives Firebase Auth's own SMS-based anomaly detection a much stronger substrate than free-form email signup does) and for a very concrete safety property: if a Table goes wrong, having verified that every attendee's account is backed by a real, distinct phone line is a meaningfully stronger baseline than email-only signup, even before we layer on ID verification for Discover.
- **Lower-friction onboarding than password-based email**, which matters for conversion on a first-open flow: no password to create/remember, no email-verification-link round-trip that drops users mid-funnel — Firebase Auth's phone flow is a single OTP round-trip.
- **Social login (Apple/Google) alone is insufficient** as the sole identity method because it authenticates "this is the same person who owns this Apple/Google account," not "this is a real, distinct, reachable individual" in the way a phone number tied to a carrier does, and because a meaningful share of the population uses Apple/Google accounts that are easy to spin up in bulk (free Gmail accounts) in a way a phone line is not. We keep Apple/Google as convenience *linking* options (faster subsequent sign-in, and Apple Sign-In is an App Store requirement whenever we offer any third-party social login) layered on top of the phone-verified identity, not as a substitute for it.
- **Firebase Auth natively supports exactly this composition** — phone auth as the primary provider, with Apple/Google as additional linked providers on the same Auth user record — without any custom identity-federation code, which is why this is a low-cost decision to implement well, not just a good idea in the abstract.

Firebase Auth also stores the canonical phone number itself (Firestore only ever holds a hash — `DATABASE.md` §3.1), because Auth is purpose-built and audited for storing identity credentials, whereas replicating that into our own document store would be unnecessary duplication of sensitive data, contrary to data-minimization (`VALUES.md`).

### 2.3 Cloud Functions (Gen 2)

All server-side logic: callable API endpoints, Firestore triggers, scheduled jobs, and the Stripe webhook handler. Organization and the callable-vs-trigger decision rule: `ARCHITECTURE.md` §5; full endpoint contracts: `API_SPEC.md`. We standardize on **Gen 2** functions (built on Cloud Run under the hood) over Gen 1 for higher per-instance concurrency, longer maximum execution time (relevant for any batch/backfill-style admin functions), and more granular CPU/memory tuning per function — Gen 1 offers no advantage for us and is only relevant for legacy projects predating Gen 2's general availability.

### 2.4 Cloud Messaging (FCM) — push notification strategy

Push is a first-class engagement mechanism for a product whose value depends on people actually showing up. This section is the single source of truth for every notification trigger in the product — `PRD.md`, `SECURITY.md`, and `SCREEN_SPECIFICATIONS.md` each describe individual triggers in the context of the requirement or screen that needs them (e.g., `PRD.md` FR-T8's invite push, FR-T24's payment reminders, FR-T16's waitlist promotion, `SECURITY.md`'s duress-signal alert, Screen 35's Notification Center), but this document is where those scattered mentions are reconciled into one consistent category taxonomy, timing table, and mute-control policy, closing a gap where three documents previously implied three different, non-matching category lists (a bare 3-category split here, a 5-key example map in `DATABASE.md` §3.1, and a 4-group filter set in `SCREEN_SPECIFICATIONS.md` Screen 35's Notification Center). The canonical category keys below are the same keys `DATABASE.md` §3.1's `notificationPrefs.categories` map actually stores, and each maps onto exactly one of Notification Center's filter groups (`All / Tables / Crews / Payments / Safety`), so the preference a user sets, the field that persists it, and the log the user reads are all one system, not three.

Every trigger below is timed off the scheduled-function infrastructure described in `ARCHITECTURE.md` §5.3 (for anything not fired synchronously off a callable's own success path) and is independently Remote-Config-tunable in its non-time-critical cadences, per the category-cadence-threshold mechanism in §2.7.

**`rsvp_updates`** (Notification Center group: Tables) — every logistics push tied to a commitment the user already made or was invited into. Opt-out only at this coarse category level, never per-Table or per-message, since suppressing any of these undermines the "people actually show up" value proposition:
- Invite received (`PRD.md` FR-T8) — sent immediately (within the ≤10s p95 delivery target, `PRD.md` NFR-4) when a user is invited to a Table or a Table they're invited to changes state before they've acted on it.
- RSVP reminders — sent at T-24h and T-2h before a Table's `startTime` to every `confirmed` attendee, and a lighter T-24h nudge to `waitlisted` attendees.
- Table-day-of nudge — a same-day T-1h message with logistics (address, host contact surface, a map deep link), distinct from the reminder above but sharing the same non-suppressible treatment, since it is framed to users as "notifications about Tables you've joined," not general engagement.
- Venue relocated (`PRD.md` FR-T9a) / Table cancelled (`cancelTable`'s notification fan-out, `API_SPEC.md` §3.1) — sent immediately to every confirmed/waitlisted/requested RSVP holder. FR-T9a is explicit that this must be "an immediate push notification... not a passive chat message easily missed," which is why it sits in this non-suppressible category rather than the mutable `chat_messages` one.
- Table viability warning (host-only, `PRD.md` FR-T14a) — sent immediately when a Confirmed Table's attendee count drops below the 2-confirmed-attendee floor inside the pre-start window.

**`waitlist_promotion`** (Notification Center group: Tables) — its own key, distinct from `rsvp_updates`, because of its unusually tight timing: promotion happens within 15 minutes of a seat opening, with only a 30-minute accept window before the offer passes to the next person (`PRD.md` FR-T16), so the push fires the instant promotion occurs, never batched or deferred.

**`chat_messages`** (Notification Center group: Tables/Crews depending on chat source) — Table Chat and Crew Chat message notifications. This category was previously unspecified in this document despite being a real, screen-documented push trigger (`SCREEN_SPECIFICATIONS.md` Screens 15 and 25 both list a chat-message push as an entry point) — the gap being closed here is cadence: a naive per-message push would flood a recipient during an active back-and-forth, so sends to a given backgrounded recipient are debounced to at most 1 push per Table/Crew per rolling 2-minute window regardless of message volume in that window, with the notification body summarizing the count ("3 new messages from your Dinner Table") when more than one arrived in the debounce window. This 2-minute window is Remote-Config-tunable, not hardcoded.

**`crew_recurrence_nudges`** (Notification Center group: Crews) — growth/engagement nudges, explicitly opt-out at the category level since (unlike the categories above) these aren't tied to a commitment already made:
- Crew re-engagement prompt — sent by a scheduled function when a Crew has had no upcoming Table scheduled for longer than a Remote-Config-tunable threshold (default a few weeks), targeted at Crew admins first, falling back to all members after a further delay if no admin acts.
- Crew Table scheduled — sent immediately when a recurring-schedule sweep or a manual schedule creates a new occurrence (`crew_table_scheduled`, §2.9).

**`billing`** (Notification Center group: Payments) — every payment-adjacent push:
- Split request received — sent immediately when `createSplitRequest` creates a PaymentIntent for a given attendee.
- Payment reminders — exactly two, at 48 hours and 6 hours before a request's 7-day expiry (`PRD.md` FR-T24) — a hard cap, not a Remote-Config-tunable-upward default, since FR-T24's "no more, to avoid nagging" is a values commitment, not a starting point.
- Payment failed / retry prompt — sent on the `stripeWebhook`'s `payment_intent.payment_failed` event (`API_SPEC.md` §3.6).
- Dispute status update — sent when a billing dispute moves to Under Review or is Resolved/Refunded (`PRD.md` FR-T25a).
- Subscription renewal reminder — sent 3 days before a TableCrew+ **annual**-plan renewal only; monthly renewals get no separate TableCrew push, since the platform billing provider's (App Store/Play Billing) own renewal-receipt notification already covers the shorter cycle, and a second in-app reminder every 30 days for a small monthly charge would be exactly the kind of low-value, nagging notification `VALUES.md` warns against. This is a reasoned decision closing a real gap — no subscription-notification cadence existed in any prior document.
- Subscription payment failed — sent immediately on the billing provider's failed-renewal callback, since an unnoticed failed renewal silently downgrades a paying user's benefits without their knowledge.

**`discover_matches`** (Notification Center group: Tables) — a new high-quality Discover match surfaced via `getMatches`, capped at no more than 1 per day per user (Remote-Config-tunable) so it cannot become an infinite-feed-style engagement pressure notification, consistent with `PRD.md` FR-D4's explicit rejection of engagement-optimized Discover mechanics. Opt-out at the category level.

**Safety — no mute key, by design.** Report status updates, Tier 2 verification results, and duress-signal confirmations are Trust & Safety notifications. Unlike every category above, they have **no corresponding key in `DATABASE.md` §3.1's `notificationPrefs.categories` map at all** — this is the actual structural mechanism behind the rule stated in `SCREEN_SPECIFICATIONS.md` Screen 35 ("a user cannot fully mute Safety-category notifications... at least one channel must remain active"): there is no toggle to turn off in the first place, so the constraint can't be silently defeated by a future settings-screen refactor that just adds one more switch to a list. The duress-signal confirmation specifically is also always delivered synchronously in-app (Screen 14's Loading States), not solely relied upon as a push, precisely because push delivery cannot be guaranteed within a duress-relevant time window.

**Quiet hours and timezone handling.** Only the two engagement-nudge categories that carry no time-bound user commitment — `crew_recurrence_nudges` and `discover_matches` — respect a device-local quiet-hours window (default 9pm–8am in the recipient's **current device timezone**, not the sender's or the relevant Table's timezone, since a growth nudge has no reason to override a user's sleep in whatever timezone they're actually in right now). A send attempted inside quiet hours is held and re-attempted at the window's end by the same scheduled-function infrastructure that generates the nudge (`ARCHITECTURE.md` §5.3), never silently dropped. Every other category — `rsvp_updates`, `waitlist_promotion`, `chat_messages`, `billing`, `discover_matches`'s own already-capped-to-1/day send, and all Safety notifications — is explicitly exempt from quiet-hours deferral, since a delayed T-2h reminder, a delayed cancellation notice, or a delayed payment-failure alert has a real-world consequence that outweighs a sleep interruption; this exemption list is deliberately the same list of categories marked non-suppressible above, for the same underlying reason. This quiet-hours behavior was previously unspecified in any document; it is a reasoned default, not an inherited product decision, and is flagged here as such.

**Retry and delivery-failure handling.** Two failure modes are distinguished. (1) **Token-level failure** — FCM reports a specific device token as invalid/unregistered — is handled by pruning that token from the user's `fcmTokens` array (unchanged from prior behavior, below). (2) **Send-level failure** — the Cloud Function's call into the FCM API itself errors (rate limit, transient FCM outage) — is retried up to 3 times with exponential backoff before being logged as a delivery failure in Cloud Logging/Error Reporting (§2.8) rather than silently dropped; this closes a previously-unspecified gap where no document stated what happens when a push send errors out server-side, as distinct from the already-covered case of a bad token. Message time-to-live (TTL) is also category-dependent: time-critical categories (`rsvp_updates`, `waitlist_promotion`, `billing`'s payment reminders) set an explicit short FCM TTL (e.g., 1 hour past the relevant deadline) so a reminder for a Table or payment deadline that has already passed is never delivered late looking like a fresh one; non-time-critical categories (`crew_recurrence_nudges`, `discover_matches`) use FCM's default TTL (4 weeks), since a stale re-engagement nudge arriving a day late is harmless.

**Delivery mechanics:** FCM tokens are stored per-device on the user's `fcmTokens` array (`DATABASE.md` §3.1), refreshed on token-rotation events and pruned when FCM reports a token as invalid/unregistered (handled in the send-path error handling of the relevant Cloud Function, so stale tokens don't silently accumulate). We use FCM's data-message + notification-message combination so the Flutter app can render a locale-appropriate, deep-linkable notification (via `go_router`, `ARCHITECTURE.md` §4.3) rather than relying solely on the OS-rendered default.

### 2.5 Cloud Storage — profile/Table photos with moderation hooks

User-uploaded media (profile photos, Table cover photos) is uploaded directly from the Flutter client to a Cloud Storage bucket using a security-rules-governed path convention (`users/{uid}/profile/*`, `tables/{tableId}/photos/*`) that mirrors Firestore's rules philosophy — a user may only write to their own profile path, and only a Table's host may write to that Table's photo path, with Firestore's `photoUrl`/`photoUrls` fields updated only after a successful upload.

**Moderation hooks:** every upload triggers a Cloud Storage-triggered Cloud Function that runs the image through an automated content-moderation check (an image-safety classification API call) before the corresponding Firestore document field (`users/{uid}.photoUrl`, `tables/{tableId}` photo fields) is allowed to reference it — the trigger writes the moderation verdict to a short-lived companion document, and the *client-visible* field is only populated by the trigger itself (Admin SDK, bypassing rules) once the verdict is clean, never written directly by the uploading client. A flagged image is quarantined (left un-referenced, original blocked from ever surfacing) and generates a Trust & Safety review task, consistent with `DATABASE.md` §3.6's Reports model — a moderation flag on media is treated as its own report-like signal rather than a silent client-side rejection, so repeat-offense patterns are visible to Trust & Safety over time.

**Firebase Extension used:** we install the official **Resize Images** Extension on the photo buckets, configured to generate a small set of standard responsive sizes (thumbnail, card, full) on upload — this avoids hand-rolling a resize Cloud Function for a well-solved, first-party-maintained problem, and keeps mobile bandwidth/rendering cost down across Discover's list-heavy UI, which is exactly the kind of "list of photos rendered small and often" workload responsive image sizing is for.

### 2.6 App Check — bot/abuse prevention

App Check is enforced on every Cloud Function callable (`API_SPEC.md` §2) and on direct Firestore/Storage access from the client, using **Play Integrity** on Android and **App Attest** (with DeviceCheck as the fallback for older OS versions) on iOS. This is our primary structural defense against the API surface being called by anything other than a genuine, unmodified instance of the app — e.g., a scripted client attempting to farm Table-creation spam, mass-request seats, or scrape Discover data directly against our backend rather than through the app. We do not treat App Check as sufficient on its own (a determined attacker can still attempt to defeat device attestation), which is why it's explicitly layered under the per-endpoint rate limiting and reasoning-through checks described in `API_SPEC.md` §5, not a substitute for them.

### 2.7 Remote Config — feature flags and staged rollouts

Remote Config drives every tunable we don't want to gate behind an app store release: per-notification-category cadence thresholds (§2.4), Crew capacity caps (`API_SPEC.md` §Crews), auto-suppression report thresholds (`API_SPEC.md` §Trust & Safety), and the `minimumSupportedVersion` gate used for API deprecation (`API_SPEC.md` §4). It is also our feature-flagging mechanism for staged rollouts of new features — a new capability ships code-complete but flag-off, then is enabled for an increasing percentage of users (via Remote Config's built-in percentage-rollout/condition targeting) so we can catch regressions on a small cohort before full exposure. The staged-rollout *process* (who approves a rollout stage, how fast stages advance, rollback procedure) is documented operationally in `DEPLOYMENT.md`; this document is scoped to *what Remote Config is used for*, not the release process around it.

### 2.8 Crashlytics

Standard crash/non-fatal-error reporting wired into the Flutter client (via `firebase_crashlytics`, with a `FlutterError.onError`/`PlatformDispatcher.onError` hook capturing uncaught Dart errors) and, separately, into Cloud Functions (structured error logging that surfaces in Cloud Logging/Error Reporting, which we treat as "Crashlytics for the backend" for on-call purposes). Crashlytics is the first signal in our incident-response loop (`DEPLOYMENT.md` runbooks) — any spike in a specific crash signature during a staged rollout (§2.7) is a rollback trigger.

### 2.9 Firebase Analytics + BigQuery export, and Mixpanel's separate role

Every product-relevant event is logged via Firebase Analytics with a consistent event-naming and parameter schema, so that every metric in `SUCCESS_METRICS.md` is computable from a specific, named event rather than inferred from a heuristic or a proxy signal — `SUCCESS_METRICS.md` §5 states this as a requirement ("traceable to a specific, named event"), and this section is where that naming convention actually lives, since a metrics document that says "measured via event X" is not meaningful if no document anywhere commits to what event X is actually called.

**Mixpanel (added 2026-08) is a deliberate second analytics tool, not accidental duplication of Firebase Analytics** — it has a narrower, specific job: fast, no-SQL-required funnel and cohort exploration for growth/marketing (the audience for `MARKETING.md`'s channel and conversion analysis, and the acquisition-funnel questions in `INVESTOR_OVERVIEW.md`'s unit-economics section), who need to self-serve ad hoc funnel breakdowns without writing BigQuery SQL or waiting on an engineer. Firebase Analytics + BigQuery export remains the system of record for every metric in `SUCCESS_METRICS.md` and every number reported externally (to investors or in this documentation) — Mixpanel is a growth-team convenience layer on top of a subset of the same event stream, not a second source of truth. To avoid the two tools drifting into different definitions of the same metric (a classic failure mode of running two analytics tools), Mixpanel is fed from the same canonical event names defined in this section via a single Cloud Functions fan-out (one event write, two destinations), not a separately-instrumented client SDK that could silently diverge in what it counts as, say, a "Table attended" event. If this dual-tool cost and maintenance overhead isn't earning its keep by the time Phase 2's scale is reached, consolidating back onto BigQuery (with a lightweight internal dashboard replacing Mixpanel's self-serve UI) is the natural simplification — tracked as an open item in `TASKS.md`.

It exists so that "we track no-show rate" (`SUCCESS_METRICS.md` §3.5/§4) resolves to a concrete, unambiguous event (`table_no_show`) rather than an implied one, closing the gap between a metrics document that names outcomes and an analytics implementation that would otherwise have to guess at event names independently. Screen-level UI-instrumentation events not listed here (e.g., `app_launched`, `onboarding_step_completed`, `profile_viewed`, `crews_list_viewed`) are intentionally excluded from this canonical minimum set — they follow the same naming convention and are fully specified in `SCREEN_SPECIFICATIONS.md` itself, but they don't feed a named `SUCCESS_METRICS.md` KPI, which is the bar for inclusion here. We enable **BigQuery export** for both Analytics events and Firestore (via the Firestore-to-BigQuery Extension, streaming document changes into a mirrored BigQuery dataset) so that:

- Product/growth analysis that needs joins across event streams and current-state data (e.g., "conversion rate from Discover search to confirmed attendance, segmented by verification tier and city") can be done in BigQuery's SQL interface rather than by hand-aggregating Firestore reads, which Firestore's join-less model makes painful (`DATABASE.md` §2).
- This BigQuery export is explicitly the mechanism referenced in `ARCHITECTURE.md` §6 as our current answer to "complex relational analytics" — it is sufficient for offline/dashboard analysis today, and its insufficiency for *interactive, operational* (not just internal-dashboard) use cases is the specific, named trigger for eventually introducing a dedicated Postgres reporting service.

### 2.10 Stripe (payments, not a Firebase product but integrated at this layer)

Used for split-bill payment collection (`API_SPEC.md` §Payments) via Stripe Connect (so funds can flow toward a host or venue payout where applicable). Stripe secrets (API keys, webhook signing secret) are stored in **Google Secret Manager**, accessed by Cloud Functions at runtime via Secret Manager bindings — never in Remote Config (which is client-readable) and never in source control.

### 2.11 Typesense (Discover search index)

Not a Firebase product, but its sync is Firebase-Functions-driven; full rationale and sync architecture: `ARCHITECTURE.md` §5.5. Its API keys (admin key for the sync Functions, scoped search-only key for the client) are likewise stored in Secret Manager / delivered to the client via a low-sensitivity Remote Config value respectively, matching the sensitivity of each key. Typesense's rebuildability from Firestore (§Section 8 of `ARCHITECTURE.md`) is a data-loss/DR answer, not an availability answer — a Typesense Cloud service outage (the service being unreachable, not the data being wrong) is handled separately as a client-side circuit-breaker fallback to a degraded Firestore-native query path (`ARCHITECTURE.md` §5.5, `API_SPEC.md` `searchTables`), which is the piece of this puzzle that used to be undocumented and is now an explicit, tested degradation path rather than an implicit "Discover just goes down" gap.

## 3. Environment Strategy

We run **three fully separate Firebase projects** — `tablecrew-dev`, `tablecrew-staging`, `tablecrew-prod` — rather than a single project with environment-prefixed collections, for reasons that matter specifically because of how deeply Firebase's products are project-scoped:

- **Security rules, Cloud Functions, and Remote Config are deployed per-project**, so a bug in a rules change or a Function deploy during active development can never affect production data even transiently — there is no shared mutable state between environments to accidentally cross-contaminate, which a single-project-with-prefixes approach cannot guarantee (a misconfigured query or rule could easily touch the wrong prefix).
- **Firebase Auth users, App Check attestation, and Analytics data are inherently project-scoped**, so separate projects give us clean, realistic test identities and event streams in dev/staging without polluting production analytics or user-facing Auth records with test accounts.
- **Cost isolation and quota isolation:** a load test or a runaway Function loop in staging cannot exhaust production's quotas or show up on production's bill, which matters for keeping cost anomalies (§4) attributable and actionable.
- `tablecrew-dev` is used for local development (engineers point their local Flutter run and Functions emulator suite at it, or use the Firebase Local Emulator Suite entirely offline for most iteration) and CI test runs; `tablecrew-staging` mirrors production configuration and is used for pre-release validation and staged-rollout rehearsal; `tablecrew-prod` serves real users. Promotion between environments (config parity checks, deploy sequencing) is a `CI_CD.md`-owned process; this document only establishes that the three-project topology is the environment boundary.
- **Data residency note:** as described in `ARCHITECTURE.md` §7, additional *production* project instances (not dev/staging) may be added per region/regulatory zone as we expand internationally — that's an extension of this same three-tier-per-region pattern, not a departure from it.

**Client application identifiers.** The Flutter app registers two separate Firebase client apps per project — Android `applicationId` `com.tablecrew.android`, iOS bundle ID `com.tablecrew.ios` — registered identically (same two identifiers) across all three projects, differing only in the generated `google-services.json`/`GoogleService-Info.plist` credentials per environment. We deliberately use distinct per-platform identifiers rather than a single shared identifier reused across both platform manifests (e.g. `com.tablecrew.app` on both): it costs one extra Firebase app registration per project (2 apps × 3 projects instead of a notionally-shared 1 per project) but keeps each platform's Firebase Android/iOS app record, crash-reporting stream, and future Play Console/App Store Connect listing cleanly separable if the two platforms ever need independent config (e.g. a platform-specific Remote Config rollout or a platform-only feature flag) without having to retroactively split a shared identifier later. This was an open gap through F0 — `flutter create`'s default scaffold ships the placeholder `com.example.tablecrew`, and no prior document had committed to a real identifier — closed when the `android/`/`ios/` platform directories were actually generated (`CHANGELOG.md`, F0 follow-up).

## 4. Cost Management

**Primary cost drivers we actively monitor**, in expected order of magnitude as we scale:

1. **Firestore reads** — the single largest likely line item, driven overwhelmingly by Discover-adjacent and list-rendering screens. This is precisely why denormalization (`DATABASE.md` §4) is treated as a cost decision as much as a latency one: every avoided per-item join-equivalent read is a direct cost saving at scale, not just a UX improvement.
2. **Cloud Functions invocations and compute time**, particularly any function in the hot path of a frequently-hit callable (`requestSeat`) or a frequently-firing trigger (Table field changes syncing to Typesense). We watch for triggers that fire more often than their side effect actually requires (e.g., a trigger that fires on *any* Table field change but only needs to act on a subset of fields) and add field-diff guards to skip unnecessary work.
3. **Cloud Storage egress and Resize Images Extension invocations**, scaling with photo upload volume and, more so, with how many responsive sizes we generate per upload and how often photos are viewed from regions far from the bucket's location (mitigated by Cloud Storage's CDN-backed download URLs).
4. **Typesense Cloud cluster sizing** (capacity-based, `ARCHITECTURE.md` §5.5) — reviewed against actual query volume and index size at each growth milestone, since over-provisioned cluster tier is a fixed cost independent of whether we're using it.
5. **BigQuery storage and query cost** for the Analytics/Firestore export — managed primarily by partitioning exported tables by date and setting sane default query cost limits for internal dashboard tooling, so an ad hoc exploratory query can't produce a surprise bill.

**Process:** we review Firebase/GCP billing against a per-product-line breakdown monthly, and treat any month-over-month increase disproportionate to user/Table-volume growth as an investigation trigger (usually traceable to a missing composite index causing full-collection scans, an overly chatty trigger, or a client screen re-subscribing to a listener more often than necessary). This monthly review is also the concrete mechanism behind `ARCHITECTURE.md` §6 migration trigger (4) — "cost exceeds the fully-loaded alternative" is evaluated here, quarterly at minimum, not asserted abstractly.
