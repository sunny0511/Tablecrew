# Deployment & Release Process

This document describes how a change goes from a merged commit on `main` to running on a user's phone, for both the Cloud Functions backend and the Flutter mobile client — two very different processes with very different constraints, chiefly because one is gated by app store review and the other isn't.

## Environment Strategy

We run three fully separate Firebase projects — **dev**, **staging**, and **prod** — detailed in `FIREBASE.md`. This is not just a Firestore-data separation; each is a genuinely distinct Firebase project with its own Auth users, Cloud Functions deployment, Storage bucket, and API keys. The reason is simple and non-negotiable given `VALUES.md`'s "respect data like it's someone's actual life": there is no code path, feature flag, or configuration error under which a bug in a dev or staging build could write to, or read, real user data, because dev and staging point at infrastructure that structurally cannot contain real user data. Local development and CI both run against the **dev** project (or, for hermetic/automated tests, the Firebase Emulator Suite, per `TESTING.md`). **Staging** is where release candidates and beta builds run — seeded with synthetic data (per `TESTING.md`'s seed script), configured as close to prod as possible (same Cloud Functions, same Firestore rules, same Remote Config structure), so that a release candidate tested on staging is testing the real thing, not an approximation of it. **Prod** serves real users and is the only project with real user PII, real Stripe live-mode keys, and real Discover verification data.

Promotion between environments is one-directional and always forward: dev → staging → prod. Cloud Functions and Firestore rules are deployed to each environment independently (via the CI/CD pipeline described in `CI_CD.md`), never hand-pushed from a developer's machine to staging or prod.

As TableCrew expands into jurisdictions with data-localization expectations (per `LEGAL.md` §7 and `FIREBASE.md`'s regional-project guidance), "prod" may become multiple regional prod projects rather than a single global one — a live consideration for future India/Brazil expansion given DPDP and LGPD. This expansion doesn't rely on an engineer manually remembering which regional project serves which market: the CI/CD pipeline (`CI_CD.md`'s Deploy-Time Region and Jurisdiction Assertion) mechanically verifies at deploy time that a build targets the correct regional project for its intended market, failing the deploy outright on a mismatch rather than proceeding on trust.

## Release Cadence

**Mobile app (Flutter client): biweekly.** We recommend a two-week release train over both weekly and monthly cadences. Weekly is too fast given app store review latency — Apple's review typically takes anywhere from a few hours to 1-2 days for an established app in good standing (with occasional multi-day outliers), and Google Play review is usually faster but not instant either; a weekly cadence leaves little to no margin if a submission gets rejected or takes longer than expected, and it means release management overhead (branch cuts, release notes, QA passes) consumes a disproportionate share of engineering time for a small team. Monthly is too slow given how fast a startup needs to iterate on a not-yet-product-market-fit product — a month is a long time to wait to get a fix or a tested hypothesis in front of users. Biweekly splits the difference: enough cadence to keep iteration fast, enough buffer to absorb a review hiccup or a beta-testing delay without needing to break the train.

**Cloud Functions and Firestore rules: continuous deployment.** Backend changes deploy to prod automatically on every merge to `main` that passes the full CI pipeline (see `CI_CD.md`), typically multiple times a day. This asymmetry — continuous backend deploys, biweekly client releases — is the direct consequence of app store review being the client's bottleneck and nothing else being the backend's bottleneck. It also means backend changes must always be backward-compatible with the currently-live client version(s) in the field, since a Cloud Function deployed today needs to correctly serve a client build that could be up to several weeks old (biweekly cadence plus users who delay updating) until users update. API/schema changes to Cloud Functions follow an additive-first, deprecate-later pattern for this reason — see `API_SPEC.md` for the specific versioning approach.

## Internal Demo Builds at Milestone Boundaries

Separate from the biweekly release cadence above — which governs shipping to real users — every Foundation engineering milestone's close now also produces and distributes a build so the founder and internal team can see and click through real progress, not just read a written milestone summary. This is the same **Firebase App Distribution** mechanism `docs/CI_CD.md`'s "Platform Choice" section already names and stage 6 of the pipeline already designs for, applied deliberately at milestone boundaries rather than waiting for that CI stage to be fully built and automated.

**Current state, disclosed honestly:** neither Fastlane lanes nor a configured Firebase App Distribution tester group exist in this repository yet — `docs/CI_CD.md`'s stage 6 describes the intended automated end state, not something that has actually run. Until that automation exists, producing a milestone demo build is a **manual step the founder runs locally**, since it needs the real Flutter/Android toolchain no agent working in this repo currently has verified access to (the same disclosed gap `TASKS.md`'s Milestone F3 closeout carries forward: `flutter build` has never been executed in CI or any sandboxed environment, only on the founder's machine). The near-term process:

1. **Android (realistic today):** `flutter build apk --debug` from `app/` produces an installable, unsigned debug APK — no Apple/Google developer account or signing infrastructure required. Distribute it via `firebase appdistribution:distribute build/app/outputs/flutter-apk/app-debug.apk --app <ANDROID_APP_ID> --groups internal-testers` (Firebase CLI), after registering an `internal-testers` tester group in the `tablecrew-dev` project's App Distribution console if one doesn't already exist. This works today with zero new infrastructure.
2. **iOS (blocked):** a demo build for iOS needs either TestFlight or ad-hoc distribution, both of which require an enrolled Apple Developer Program account and real signing certificates/provisioning profiles — neither exists yet in this project (the iOS toolchain itself has been a disclosed, unverified gap since Milestone F0). This is a genuinely new, tracked open item (`TASKS.md`), not silently skipped: Apple Developer Program enrollment should happen before Fastlane's `match`-based signing (`docs/CI_CD.md`) can be wired up at all, for demo builds or real releases alike.

**Real gap found on the first actual attempt (2026-08):** `app/android/` and `app/ios/` — the native project wrappers `flutter build` needs — do not exist anywhere in this repository's history, a previously-undetected Milestone F0 scaffold gap (F0's Flutter scaffold was hand-authored before any real Flutter SDK was available in this project's tooling, and hand-authoring never generated these machine-specific, `flutter create`-generated directories). Fix is `flutter create --platforms=android,ios .` from `app/`, safe on an existing project. See `TASKS.md`'s Milestone F4 demo-build update for the full diagnosis and the corrected, ordered command sequence (including Android SDK installation and `flutterfire configure`, since the Flutter client has never actually been wired to Firebase yet either).

**What a milestone demo build should and shouldn't be read as:** it reflects the actual state of `app/` at that milestone's close — for a backend-only milestone (e.g., F4, which shipped Cloud Functions callables with no client-visible UI), the demo build will look and behave identically to the previous milestone's, which is expected and worth stating plainly in the distribution notes rather than leaving testers to wonder if something's broken. It is not a release candidate, is not staged-rollout-percentage-controlled, and carries no App Store/Play Store review — it exists purely for internal visibility into engineering progress between the (much less frequent) real beta/release builds described elsewhere in this document.

## Staged Rollout

We never flip a new client release or a new feature to 100% of users on day one. Two complementary mechanisms handle this:

**App-store staged/percentage rollout.** Both the App Store (via App Store Connect's phased release, which ramps over roughly a week in increasing daily percentage steps) and Google Play (via the Play Console's staged rollout percentage, which we control more granularly) are used for every release. We start new releases at a small percentage (typically 10-20% on Android, where we have finer control; iOS's phased release follows Apple's fixed schedule but can be paused) and monitor Crashlytics crash-free-user rate and key funnel metrics (per `SUCCESS_METRICS.md`) before manually advancing or pausing. A release is only fully ramped to 100% after at least 24-48 hours at a partial percentage with no crash-rate regression or safety-relevant incident.

**Remote Config for feature-level rollout**, independent of the binary rollout above. Because a feature flag check happens at runtime against Remote Config rather than being compiled into the binary, we can ramp a specific feature's exposure (e.g., a new Discover matching algorithm, a redesigned RSVP flow) up or down within an already-shipped binary, targeting by percentage, region, or user segment, without waiting on app store review at all. This is the mechanism that makes "bias toward shipping, with a rollback plan" (per `VALUES.md`) practical for client-side features specifically — the binary ships broadly and conservatively (behind flags, defaulted off or to old behavior), and the actual feature exposure ramps independently and reversibly via Remote Config.

## Feature Flag Lifecycle

Every feature flag follows the same lifecycle, and every flag has a named owner (the engineer who introduced it) responsible for driving it through to removal — a flag is not "done" when it merges, it's done when it's fully ramped and removed.

1. **Flag created, defaulted off.** The feature merges to `main` behind a Remote Config flag, off by default in prod. It may be on in dev/staging for continued testing.
2. **Internal/beta ramp.** Flag turned on for the internal team and beta testers (per `TESTING.md`) to get real usage before wider exposure.
3. **Percentage ramp in production.** Flag ramps in prod in deliberate steps (e.g., 5% → 25% → 50% → 100%), with a monitoring pause at each step to check crash rates, error rates, and relevant product metrics before advancing. Ramp speed depends on risk: a cosmetic UI change might ramp over a day or two; anything touching Discover, verification, or payments per `SECURITY.md` ramps more slowly and gets explicit trust & safety sign-off before advancing past internal beta.
4. **Fully on.** Flag reaches 100% and stays there for a stabilization period (at least one full release cycle) to confirm no delayed issues emerge.
5. **Flag removed.** Once stable at 100% for a full cycle, the flag owner removes the flag and all conditional branches referencing it from the codebase in a dedicated cleanup PR. Flags are not allowed to linger indefinitely — an accumulation of dead, always-on flags is tech debt that makes the codebase harder to reason about and is explicitly called out in sprint planning if it's piling up. We track live flags and their owners in a simple registry (a section of `TASKS.md` or a dedicated tracking doc) so a flag never becomes orphaned with no one accountable for finishing its lifecycle.

## Rollback Procedures

**Cloud Functions rollback** is fast and close to complete: because Cloud Functions deploys are versioned and the previous deployment artifact is retained, rolling back means redeploying the last-known-good version via the CI/CD pipeline (a one-command re-trigger of the deploy job pointed at the previous `main` commit SHA, see `CI_CD.md`), typically restoring service within minutes. Firestore rules rollback works the same way — the previous `firestore.rules` file is redeployed. Because backend rollback is fast and low-risk, we default to "roll back first, investigate root cause after" for any prod incident traced to a backend deploy, rather than trying to hotfix forward under pressure.

**Mobile client rollback is fundamentally different and more limited**, and every engineer needs to internalize this asymmetry: once a binary is in a user's hands, we cannot make their installed app disappear or instantly revert to older code the way we can redeploy a function. Our actual levers are: (1) **halt or reduce the staged rollout percentage** in App Store Connect / Play Console immediately, which stops the bad build from reaching more users but does nothing for users who already updated; (2) **flip the relevant Remote Config feature flag off**, which is why the flag lifecycle above matters so much — if the risky new behavior was properly flagged, "rollback" for affected users is a Remote Config change taking effect the next time their app fetches config (typically within the hour, and we can force a more immediate fetch on app foreground for critical kill-switches), not a new binary; (3) for a client-side bug with no flag protecting it (which is exactly the failure mode we try to prevent by requiring flags on all client-visible changes per `ENGINEERING_GUIDELINES.md`), the only real fix is an expedited new release through the hotfix process below — there is no faster path. This is precisely why Remote Config kill-switches for any client feature with meaningful risk (anything touching Discover, payments, or verification, in particular) are not optional polish — they're the only rollback mechanism that works at internet speed rather than app-store-review speed.

## App Store Submission

**iOS (App Store Connect)**: builds are uploaded via the CI/CD pipeline's Fastlane lane (`CI_CD.md`) after passing the full test suite and internal beta. Apple's review is typically fast for an established app with no policy violations (often same-day to a couple of days) but can take longer, and certain categories of change — anything touching account deletion, payments, or content involving user-generated media (directly relevant to TableCrew's profiles and Table descriptions) — tend to draw closer scrutiny and occasional manual review escalation. We build in review-time buffer to the release calendar rather than assuming best-case turnaround, and we keep release notes and App Review notes (a private field explaining anything non-obvious about the build, e.g., "Discover matching requires ID verification to test — see attached test account") current so a reviewer isn't left guessing.

**Android (Google Play Console)**: review is generally faster than iOS and less variable, though Google has escalated scrutiny in recent years for apps handling sensitive categories (again, relevant to us given Discover's people-matching nature) and for permissions usage — we keep our Play Data Safety form and permissions declarations in lockstep with what the app actually collects, cross-referenced against `SECURITY.md`'s minimal-collection principle, since a mismatch here is a common source of review delay or suspension.

Both submissions are automated through the pipeline described in `CI_CD.md` — no engineer manually drags a build through App Store Connect or the Play Console UI under normal circumstances; Fastlane handles build, signing, metadata, and submission.

## Hotfix Process

A hotfix is warranted when a SEV1 or SEV2-class issue (per `SECURITY.md`'s severity classification) is discovered in a production client release and cannot be mitigated by a Remote Config flag flip alone — meaning a new binary is genuinely required. The process deliberately bypasses the normal biweekly train:

1. Branch directly off the currently-live release tag on `main` (not off whatever half-finished work is currently on `main` for the next scheduled release), containing only the minimal fix.
2. Full CI pipeline runs as normal (`CI_CD.md`) — a hotfix does not skip tests, since shipping a second bug while fixing the first is a worse outcome than a short delay.
3. Abbreviated but real beta: internal team verification is mandatory and immediate; external beta is shortened to hours rather than days for a genuinely urgent SEV1, but is not skipped outright unless the fix is trivial and low-risk (e.g., a one-line config value) — "we were in a hurry" is not an acceptable explanation for a hotfix that introduces a new incident.
4. Submitted to both stores with an App Review note flagging it as an expedited fix; both Apple and Google offer expedited review request mechanisms for genuine critical bugs (including safety-relevant ones), which we use for true SEV1s rather than saving as a reflex for every hotfix.
5. Staged rollout still applies even to hotfixes, at a faster ramp than normal (given the urgency) but not skipped entirely — a hotfix that itself has a bug and reaches 100% of users instantly is strictly worse than the incident it was meant to fix.
6. Every hotfix gets the same blameless postmortem treatment as the incident it addresses, per `SECURITY.md`.
