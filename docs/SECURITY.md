# Security & Trust and Safety

TableCrew's entire premise involves putting real people in real rooms with each other, and Discover — our surface for meeting people outside your existing network — does this with strangers. That makes this document, not `ARCHITECTURE.md`, the most consequential engineering doc in the repo for anyone touching that surface. Per `VALUES.md`: "Safety is a feature, not a department." Every requirement below is a launch gate, not a backlog item to get to eventually. Closed/Crew-only Tables (where attendees already know each other, per `PRODUCT.md`) carry lighter requirements than Open/Discover Tables throughout this document — we call out the distinction explicitly wherever it matters.

## Identity Verification Tiers

TableCrew uses a two-tier verification model, escalating with the risk of the surface being accessed.

**Tier 1 — Phone verification (baseline, all users).** Every account requires a verified phone number via Firebase Auth's phone sign-in flow (SMS OTP) before any use of the app. This is non-negotiable and gates account creation entirely, not just certain features. Phone verification alone is weak — SIM farms and disposable numbers exist — but it's the floor that makes basic abuse (instant mass account creation, easy ban evasion) meaningfully harder and costlier, and it gives us a stable identifier for account-level actions like rate limiting and no-show tracking, described below.

**Tier 2 — ID + selfie liveness verification (required to host or join any Open/Discover Table).** Before a user can create an Open Table, RSVP to one, or appear in Discover search/matching at all, they must complete a stronger verification: government ID scan plus a live selfie check that confirms the person holding the phone matches the ID and is physically present (not a photo of a photo, not a static image). We recommend **Persona** over Stripe Identity for this. Both are credible, PCI-adjacent-grade identity vendors; Persona wins for TableCrew's specific needs on two counts. First, Persona's product is purpose-built for identity/trust-and-safety workflows across many document types and countries and exposes a more configurable case-management and manual-review workflow out of the box — relevant because "global-first, not US-first" (per `VALUES.md`) means we need solid non-US ID format coverage from day one, not a US-driver's-license-first product we bolt international support onto later. Second, decoupling identity verification from our payments vendor (Stripe) keeps the two integrations independently swappable and avoids a single vendor holding both our money movement and our identity data — a deliberate reduction of blast radius if either vendor relationship ever needs to change. Persona verification results and audit trail are stored server-side only (a `verificationStatus` and `verificationTier` field on the user document per `DATABASE.md`, with the actual ID images and biometric data never touching Firestore or the client — they live in Persona's vault, referenced by an opaque case ID).

**Superseded for Phase 0 — 2026-08, ADR [0007](adr/0007-manual-identity-verification-for-phase-0.md).** Everything in the paragraph above describes the vendor design this document has assumed since it was written, and it remains the intended end state — but it is **not** what Phase 0 ships. No identity vendor is in the flow. Tier 2 is performed by manual human review: the user uploads a government ID and a selfie to a Cloud Storage path no client may read, an administrator reviews them and calls an admin-only endpoint (`API_SPEC.md` §3.7), and the images are deleted the moment a decision lands. Three sentences above are therefore false as of Phase 0 and are corrected here rather than left to be discovered in the code:

1. **"The actual ID images and biometric data never touch Firestore or the client."** They now touch TableCrew's own Cloud Storage. TableCrew is the custodian of government ID images for the duration of a review, which makes it the data fiduciary for that data under the DPDP Act. The mitigations are real but bounded: no client may read the objects (not even the uploader), the images are deleted on decision, and nothing ID-derived is ever persisted to Firestore (`DATABASE.md` §3.10).
2. **"A live selfie check that confirms the person holding the phone matches the ID and is physically present (not a photo of a photo, not a static image)."** A human comparing a selfie to an ID does not establish presence. A printed photo, a screen, or a replayed video defeats it — defeating exactly those is what vendor liveness is *for*. During Phase 0 the `id_verified` badge means "a human compared a submitted ID against a submitted selfie," which is meaningfully more than phone verification and meaningfully less than this paragraph promises. User-facing copy must not claim liveness (`SCREEN_SPECIFICATIONS.md` Screen 8 is written accordingly).
3. **The Aadhaar/India coverage question this section flags as an open vendor dependency is not resolved by this change — it is deferred.** A human can read an Aadhaar card, so manual review is not *blocked* on the AUA/KUA licensing question recorded in `TASKS.md`; but neither does it deliver cryptographically-verified Aadhaar Offline e-KYC. It sidesteps the question rather than answering it, and the question returns in full the moment a vendor is contracted.

ADR 0007 records why this trade was accepted (Milestone F7 was blocked for four weeks on an unresolved vendor decision with no forcing function) and states plainly that it is a bridge, not a destination.

**Open, unconfirmed dependency — do not read the paragraph above as a settled fact for our anchor market.** TableCrew's Phase 0 anchor city is Hyderabad, India (`ROADMAP.md`), which makes Persona's specific document-format and liveness coverage for Aadhaar and other India-issued government IDs a first-day launch dependency, not a "nice to have broader than the US." This has **not** been confirmed directly with Persona as of this writing — the "global-first, not US-first" reasoning above is why we chose Persona over a US-driver's-license-first competitor, but that is a reason to prefer Persona if its coverage holds up, not itself proof that Aadhaar coverage is adequate. Per `LEGAL.md` §11 and `TASKS.md`, this is tracked as an open, Phase-0-gating item — confirm coverage with the vendor before launch, with an India-specific Aadhaar e-KYC vendor identified as the fallback if Persona's coverage proves inadequate. This document deliberately does not resolve that question here; doing so would mean guessing at a vendor capability this team cannot verify from a documentation pass alone.

**Raised urgency, 2026-08:** this was previously framed as something to resolve "before Phase 1 launch" — a real deadline, but a distant one. `docs/IMPLEMENTATION_PLAN.md`'s new Milestone F7 now builds the real Persona/Tier 2 integration during Foundation, immediately after F6's Trust & Safety infrastructure lands, not during Phase 1's engineering work. Confirming Aadhaar/India-ID coverage doesn't block *writing and testing* that integration (Persona's sandbox mode is sufficient for that), but it should move up the founder's priority list now rather than stay a background item — F7 is materially less useful to have built if this comes back unresolved right when Phase 1 launch approaches, since Persona's sandbox behavior confirming "the integration works" says nothing about whether real Aadhaar documents actually pass verification in production.

**This is identity verification, not a background check, and the distinction is legally and operationally material, not just semantic (see `LEGAL.md` §5).** Persona's ID + selfie liveness flow confirms that the person holding the phone is a real, live individual who matches the government ID they presented — it does not query criminal history, sex-offender registries, or any other background-check database, and TableCrew does not represent otherwise anywhere in-app or in marketing copy. Confusing the two is a real risk: claiming or implying a criminal background check when none is run is both a false-safety-guarantee problem (a user could reasonably over-trust a "verified" badge as more than it is) and a regulatory one — actual background checks trigger FCRA (federal) and state ban-the-box/fair-chance obligations (adverse-action notices, permissible-purpose disclosures, look-back limits) that are entirely separate from, and not satisfied by, our Persona identity relationship. Every occurrence of `verificationTier`/`idVerified` in this document, in `DATABASE.md`, and in user-facing copy (badges, onboarding, ToS) refers only to identity verification. If TableCrew builds a background-check product in the future (a reasonable Trust & Safety enhancement, tracked as an open `TASKS.md` item per `LEGAL.md` §5), it must be its own FCRA-compliant workstream — a new vendor relationship, new consent flows, and a new adverse-action process — not an extension of the existing Persona identity-verification integration, and it must not ship without dedicated legal review.

Verification status is enforced server-side in Cloud Functions and Firestore Security Rules, never trusted from client state alone — a client could be compromised or simply out of date, and gating a safety-critical permission on client-reported state is a rules bypass waiting to happen. Any callable function that creates an Open Table, RSVPs to one, or writes to the Discover-visible index checks `verificationTier == 2` server-side before proceeding.

Re-verification is required if: the account is flagged by three or more reports (see below), the account is reactivated after a suspension, or a device/behavioral signal suggests possible account takeover (new device + new location + immediate Discover activity). Verification doesn't expire on a fixed timer for now — we'll revisit this if we see evidence of verified-then-compromised accounts at scale.

**A report filed while Tier 2 verification is still in progress.** Persona's processing is asynchronous — the result can arrive after the user has backgrounded the app (`docs/SCREEN_SPECIFICATIONS.md` Screen 8) — which creates a real ordering question this document did not previously answer: a user could be reported by someone else in the window between submitting ID/selfie capture and Persona returning a result, and a naive implementation would grant `verificationTier: "id_verified"` purely because the Persona callback happened to land before a human reviewed the new report. We close this by re-checking the account's current `trustSignals`/open-report state at the moment a verification result is *about to be applied*, not only at the moment the Persona flow was initiated: if an open report was filed against the account after verification was kicked off, the grant is held for manual Trust & Safety review rather than completing automatically — the same manual-review branch already used for a report-count threshold being crossed (`API_SPEC.md` `reportUser`) or an ID/DOB mismatch (above), not a new mechanism. This closes the gap where async timing alone could let a user under active investigation reach Discover before their report is looked at.

## Age Gating and Minimum Age Enforcement

Per `LEGAL.md` §8's recommendation, TableCrew sets a single platform-wide minimum age of 18, with no lower "Crew-only" tier for minors — there is no in-app path for a self-identified under-18 user to access any part of the product, not even Closed/Crew Tables. This section specifies how that's technically enforced and states plainly where the real limitation is, rather than leaving enforcement as an unstated assumption.

**Signup-time gate (self-reported, all users).** Every signup flow requires entering a date of birth before an account is created; the client and a Cloud Function both reject a submitted date of birth that computes to under 18 at submission time — enforced server-side in the account-creation callable, not just a client-side form validator, so a modified client can't bypass it by skipping the check. This gate is trivially fakeable by a determined minor entering a false birth date, the same limitation every consumer app with a self-reported age gate has — we do not claim otherwise.

**Secondary, ID-verification-derived signal (Tier 2 only — Discover access).** Because Tier 2 (ID + selfie liveness via Persona, above) already extracts date of birth from a government-issued ID as part of the identity-verification flow, we cross-check that ID-derived date of birth against the self-reported signup date of birth before granting `verificationTier: "id_verified"`. A mismatch beyond a small tolerance (to allow for, e.g., a birthday occurring between signup and verification) blocks Tier 2 verification pending manual trust & safety review rather than silently accepting whichever age is more favorable to account creation. Practically, this means anyone who reaches Discover — the surface where an adult is introduced to a stranger in person — has had their age confirmed against a real government ID, not just a self-reported form field. **Mechanism changed for Phase 0 (2026-08, ADR 0007):** with no OCR in the flow, this cross-check is performed by the human reviewer and recorded as an explicit attestation (`dobMatchesId`, `API_SPEC.md` §3.7, `DATABASE.md` §3.10) rather than extracted automatically. The requirement is unchanged and is enforced structurally — an approve that does not carry the attestation is rejected as `invalid-argument` rather than granting the tier — but it now depends on a person actually performing the comparison, which is a weaker guarantee than a machine-extracted field and is stated as such.

**Accepted, bounded risk: Crew-only (Tier 1) access.** A user who never attempts to access Discover or host/join an Open Table is never required to complete Tier 2 ID verification (by design — requiring ID verification for Crew-only use, where attendees already know each other, would be disproportionate friction relative to the tiered-risk model above). This means a minor who enters a false birth date at signup and only ever uses Crew-only Tables with people they already know cannot be technically prevented from doing so without requiring ID verification platform-wide, which we deliberately do not do. We state this as an accepted, bounded risk rather than a solved problem: it is bounded because (a) Crew-only Tables involve only people the user already has an existing relationship with, the same lower-risk logic that governs every other tiered requirement in this document, and (b) it is the same residual risk essentially every mainstream consumer app with a self-reported age gate carries. It is not bounded to zero, and this document does not claim it is.

## Authentication: Session Lifecycle, Token Handling, and Device Compromise

Tier 1 phone verification (above) is how a user *first* proves who they are; this section is the previously-missing answer to how TableCrew keeps proving that on every subsequent request, and — a real gap this document did not address before this pass — what happens when the device that completed that proof is lost, stolen, or otherwise compromised.

**Token issuance and refresh.** Firebase Auth issues a short-lived ID token (1 hour, Firebase's standard expiry) plus a long-lived refresh token on successful phone-OTP sign-in. The `cloud_functions` client SDK attaches the current ID token to every callable automatically and transparently mints a new ID token from the refresh token before expiry, so a session persists across app opens without re-prompting for OTP — this is the mechanism behind `docs/SCREEN_SPECIFICATIONS.md` Screen 1 (Splash)'s "check auth token validity/refresh" cold-start step. Every callable function independently verifies the ID token's signature and expiry server-side before executing (`API_SPEC.md` §2, `context.auth`); an expired or tampered token is rejected with `unauthenticated` — token validity is never trusted from client-reported state, the same principle this document applies to verification tier (above) and every other safety-critical field.

**Compromised or lost device — the gap.** A phone that is lost, stolen, or left unlocked while the TableCrew app is still signed in is a real risk: whoever holds the device can act as the account owner for as long as its refresh token remains valid, independent of whether they can receive a new SMS OTP to that number. A short-lived ID token alone does not solve this — it limits the *blast radius per token* but a valid refresh token keeps silently minting new ones. TableCrew's response:

- **Settings > Security > "Log out of all other devices."** This calls a new callable, `revokeSessions` (not yet in `API_SPEC.md`'s endpoint list — flagged here as a real gap that document must close, and added to `TASKS.md`'s existing tracked-gaps list in this pass, following the same pattern already used for the duress-signal and account-deletion endpoint gaps), which invokes the Firebase Admin SDK's `revokeRefreshTokens` for the caller's own UID. This invalidates every outstanding refresh token instantly — every other signed-in instance of the app (including the current one, since a user invoking this from a *replacement* device is the common real case) is forced through a fresh phone-OTP challenge on its next request, regardless of how long that instance's ID token had left to live. One action covers both "my phone was stolen" and the far more common "I signed in on a friend's device and forgot to sign out."
- **Support-triggered revocation.** A user who can no longer access the app at all (device lost, not just "signed in elsewhere and still has this device") reaches the same `revokeSessions` effect through a Trust & Safety/support contact channel, gated by a fallback identity check (a fresh OTP challenge to the phone number on file). If the SIM itself is what was compromised (so a fresh OTP isn't a safe check), this is deliberately a **manual, human-reviewed support process, not further automated in v1** — automating account recovery without phone-number possession is itself a common account-takeover vector, and a human-reviewed fallback is the safer default at TableCrew's current scale and staffing.
- **Interaction with the re-verification triggers above.** A device/behavioral signal suggesting takeover (new device + new location + immediate Discover activity, already a re-verification trigger above) and an explicit `revokeSessions` call both funnel into the same Tier 2 re-verification requirement before Discover-adjacent actions resume for that account — a forced logout alone is not treated as sufficient to re-establish trust for the highest-risk surface; the account must re-prove identity, not just re-prove phone possession.
- **What v1 does not yet build, stated plainly rather than silently assumed:** a per-device session list ("see everywhere you're signed in, with device name and last-active time, and revoke individually") would be a strictly more usable control than today's all-or-nothing `revokeSessions`, and is a real, open enhancement tracked in `TASKS.md`. v1 ships the coarser all-devices revocation because it closes the actual security exposure (an attacker holding the device cannot stay silently signed in indefinitely once the legitimate owner acts) even without the friendlier per-device UI — shipping the blunt, effective version now rather than waiting for the nicer one is the deliberate trade-off here.

## Firestore Security Rules Philosophy

Rules are the last line of defense, not the only one — Cloud Functions perform business-logic validation (per `ARCHITECTURE.md` and `API_SPEC.md`), but rules must independently enforce the security-critical invariants because a client is never trusted, full stop. Our guiding principle: **rules default-deny, and every allow is scoped to the minimum data and minimum actor necessary.** We do not write broad `allow read, write: if request.auth != null` rules and rely on Cloud Functions to "do the right thing" — any authenticated user hitting Firestore directly (bypassing our functions, whether by a modified client or direct SDK calls) must be safely constrained by rules alone.

Concrete examples reflecting the collections in `DATABASE.md`:

- **Users**: a user can read their own full profile document, but can only read a restricted public subset of another user's profile (display name, photo, verification badge, ratings summary) — enforced by splitting sensitive fields (phone number, verification case ID, email) into a subcollection or a separate document only the owner and trusted Cloud Functions can read, rather than relying on field-masking in rules alone, which is easy to get subtly wrong.
  ```
  match /users/{userId} {
    allow read: if request.auth.uid == userId;
    allow read: if resource.data.profileVisibility == 'public'; // public subset doc only
    allow write: if request.auth.uid == userId
                 && request.resource.data.verificationTier == resource.data.verificationTier; // clients cannot self-elevate verification tier
  }
  ```
- **Tables**: only the host can update host-controlled fields (time, place, cap); any confirmed attendee can read; write access to `status` transitions is restricted to Cloud Functions only (via a custom claim or service-account check) because status transitions (Proposed → Filling → Confirmed → Happened → Rated) encode business rules — like minimum headcount or payment capture — that must not be forgeable by a client directly setting a field.
  ```
  match /tables/{tableId} {
    allow read: if resource.data.visibility == 'open'
                 || request.auth.uid in resource.data.attendeeIds;
    allow update: if request.auth.uid == resource.data.hostId
                  && request.resource.data.status == resource.data.status; // status is function-only
  }
  ```
- **Reports**: a user can create a report naming themselves as reporter, but can never read any report (their own or others') — reports are visible only to Cloud Functions (via the Admin SDK, which bypasses rules) and the trust & safety tooling used by human moderators. This prevents a reported user from ever discovering who reported them through a rules loophole, which is itself a safety property (retaliation prevention).
  ```
  match /reports/{reportId} {
    allow create: if request.auth.uid == request.resource.data.reporterId;
    allow read, update, delete: if false; // Admin SDK / staff tooling only
  }
  ```
- **RSVPs**: a user can create/delete their own RSVP but cannot edit another user's RSVP status or forge attendance for someone else — `request.auth.uid == request.resource.data.userId` on every write.

All rules changes ship with corresponding Firestore Rules unit tests (see `TESTING.md`) in the same PR, and per `ENGINEERING_GUIDELINES.md`, rules PRs require two reviewer approvals given how easy a subtly wrong rule is to ship and how costly it is if it under-restricts access to sensitive data.

## Reporting and Blocking

Reporting and blocking must be reachable in **at most 2 taps from any screen that displays another person** — a Table roster, a chat, a profile view, a Discover card. This is a hard product requirement, not a nice-to-have: tap 1 opens a "..." or overflow menu on that person's name/avatar, tap 2 is "Report" or "Block." No screen showing a human being is exempt from this, including group chat member lists and post-Table rating screens.

**Blocking** is immediate and client-visible within seconds: a blocked user disappears from the blocker's Discover results, cannot see or RSVP to Tables the blocker hosts if those Tables are Open, and cannot message the blocker. Blocking is one-directional and silent — the blocked user is never notified that they were blocked, only that (if relevant) they're no longer able to see or join a given Table. Blocks are stored server-side (`private/profile.blockedUserIds`, per `DATABASE.md` §3.1) and enforced in Discover's search/matching query layer (Typesense filtering, per `ARCHITECTURE.md`) as well as at the app layer for direct reads.

**Blocking inside a shared Crew — resolved, not left as an open assumption.** A block and a Crew are both relationships a user can share with the same other person at once (they blocked someone from a past Open Table, but that person is also, separately, in a Crew with them), and `docs/SCREEN_SPECIFICATIONS.md`'s Block Confirmation screen (Screen 28) had flagged the interaction as an unresolved product assumption. It is resolved here, because leaving it open meant "cannot message the blocker" (the guarantee stated above) was silently false for anyone who shared a Crew with their blocker: **"cannot message the blocker" holds inside a shared Crew too.** Concretely — Crew membership itself (roster, chat history visibility for everyone else, Table history) is unaffected by a block between two members, since removing membership is a separate, deliberate action (`leaveCrew`/`removeMember`) that this document does not want to trigger as an automatic side effect of a block a Crew's other members had no part in. But message *delivery/visibility* between the two specific blocking parties is suppressed the same way it is everywhere else: a blocked party's future Crew Chat messages are filtered out of the blocker's view of that chat (and vice versa — the block is enforced symmetrically for messaging purposes even though it was one-directional to create), consistent with the app-layer post-filtering pattern `DATABASE.md` §3.1 already uses for Discover. Both users can still see each other listed in the Crew roster (since hiding membership itself would be confusing and inconsistent with the roster the rest of the Crew sees) — what's suppressed is direct message exchange between them, which is the actual safety property "cannot message the blocker" is meant to guarantee.

**Reporting** captures a reason (harassment, no-show, unsafe behavior, fake profile, inappropriate content, other), an optional free-text field, and is tied to a specific Table or interaction where possible for context. Every report triggers a Cloud Function that writes to the `reports` collection and enqueues the case for the trust & safety review queue described below. Reporting a user does not automatically block them — the UI offers both as separate one-tap actions so a reporting user isn't forced to choose.

Report submission is rate-limited per user (to blunt coordinated false-reporting campaigns against a target) but the rate limit is generous enough not to discourage a genuine report — we bias toward taking reports seriously over minimizing report volume.

**Off-platform contact and stalking after a Table.** In-app blocking (above) stops contact through TableCrew's own surfaces, but it cannot stop a person from acting on information they gained in person (a face, a first name, a workplace mentioned in conversation) to contact or follow someone outside the app entirely — a materially different and higher-stakes case than a blocked in-app message, because TableCrew's own product created the introduction that led to a real-world safety threat. We treat a report of off-platform contact or stalking following a TableCrew-arranged Table as its own case type, not folded into ordinary harassment reports:
- The `reports.reasonCode` set (`DATABASE.md` §3.6) includes a distinct `off_platform_stalking` value so this case type is queryable and trackable separately from in-app harassment, and is never silently merged into general "harassment" volume where its distinct severity could get lost.
- Any report tagged `off_platform_stalking` is treated as at least SEV2 on intake, escalating to SEV1 if the report describes a credible immediate threat (e.g., the accused has shown up at the reporting user's home or workplace) — a deliberate departure from the default report-triage flow, because the physical-world stakes here match a duress signal during a live Table (above).
- Trust & safety response includes account-side action available regardless of whether a criminal complaint has been filed — immediate suspension of the accused's Discover access and messaging capability pending investigation, since our bar for internal action is "credible safety risk," not "legally proven" — plus explicit in-app guidance for the reporting user on preserving evidence (screenshots, dates, descriptions) and a direct pointer to local law enforcement and relevant victim-support resources. TableCrew is not a substitute for either, and the in-app copy says so rather than implying account controls alone can resolve a real-world stalking situation.
- This case type gets the same SEV1/SEV2 postmortem and user-communication commitments as any other incident of its severity (below) — it is not a lesser category just because the harmful conduct happened off our platform.

## Moderation Consequences, Escalation, and Appeals

Reporting (above) describes how a report reaches Trust & Safety; this section is the previously-missing answer to what actually happens to the reported account afterward — escalation, consequences, and how a user disputes a decision made about them. `DATABASE.md` §3.1 already defines the field this section narrates (`trustSignals.standingStatus`, enum `"good" | "warned" | "restricted" | "banned"`), but until this pass nothing explained what moves an account between those states or how a user pushes back on one.

**Review queue and baseline turnaround.** Every report lands in the `reports` collection (`DATABASE.md` §3.6) and the Trust & Safety review queue (`DATABASE.md` §5's `(status, createdAt)` composite index — oldest open reports reviewed first). Baseline target: a standard-severity report (harassment, fake profile, inappropriate content) gets an initial review within **3 business days**; `off_platform_stalking` reports are SEV1/SEV2 on intake (above) and follow that faster incident-response clock instead (15-minute acknowledgment / 1-hour mitigation for SEV1, 4-hour mitigation for SEV2), not this baseline. Per the surge protocol (below, Incident Response), if backlog depth means this baseline can't be met, that degradation is stated internally and, where it materially affects a user, reflected in what they're told — never a silent miss.

**Escalation ladder.** `standingStatus` moves through four states, and a move is always a deliberate Trust & Safety staff decision (never a fully automated one) once a report reaches human review, though automated signals can trigger the review itself:
- **`good`** — default state; no restriction.
- **`warned`** — a substantiated report of a real but lower-severity issue (e.g., a single inappropriate-content or minor-harassment finding). Consequence: an in-app notice explaining what was found and what it means if it recurs; no functional restriction yet. This mirrors the no-show ladder's "first incident is tracked, not punished" philosophy above.
- **`restricted`** — a substantiated pattern (repeated warnings), or a single substantiated report serious enough to warrant an immediate but not permanent restriction (e.g., a credible harassment finding that falls short of `off_platform_stalking`'s SEV1/SEV2 bar). Consequence: Discover visibility and the ability to create new Open/Discover Tables are suspended pending review; Crew-only/Closed Table use continues, mirroring the same tiered-risk logic the no-show and age-gating sections above already apply (Discover is the higher-risk, stranger-facing surface; Crew-only involves only people the user already has a relationship with).
- **`banned`** — a substantiated serious-safety-risk finding (assault, credible threat, `off_platform_stalking` confirmed, repeated `restricted`-level conduct). Consequence: full account suspension — Discover, Table hosting/joining, and messaging all blocked platform-wide, not just the Discover-adjacent subset `restricted` limits. A banned account is also the case the ban-evasion duplicate-detection mechanism (Abuse Prevention, below) is built to catch on re-registration.

**Effect on that user's existing Tables when standing changes to `restricted` or `banned`.** This was a real edge case this document did not previously answer: a host doesn't stop hosting Tables just because a report is filed against them elsewhere. On a transition to `restricted` or `banned`:
- Any Open/Discover Table the user hosts is immediately set `reportFlags.isSuppressed: true` (the same field/mechanism `API_SPEC.md`'s `reportUser` already uses for report-threshold suppression, applied here by a trigger on the `standingStatus` write rather than invented as a new mechanism) and, if not yet `happened`, is cancelled through the same system-triggered path `cancelTable` already uses for a host-initiated cancellation — confirmed/waitlisted/requested attendees are notified, since strangers relying on a Discover-listed Table are the exact population this restriction protects.
- Crew-only/Closed Tables the user hosts are **not** auto-cancelled by a standing change alone — consistent with this document's standing tiered-risk treatment of Crew-only surfaces (attendees already know the host) — unless the substantiated report that triggered the standing change was filed by an attendee of that specific Table, in which case that Table is cancelled through the same system path and its other attendees are notified with safety-neutral copy ("this Table has been cancelled" — never copy that discloses the report or names the reported user, consistent with reports never being visible to their subject or bystanders).
- A user who is merely `warned` keeps hosting/attending normally on every surface; `warned` carries no Table-level consequence, only the in-app notice above.

**Appeals.** Any user moved to `restricted` or `banned` receives an in-app notice stating that their standing changed and why in general terms (the category of finding, not the reporter's identity or the report's specific content, per the same retaliation-prevention logic that makes reports themselves unreadable to their subject) and a direct path to appeal through the same Trust & Safety contact channel the no-show dispute process above uses — this is a deliberate reuse of one lightweight, human-reviewed channel rather than a second parallel system. Target: an initial appeal response within **5 business days** (matching this document's postmortem cadence elsewhere, for consistency). Where team size allows, an appeal is reviewed by a different Trust & Safety staffer than whoever made the original call; at TableCrew's current founding-team-sized Trust & Safety desk (the same roster named in Incident Response's on-call rotation below), we state plainly that this segregation is a target we can't yet always guarantee, not a claim we make falsely — `TASKS.md` tracks adding a second-reviewer requirement as a formal process step once headcount supports it, the same honesty this document already applies to the on-call rotation's size.

## No-Show Accountability

No-shows undermine the entire premise of TableCrew — a Table that doesn't fill because past no-shows scared off attendees is a failure of trust, not just etiquette. We track no-shows explicitly:

- After a Table transitions to `Happened`, the host (and optionally other attendees) confirm who actually showed up, via a simple post-Table attendance check-off, distinct from the star rating flow.
- A confirmed no-show increments a `noShowCount` on the offending user's trust record (a fields on the user document not readable by other users, only by the owner and Cloud Functions, similar to the sensitive-fields pattern above).
- **Thresholds and consequences** are graduated, not a single ban switch: 1 no-show in a rolling 90-day window is tracked silently with no visible consequence (people miss things; we don't punish a single incident). 2 no-shows trigger an in-app nudge and a temporary reduction in Discover visibility (the user's Open Table RSVPs get lower ranking priority in Discover's matching for 30 days). 3 or more no-shows in the rolling window trigger a required re-confirmation step before the user can RSVP to any further Open Table (a lightweight "are you sure — no-shows affect other people" friction step) plus a further Discover visibility penalty. A pattern of 4+ escalates to manual trust & safety review and can result in Discover suspension (the user can still use Closed/Crew Tables, since those carry lower risk to strangers, but loses access to the stranger-facing surface) pending review.
- No-show counts decay over a rolling window (90 days) rather than accumulating forever — people's behavior and circumstances change, and permanent scarlet-letter tracking isn't proportionate to a missed brunch.
- Disputed no-shows (a user claims they did show up, or had a legitimate emergency) go through a lightweight appeal reviewed by trust & safety staff, not an automated system, since this is exactly the kind of judgment call that shouldn't be fully automated.
- **Defense against false or retaliatory no-show marking.** A no-show mark is not a unilateral, unreviewable action even before an appeal is filed. For Tables with 3+ confirmed attendees, a mark made solely by the host with no other attendee corroborating that the named person didn't show is flagged internally as single-source and weighted accordingly: it still increments `noShowCount` (a genuine no-show shouldn't go untracked just because only the host noticed), but it does not by itself trigger the harsher consequences at the 3+/4+ thresholds without the check above — if the accused user disputes it (via the appeal mechanism above) and no other attendee corroborates the host's account, the dispute is presumptively resolved in the accused user's favor pending trust & safety judgment, not the host's. This exists because a host's incentive is not always aligned with accuracy: a host who had a bad experience with an attendee for reasons unrelated to attendance has both the means and a motive to falsely mark them absent, and an unreviewable host-only attestation would make that a trivially effective harassment tool.
- **Pattern detection on the marking side, not just the marked side.** A host (or a small recurring group of attendees) whose no-show-marking rate against a specific individual, or whose overall no-show-marking rate across their hosted Tables, is a statistical outlier relative to other hosts is itself flagged for trust & safety review — coordinated false-marking (a group agreeing in advance to falsely report someone as a no-show) looks structurally different from organic no-show patterns (concentrated on one target, or an unusually high marking rate from one host), and we treat that signal with the same seriousness as the no-show pattern on the accused side.

## Content Moderation

**Corrected 2026-08, Milestone F5:** this section previously described a two-layer (automated-plus-human-review) moderation system, including known-bad-image-hash matching and a text-moderation pass, none of which had an owning milestone or a named implementation anywhere — it was aspirational scope written before any of it was actually scheduled to be built. F5 is the first milestone to build any of this, and it builds a narrower, real slice: automated image-only moderation for profile photos, via the pipeline actually specified in `FIREBASE.md` §2.5 and `DATABASE.md` §3.1a. The text below reflects what's actually built or concretely planned, with everything not yet scheduled disclosed as open rather than silently implied.

**What's actually built (Milestone F5): automated image check on profile photos.** Every photo uploaded to `users/{uid}/profile/pending/*` triggers a Cloud Storage-triggered Cloud Function that runs it through Google Cloud Vision API's SafeSearch Detection (ADR 0006) before the image is ever made visible to anyone else — checking adult/violence/racy/medical/spoof categories. A flagged image is quarantined (never copied to a publicly-readable path, never referenced by `users/{uid}.photoUrl`) and generates a Trust & Safety review task via the existing Reports model (`DATABASE.md` §3.6) — reviewed through the same moderation-consequence/escalation process this document's "Moderation Consequences, Escalation, and Appeals" section already covers for reports generally, rather than a separate, purpose-built moderation queue tool. There is currently no dedicated human-review UI beyond that shared Reports/review-task path, and no sampling of unflagged content to audit the automated system's false-negative rate.

**Explicitly not yet built, disclosed rather than silently assumed:** (1) known-bad-image-hash matching (to catch previously-reported abusive images being re-uploaded under a new upload) — SafeSearch's category-detection model doesn't provide this; a dedicated capability would need its own vendor/implementation decision, not assumed as a byproduct of ADR 0006. (2) A text-moderation pass over Table/profile descriptions and bios (hate speech, solicitation, off-platform-contact-pattern detection) — no Cloud Function or vendor call exists for this anywhere in the codebase. (3) Table cover-photo moderation — F5's pipeline is written generically enough to extend to `tables/{tableId}/photos/*` (`FIREBASE.md` §2.5) once a later milestone (F6+) actually builds Table photo upload, but that extension itself hasn't happened yet. None of these three block F5's actual scope (profile photos only, Screen 5), but a milestone that eventually builds Table cover photos, Table/bio text fields, or a real content-moderation queue tool should close these rather than assume they already exist because this section once implied they did.

## In-Table Emergency and Duress Response

A Table is a real, in-person gathering, and per `LEGAL.md` §3, the absence of any in-app answer to "what do I do if something goes wrong while I'm here" was a real gap, not a theoretical one. This section is the technical and process source of truth for that flow; `PRD.md` and `FEATURES.md` should reference this section for the product requirement rather than restate it.

**Quick-exit / duress signal.** Every live Table screen (the in-progress view shown to a confirmed attendee between a Table's `confirmed` and `happened` status transitions, per `DATABASE.md` §3.2) surfaces a persistent, always-visible safety affordance — not buried in a menu — that does two distinct things depending on how it's invoked:
- A single tap opens a lightweight "Are you OK?" quick-exit sheet: one tap to leave the Table screen entirely (closing out without needing to interact with other attendees or chat first) and one tap to trigger a duress signal.
- A duress signal (a long-press, or another deliberately-hard-to-trigger-by-accident action, to avoid false positives from casual taps in a genuinely urgent UI element) immediately: (1) writes a `duressSignal` document (`tables/{tableId}/duressSignals/{userId}`, Functions-only readable/writable, mirroring the `reports` collection's structural unreadability by other clients per `DATABASE.md` §6) timestamped and geo-tagged with the user's last known device location if location permission is granted; (2) pages the Trust & Safety on-call rotation described below as an automatic SEV1, with no human triage judgment call needed to escalate it — a duress signal is definitionally a SEV1, not a "let's see if it's serious" step; (3) shows the user immediate confirmation that help has been notified, plus one-tap access to locale-aware emergency calling (below), without requiring them to navigate away from the duress flow to find it.

**Locale-aware emergency-number display.** The emergency number surfaced in the duress flow and in the Table's static "Safety" info panel is never hardcoded to a single country's number — a US-centric `911` default is a common and dangerous mistake in this product category, and we call it out explicitly here to make sure it's never silently reintroduced. The number shown is resolved from the Table's `location.geopoint` (not the user's home country or app-store region, since a traveling user attending a Table abroad needs the local number for where they physically are) against a maintained country-to-emergency-number mapping (e.g., 911 in the US, 112 across the EU/UK, 000 in Australia, the police/fire/ambulance split in India, etc.), reviewed as part of the same international-expansion process that gates new-market launches per `ROADMAP.md`. If a Table's location can't be resolved to a known country mapping (a new or unmapped market), the panel falls back to general international emergency-number lookup guidance rather than silently defaulting to a US number — a wrong number in a genuine emergency is worse than an honest "we don't have this mapped yet, here's how to look it up."

**Opt-in "share my location with a trusted contact" for a specific Table.** A user may, per-Table, opt in to sharing a live location feed with one or more contacts they designate — which can be, but is not required to be, a TableCrew Crew member, since an SMS-delivered link works for someone entirely outside the app and the point is a real-world safety contact, not necessarily another TableCrew user. This is: (1) off by default, requiring an explicit opt-in each time rather than a persistent always-on setting, since a stale "always share" toggle is itself a privacy risk if forgotten; (2) scoped to the duration of that specific Table only, automatically expiring when the Table transitions to `happened` or after a fixed ceiling (e.g., 6 hours) if the status transition doesn't fire for some reason, so a share never silently persists indefinitely; (3) revocable by the sharing user at any time with immediate effect; (4) implemented via a signed, time-limited, unauthenticated-viewable link (so the trusted contact doesn't need a TableCrew account) that shows only the sharing user's live location and the Table's venue, not any other attendee's data or any other part of the sharing user's profile.

**Routing to Trust & Safety on-call.** A duress signal routes into the exact same on-call and severity process defined in `Incident Response` below, entering as a pre-classified SEV1 (active harm/immediate safety risk) rather than a lower severity requiring triage first — the 15-minute acknowledgment and 1-hour mitigation targets apply from the moment the signal is written, and the on-call engineer's available mitigations include the same platform-side levers described below (e.g., immediately suspending other attendees' Discover access pending review) plus a duress-specific step this flow adds: the on-call responder follows a documented, rehearsed script for whether and how to advise the user to contact local emergency services directly (TableCrew is never a substitute for that, and the in-app flow's copy says so explicitly) versus when the situation calls for TableCrew-side account action (suspension, evidence preservation) without necessarily being an emergency-services-level event.

## Incident Response

Incidents are classified by severity:

- **SEV1** — active harm or immediate safety risk to a user (e.g., a credible report of assault or threat tied to a Table meetup, a data breach exposing verification/identity data, Discover matching a known-banned user due to a bug). Page the on-call engineer immediately, 24/7, via the paging tool; founding team is notified regardless of time of day. Target: acknowledgment within 15 minutes, mitigation (even partial — e.g., disabling Discover matching entirely if needed) within 1 hour.
- **SEV2** — significant safety or trust degradation without confirmed active harm (e.g., a moderation bypass allowing explicit images through, a rules bug over-exposing report data, a spike in a specific abuse pattern). On-call notified during business hours, or immediately if detected outside business hours by automated alerting. Target: mitigation within 4 hours.
- **SEV3** — a bug or gap with safety relevance but no near-term exploitation risk (e.g., a no-show threshold miscalculating in a way that's too lenient, not too harsh). Standard priority triage, fixed within the current or next sprint.

On-call rotation: for a founding team this size, on-call is the engineer who most recently touched trust & safety code, backed up by a second named engineer, rotating weekly — formalized in the on-call schedule tool once the team is large enough to need one; until then, it's an explicit Slack-pinned rotation, not an implicit assumption.

**Surge staffing when report volume spikes faster than headcount.** The on-call rotation above is sized for steady-state volume with a founding-team-sized roster; it is not sized for a viral moment, a bad-press cycle, or a coordinated bad-actor campaign that spikes report volume well beyond normal — "we'll hire more people eventually" is not an adequate answer to a spike happening this week. When open-report-queue depth or SEV1/SEV2 incident rate exceeds a defined multiple of trailing 7-day average (a concrete trigger, tracked via the same `reports` composite index used for the T&S queue per `DATABASE.md` §5, not a vibes-based judgment call), the following surge protocol activates as a documented degradation, not an ad hoc scramble:
1. **Temporary engineer reallocation.** Any engineer with prior trust/safety-surface experience (per the two-approver rule in `ENGINEERING_GUIDELINES.md`, a defined, non-empty set even on a small team) is pulled into a temporary review rotation, with feature work explicitly deprioritized for the duration — this is a founder-pre-approved action, not something that needs a real-time judgment call during the surge itself.
2. **Tightened admission valve, not just faster processing.** If review capacity genuinely cannot keep pace, we have a pre-agreed lever to reduce new-report inflow's downstream risk rather than let a backlog of unreviewed, potentially-unsafe content or accounts sit exposed: temporarily raising the bar for new Open Table creation or Discover visibility (e.g., a short additional cooling-off period before a new Tier-2-verified account's Table becomes Discover-visible) until the backlog clears. This trades growth for safety deliberately during a surge, consistent with "safety is a feature, not a department."
3. **SLA transparency, not silent degradation.** If the backlog means our normal review-time expectations (referenced throughout this document) can't be met, that degradation is stated internally (tracked in `TASKS.md` with a visible backlog-age metric) and, where it materially affects user-facing timelines, reflected in user-facing messaging rather than pretending normal SLAs still hold.
4. **Postmortem regardless of whether any single incident was a SEV1.** A surge event gets the same blameless postmortem treatment as an incident even if no individual report during the surge rose to SEV1 — the surge itself, and whether the trigger threshold and response were adequate, is the thing being reviewed.

**User communication commitments**: any SEV1 incident involving actual user harm gets direct, individual communication to affected users within 24 hours of confirmation, in plain language, describing what happened and what we're doing about it — never a vague "we take safety seriously" non-statement. Any incident requiring disclosure under GDPR/CCPA/LGPD/DPDP breach-notification rules (see below) follows the applicable legal timeline (e.g., GDPR's 72-hour authority notification), which our incident process treats as a floor, not a ceiling — we aim to tell affected users promptly regardless of whether the law strictly requires it in a given case.

Every SEV1 and SEV2 incident gets a blameless postmortem within 5 business days: timeline, root cause, what caught it (or why nothing did), and concrete follow-up actions with owners and dates, tracked in `TASKS.md`.

## Data Privacy Compliance

TableCrew is global-first by design (`VALUES.md`), which means privacy compliance isn't "GDPR for our EU users, ignore the rest" — it's built as a general capability that happens to satisfy multiple regimes at once: **GDPR** (EU/EEA), **CCPA/CPRA** (California), **LGPD** (Brazil), and **India's DPDP Act**. These regimes differ in enforcement detail (e.g., DPDP's "consent manager" concept, LGPD's ANPD authority structure, CCPA's opt-out-of-sale framing vs. GDPR's consent-first framing) but converge on the same core mechanics we build once: a lawful basis for each category of data collected, minimal collection, a real data export mechanism, and a real data deletion mechanism — not a support ticket that quietly does nothing.

**Minimal collection**: we collect what a gathering-coordination app needs (name, phone, photo, location for Table matching, RSVP/rating history) and explicitly avoid collecting what we don't need to operate the product, even if it would be marketing-useful (e.g., we do not ingest a user's full contacts list to build a social graph — Crew formation is user-initiated by invite, not scraped).

**Data export**: implemented as a callable Cloud Function (`exportUserData` — see `DATABASE.md` §7, which is the canonical name for this callable; this document previously called it `requestDataExport`, a naming drift between the two documents fixed in this pass) that assembles the user's Firestore documents (profile, Tables hosted/attended, RSVPs, ratings given/received, Crew memberships) into a structured JSON/CSV bundle, generated asynchronously and delivered via a signed, time-limited Cloud Storage download link, with the request and completion logged for audit purposes. This is a real mechanism a user can trigger from their account settings, target turnaround under 48 hours, not a manual, ad hoc process run by an engineer on request. Note for whoever formalizes this in `API_SPEC.md` (tracked in `TASKS.md`): the endpoint is referenced by name in both `SECURITY.md` and `DATABASE.md` but has no actual entry in `API_SPEC.md`'s endpoint list yet — a real spec gap, not an oversight to silently paper over.

**Data deletion**: implemented as a callable Cloud Function (`deleteAccount` — see `DATABASE.md` §7, the canonical name; this document previously called it `requestAccountDeletion`, corrected here to match) that performs actual deletion, not a soft "deactivated" flag masquerading as deletion. On confirmed deletion request: the user's Firebase Auth record is deleted, their Firestore user document and owned subcollections are deleted (per `DATABASE.md` §7's public-document-tombstone-plus-private-document-hard-delete split), their profile photos in Cloud Storage are deleted, and they're removed from any Table rosters, Crew memberships, and the Discover Typesense index. Data we retain past deletion is limited to what's legally or safety-necessitated and is explicitly minimal: aggregated/anonymized analytics that can't be tied back to the individual, and — where a user has an active trust & safety case (e.g., an unresolved report against them, or they're the confirmed subject of a serious safety report) — the minimum record needed to prevent re-registration and evade a ban, retained for a defined period and reviewed periodically for continued necessity, not kept indefinitely by default. This retention exception is documented plainly in our privacy policy, not hidden in fine print. This endpoint has the same `API_SPEC.md` formalization gap noted for `exportUserData` above.

Financial/payment records are a distinct, narrower exception from the trust-and-safety retention above, and this document is explicit about it rather than promising unqualified deletion of "all user data." Per `VALUES.md`, a deletion request removes or irreversibly anonymizes personally-identifying data immediately (as described above), but a minimal transaction ledger — amounts, dates, and a tokenized/anonymized reference sufficient for tax and financial-regulatory compliance, with the Stripe customer/payment-method identifiers that could re-link it to the person removed or replaced with an opaque token — is retained for approximately 7 years, matching standard tax and financial recordkeeping requirements in our operating jurisdictions. This is not a loophole we're using to quietly retain more than we admit to: it's disclosed in the same privacy-policy retention-exception language as the trust-and-safety exception above, but is a separately-named, narrower exception (financial ledger only, anonymized, ~7 years, justified by tax/legal compliance) rather than being folded into the trust-and-safety bucket's different justification (preventing ban evasion).

Deletion requests are honored within the legally required window (30 days under most regimes; we target 14 days as our internal SLA to give margin), subject to the two named retention exceptions above.

**Cross-border data residency**: Firestore/Firebase project region selection (detailed in `FIREBASE.md`) is chosen with data residency expectations in mind for major markets; as TableCrew expands into jurisdictions with data localization requirements (a live consideration for future India/Brazil expansion given DPDP and LGPD), we evaluate regional Firebase project deployment rather than assuming a single global project services every market indefinitely.

## Abuse Prevention

- **App Check** is enforced on every callable Cloud Function and Firestore access path (per `FIREBASE.md`), rejecting requests that don't originate from a genuine, unmodified instance of the TableCrew app — this is our primary defense against scripted/automated abuse (mass fake account creation, scraping Discover profiles, automated report spam) that doesn't come through the real client at all.
- **Rate limiting** is enforced in Cloud Functions (per-user and per-IP where relevant) on sensitive actions: account creation, RSVP creation, report submission, messaging first-contact (a new conversation with a stranger from Discover is rate-limited more tightly than messaging within an existing Crew, since unsolicited-contact abuse is a Discover-specific risk).
- **Fake-account detection** combines signals rather than relying on any single check: phone verification (Tier 1) blunts trivial mass creation; velocity signals (many accounts from the same device/IP in a short window) are flagged for review; and behavioral signals post-signup (an account that immediately attempts high-volume Discover RSVPs or messaging with no organic usage pattern) feed a risk score that can require Tier 2 re-verification or throttle the account pending review, without necessarily banning outright on a false-positive-prone automated basis alone.
- **Ban-evasion resistance via verification-vendor duplicate detection.** Because Tier 2 verification is required for any Discover-adjacent action, a banned user attempting to evade the ban by creating a new account with a new phone number faces Persona's own document/biometric duplicate-detection signal (the same government ID or matched face reappearing under a new account) as a barrier that's harder to fake than a phone number alone — an account whose ID-verification submission matches a previously-banned case ID is auto-flagged for trust & safety review before being granted `verificationTier: "id_verified"`, rather than silently re-verified as if new. This is the concrete mechanism behind `DATABASE.md` §7's commitment to retain the minimum record needed to "prevent re-registration and evade a ban" — without a persisted, cross-checkable reference to the banned case, that retained data would have nothing to check against. **Not available in Phase 0 (2026-08, ADR 0007).** Manual review has no cross-account document or biometric matching — nothing compares a new submission against previously-banned ones, and a reviewer's recall is not a control. This is the most consequential capability this document loses under manual verification, because it is a specific commitment made here and in `DATABASE.md` §7 rather than a general aspiration: for the Phase 0 window, a banned user who re-registers with a new phone number and submits the same genuine ID faces no automated barrier at this gate. It is disclosed here rather than quietly left standing, and it is a first-order reason to restore a vendor before Discover opens beyond closed beta.

## Safety Gate Checklist

Per `PRD.md`, every new feature — and especially anything touching Discover — must pass this checklist before launch, not after. This is enforced as a literal checklist item in the feature's launch PR/plan, reviewed by at least one engineer who didn't write the feature:

1. **Does this feature expose a user to another user they don't already know (i.e., is it Discover-adjacent)?** If yes, items 2–7 are mandatory, not optional.
2. **Is reporting reachable within 2 taps from every new screen that shows another person?** Verified by an actual tap-count walkthrough, not an assumption.
3. **Is blocking reachable within 2 taps, and does it take effect immediately across Discover search, messaging, and Table visibility?**
4. **Does any new data field or surface respect existing Firestore rules defaults (deny-by-default), or does it require new rules — and if so, do those rules have unit tests?**
5. **Does this feature touch verification-gated actions (hosting/joining Open Tables)? If so, is Tier 2 verification enforced server-side, not just client-side?**
6. **Does this feature introduce new user-generated content (images, text)? If so, is it wired into the moderation pipeline (automated + human review queue) before going live to Discover?**
7. **Does this feature ship behind a feature flag with a named owner and a written rollback plan** (per `ENGINEERING_GUIDELINES.md` and `DEPLOYMENT.md`), so that if a safety issue emerges post-launch, it can be turned off in minutes, not days?
8. **Has the data this feature collects been checked against the minimal-collection principle** — is every new field actually necessary, and is it covered by the existing export/deletion mechanisms above?
9. **If this feature adds or modifies any screen shown during a live Table, does it preserve unobstructed access to the quick-exit/duress affordance described in `In-Table Emergency and Duress Response` above** — no new live-Table UI may cover, delay, or bury that affordance behind additional taps.

A feature that can't check every applicable box here does not ship to production, full stop — this is what "safety is a feature, not a department" means in practice: it's a gate enforced by engineering process, not a separate team's problem to catch later.
