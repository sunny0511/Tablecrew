# Changelog

This is the dated record of material changes to the TableCrew knowledge base and, later, the product itself. Every entry states what changed and why — not just what, because the "why" is what keeps future decisions consistent with past reasoning. Entries are in reverse chronological order.

## 2026-08 — Foundation re-scoped: Discover pulled forward to new Milestone F7, recurring Crews deferred to Phase 1, internal demo-build practice started

**What changed, and why (founder-directed):** Discover — TableCrew's most differentiated feature, since coordinating with people you already know already has many adequate solutions (WhatsApp groups, calendars, generic messaging), while finding meaningful conversation with people you don't already know does not — is now **built** during the Foundation engineering effort, immediately after Trust & Safety infrastructure (Milestone F6) lands, rather than treated as pure Phase 1 work to start only after the entire Crew-first product ships. The founder's reasoning: validate the differentiated bet as early as practical, once (not before) the safety backbone `docs/ROADMAP.md` already requires is proven. Recurring Crews (`scheduleRecurringTable`) moves the opposite direction — out of Foundation, deferred to Phase 1, the same treatment bill-splitting already received.

**This is a build-timing change, not a launch-timing one.** `docs/ROADMAP.md`'s Phase 0 exit criteria and Discover's legal/statute review are unchanged and still gate when Discover's Remote Config flag (per `docs/DEPLOYMENT.md`'s existing Feature Flag Lifecycle) actually ramps for real users — Discover's code now ships inside Foundation's binary, defaulted off, the same way any other risky feature ships dark before its flag ramps.

**`docs/IMPLEMENTATION_PLAN.md`** — the primary document, substantially revised: Section 0 gets a build-vs-launch distinction (Foundation no longer strictly equals Phase 0's scope, though it still equals Phase 0's *launch* surface); Section 1's scope description updated; a new Section 2.4 records the full reasoning and every downstream document touched; R7 (originally "defer Typesense entirely") is superseded by the new plan and a new R8 documents the milestone-boundary demo-build practice; the milestone table grows from nine milestones (F0–F8) to ten (F0–F9) — F0–F6 unchanged (F0–F4 already shipped, numbering frozen), **new Milestone F7 (Discover)** inserted (Tier 2/Persona integration, Typesense infrastructure with a real CI story, Open-Table visibility, Discover browse/search/filter, all behind a flag), old F7 (Live Table/Chat/Rating/Crew management) becomes **F8** with Screen 26/`scheduleRecurringTable` removed from its scope, old F8 (Notifications/hardening) becomes **F9**; total duration estimate revised from 14–18 weeks to roughly 17.5–22 weeks.

**Documents corrected to stay consistent with the re-scope, each with inline reasoning:** `docs/ROADMAP.md` (new build-vs-launch note in the Sequencing Philosophy section, plus inline clarifications on the Phase 0/1 feature lists); `docs/PRD.md` (FR-T14c tagged explicitly Phase 1; a build-vs-launch footnote on the Phase 0 launch-blocker list); `docs/FEATURES.md` (a genuine, pre-existing contradiction this re-scope surfaced and resolved: the "Recurring Table series" row said "Won't (v1)... superseded by" Phase 2's nudge system, which was never actually true — `PRD.md` FR-T14c and a fully-specified `scheduleRecurringTable` endpoint already described a real planned feature; corrected to "Deferred (Phase 1)" with the nudge-system relationship clarified); `docs/SECURITY.md` (raised the urgency of confirming Persona's Aadhaar/India-ID coverage, since the new F7 needs the real Tier 2 integration built during Foundation, not just before Phase 1 launch — still doesn't block *writing and testing* the integration, since Persona's sandbox mode suffices for that).

**Internal demo builds, starting retroactively at Milestone F4 (separate founder directive, same session).** Every milestone close now also produces and distributes a build via Firebase App Distribution — `docs/DEPLOYMENT.md`'s new "Internal Demo Builds at Milestone Boundaries" section, cross-referenced from `docs/CI_CD.md`'s stage 6 (which describes the intended automated end state but has never actually run — no Fastlane lane or App Distribution tester group exists yet). Near-term this is a manual founder-run step (`flutter build apk --debug` + `firebase appdistribution:distribute`); iOS demo builds are blocked pending Apple Developer Program enrollment and Fastlane signing setup, a new disclosed open item. F4's own catch-up build is the founder's to run — exact commands in `TASKS.md`; disclosed there that it'll look identical to F3's build, since F4 was backend-only.

**Not done in this pass, disclosed as a follow-up:** `docs/adr/0002-typesense-over-algolia.md` and `docs/adr/0005-persona-over-stripe-identity.md` both contain a now-stale "not in Foundation's critical path" claim. Per `docs/ENGINEERING_GUIDELINES.md`'s ADR-immutability policy, fixing this needs superseding ADRs, not in-place edits — the underlying vendor decisions are unaffected and remain correct, only the timing/scope claim is wrong. ## 2026-08 — Milestone F4 (Core API surface: Tables & Crews) complete and fully verified: 11 callables, two shared infra pieces, two pre-existing rules gaps and one real spec contradiction found and fixed, plus three real bugs caught by live emulator runs

**What changed:** Implemented `docs/API_SPEC.md` §3.1/§3.2 for real — all 7 Tables callables (`createTable`, `updateTable`, `requestSeat`, `confirmAttendee`, `cancelTable`, `cancelRsvp`, `endTableEarly`, commit `e8a93f7`) and all 4 Crews callables (`createCrew`, `updateCrew`, `addMember`, `removeMember`/`leaveCrew`, commit `46c6dbf`), backed by two new shared Cloud Functions infrastructure pieces built first: `functions/src/shared/idempotency.ts` (the real `idempotencyKeys/{key}` store, commit `a3bb7b3`) and `functions/src/shared/rateLimit.ts` (the real fixed-window `rateLimits/{bucketId}` counter, commit `0057c4c`), both unit-tested to 100% coverage via in-memory fakes.

**Two pre-existing security-rules gaps found and fixed before building on top of them, same category Milestone F2 found for `users`:** `tables/{tableId}`'s F1 create/update rules were client-writable (checked only `hostId`, not what got written — a client could set `status` directly, bypassing every callable's business rules); now fully Functions-only (commits `c0cb3f7`, `0057c4c`). `crews/{crewId}`'s update rule allowed *any* member (not just an admin) to write directly, via a denylist that silently allowed `recurrence` (schema-present but ungoverned until Phase 1's `scheduleRecurringTable`); fixed to admin-only with an allowlist (commit `b5c3a53`).

**One real internal contradiction found in `docs/API_SPEC.md` itself, not just an implementation ambiguity:** `createCrew`'s text claimed added members require "invite acceptance, not unilateral addition" — but `addMember`'s own "Server behavior" paragraph describes an immediate direct membership write, and no invite/token data model or issuance endpoint exists anywhere in `docs/DATABASE.md` to back the claimed acceptance flow. Resolved in favor of `addMember`'s mechanically-specific, actually-buildable description; both endpoints' spec text corrected inline with the reasoning. Disclosed consequence: admin-privileged unilateral add is presently possible, and `addMember`'s `inviteToken` request mode throws `not-found` rather than pretending to support a flow with no backing schema.

**Three stale "shared Zod schema" claims corrected** (`docs/API_SPEC.md` ×2, `docs/ARCHITECTURE.md` ×1) — this codebase never adopted Zod; the real, established convention since Milestone F2 is hand-rolled per-field validators. One of the three was incorrectly describing already-shipped F2 code, not just a forward-looking miss.

**Two disclosed, reasoned product-spec gaps resolved rather than silently invented or silently skipped:** no closed interest-tag taxonomy exists anywhere in the docs (resolved via a hard-coded starter `KNOWN_INTEREST_TAGS` set, flagged as needing a real taxonomy-management system before Discover facets on it); `CREW_AT_CAPACITY`'s soft cap has no documented numeric default anywhere either (resolved via a disclosed `CREW_MEMBER_SOFT_CAP = 20`, flagged as needing a real Remote Config read once product needs it tunable without a redeploy). The "Location TBD" flow (`isTBD`/`tbdConfirmBy`) has no reachable path through `createTable`'s documented request shape — every Table this milestone creates has `location.isTBD: false`, disclosed rather than guessed at.

**Deliberately not wired, disclosed in code comments:** notification fan-out and Typesense index removal on `cancelTable` (FCM is Milestone F8, Typesense is Phase 1); the blocked-user check on `requestSeat` (`blockUser` is Milestone F6).

**Verified for real, in my own sandbox** (Node/npm present; `functions/node_modules` already existed from the founder's earlier real `npm install`, letting me self-verify Functions-side TypeScript without a founder round-trip for the first time this project): `npm run build` clean, `npm run lint` clean, `npm run test:coverage` 85/85 passing, both `tables/validation.ts` and `crews/validation.ts` at 100% line coverage. `firestore/test/rules/`'s `tsc --noEmit`/`npm run build` both clean.

**Functions emulator integration tests added** (`functions/test/integration/tables.integration.test.ts`, 13 tests; `crews.integration.test.ts`, 10 tests; commit `6714c2e`), extending Milestone F2's `users.integration.test.ts` pattern — real Auth/Firestore/Functions emulators, no mocking. `emulatorClient.ts` gained `seedUserProfile()` for direct Admin-SDK profile seeding (needed to exercise `TRUST_STANDING_RESTRICTED`, which `completeAccountSetup`'s request contract has no field to set).

**The founder then ran both emulator suites for real, and — consistent with every prior milestone's first live-emulator run — it found real bugs no amount of unit-testing or hand-review could have caught, across three iterations:**

1. **Rules-emulator, first run (57/59):** two tests in `firestore/test/rules/src/tables.rules.test.ts` were still asserting the *old* F1 behavior (direct host create/update) that this same milestone's own rules change had just replaced with `if false` — I'd updated `crews.rules.test.ts` to match its rule change but missed the equivalent fix for `tables.rules.test.ts`. Fixed (commit `008a328`); **second run: 59/59.**
2. **Functions-integration, first run (28/31):** three of my own test fixtures used an illegal `capacity: {min: 2, max: 1}` (`tables/validation.ts`'s hard floor is `max >= 2`), so `createTable` correctly rejected them before the tests' real logic ran. Fixed to `max: 2` with a third guest per scenario (commit `8eee524`).
3. **Functions-integration, second run (30/31) — a real bug in `functions/src/tables/index.ts`, not a test bug:** `cancelRsvp`'s transaction called `tx.delete(rsvpRef)` *before* its waitlist-promotion `tx.get(...)` query later in the same function. Firestore requires every transaction read to happen before any write; violating that threw "transactions require all reads to be executed before all writes," surfacing as a `500 INTERNAL` whenever `cancelRsvp` needed to promote a waitlisted RSVP — exactly the class of bug the deliberate fake-Firestore-unit-tests/real-emulator-integration-tests split exists to catch, since no in-memory fake models Firestore's actual read-before-write ordering. Fixed by hoisting the read before any write (commit `72b1b22`); **third run: 31/31.**

**Final verified state:** rules-emulator 59/59, Functions-integration 31/31 — covering all 11 new Tables/Crews callables' real transactional behavior (capacity races, idempotency-store interplay with a real Firestore `create()`, waitlist promotion, Crew membership-map transactions) plus the 8 pre-existing Milestone F2 tests, unaffected throughout. The founder also re-ran the full Milestone F3 Flutter suite alongside this work — still clean, no regression.

**Milestone F4 is now complete.** Milestone F5 (Feature: Onboarding, Screens 1–7) may begin per `docs/IMPLEMENTATION_PLAN.md`.

**What changed:** Delivered every piece `docs/IMPLEMENTATION_PLAN.md` scopes into Milestone F3: a Material 3 theme hand-transcribed from `docs/DESIGN_SYSTEM.md` (Recommendation R3's `ColorScheme` slot-mapping, `app/lib/core/theme/`, commit `c794820`); a GoRouter route table covering all 27 Foundation-scope screens, every route rendering a stub placeholder (`app/lib/core/routing/app_router.dart`, commit `10b2af4`); a named, docs-only `app/lib/features/` skeleton (`onboarding/`, `tables/`, `crews/`, `trust/`, `account/`, commit `2eae7ee`); `OfflineMutationQueue` (Recommendation R1, `app/lib/core/offline/`, commit `eea53a3`); and an Alchemist-based golden-test harness (Recommendation R2) with `StatusChip` as its first covered component (commit `71e3cf4`).

**Kickoff (commit `a3bdfda`), the necessary first step:** no Flutter/Dart toolchain had ever run in this build environment before this milestone — every Dart file since F0 was only hand-brace-balance-checked. The founder's real Flutter 3.44.8 install immediately surfaced that every hand-guessed `pubspec.yaml` pin from F0/F2 was over a year stale, and one (`riverpod_generator: 2.4.3`) didn't resolve at all against current tooling. **OfflineMutationQueue:** `idempotency_key_store.dart` persists a mutationId → UUIDv4 map in `SharedPreferences`, matching `docs/API_SPEC.md` §2's exact contract (client-generated UUID v4, persisted before the first attempt, reused across retries including app restarts). Deliberately out of scope: auto-replaying a failed call once back online — a Dart closure can't survive an app restart, so replaying the call with rehydrated draft data is left to the feature layer (F6/F7), the only layer that knows how to reconstruct it.

## 2026-08 — Milestone F2 verified: three real emulator runs, two real bugs found and fixed, 8/8 integration tests passing

**What changed:** Closed the two verification items left open by the entry below. First, the founder re-ran the rules-emulator suite for real (`firebase emulators:exec --only firestore ...`) — all tests passed, including the two flipped `assertFails` create-tests and the new `dateOfBirth` restriction test.

Second, and more involved: real Firebase Emulator Suite integration tests were added at `functions/test/integration/` for `validateAge`/`completeAccountSetup`/`revokeSessions` (signing in a real emulated Auth user, calling the actual deployed callables over HTTP — not mocks). Getting these green took three real runs, each surfacing a genuine bug real execution alone could catch:

1. **Run 1 (7/8 failing):** every authenticated call returned a generic `{"message":"Unauthenticated","status":"UNAUTHENTICATED"}` rather than our own handler's `"Sign-in required."` text — proof the rejection happened inside the Functions Framework itself, before our handler ran. The emulator's own log had flagged `firebase-functions@5.1.1` as outdated; founder confirmed current versions via `npm view` (`firebase-functions@7.3.2`, `firebase-admin@14.2.0`) and we bumped to those (commit `e2a6965`).
2. **The bump surfaced a real compile break:** `firebase-admin@14.2.0` removes the old namespaced `admin.apps`/`admin.initializeApp()`/`admin.firestore()`/`admin.auth()`/`admin.firestore.FieldValue` API entirely — a genuine `tsc` error the founder hit immediately after `npm install`. Migrated every call site (`functions/src/index.ts`, `functions/src/users/index.ts`, `functions/test/integration/*.ts`) to the modular `firebase-admin/{app,auth,firestore}` imports (commit `9bb8846`).
3. **Run 2, same 7/8 failures:** the version bump didn't fix the original bug. Root cause, finally isolated: `enforceAppCheck: true` really is enforced by the Functions emulator — this suite's original assumption that it wasn't was simply wrong — and Firebase's callable framework returns that same generic `Unauthenticated` error when App Check enforcement fails, deliberately indistinguishable from an Auth failure so as not to leak which layer rejected the request. Since the Firebase Emulator Suite has no App Check emulator at all, `enforceAppCheck: true` made these callables permanently untestable (and undevelopable) locally. Fixed by enforcing App Check only outside the Functions emulator: `ENFORCE_APP_CHECK = process.env.FUNCTIONS_EMULATOR !== 'true'`, using the framework's own env var rather than a bespoke flag (commit `db8a31a`).
4. **Run 3: 8/8 passing**, with the unauthenticated case's error message now correctly reading back our own `"Sign-in required."` text — confirming the original diagnosis was right. Coverage: unauthenticated rejection; `validateAge`'s eligible/ineligible/malformed-input branches; `completeAccountSetup`'s under-18 and invalid-displayName rejections; successful `users/{uid}` + `private/profile` creation with `residencyRegion` correctly derived from a GB phone number; idempotent-on-retry behavior (`createdAt` unchanged on a second call, no duplicate write); and `revokeSessions` advancing `tokensValidAfterTime`.

**Why this is a separate entry from the one below:** same reasoning as F1's analogous two-entry split — real tool execution surfaced real, previously-undetectable defects (a stale dependency pin, a breaking API removal, and a wrong assumption about local App Check behavior), which this changelog records distinctly from "as-planned, unverified" scaffolding work.

**Disclosed, not silently accepted:** App Check enforcement itself is still not exercised by this suite — it's simply inactive during emulator runs by design now, since there's no way to satisfy it locally; production behavior (`enforceAppCheck: true` outside the emulator) is unchanged. The Flutter toolchain gap (no Flutter SDK available anywhere in this build environment since F0) is carried forward, non-blocking, same as it has been since F0.

## 2026-08 — Milestone F2 (Auth & identity, Tier 1): code complete, verification pending

**What changed:** Implemented Milestone F2 per `docs/IMPLEMENTATION_PLAN.md` and founder go-ahead: phone/OTP sign-up's account-creation step, DOB/age-gate with server-side validation, and session lifecycle (`revokeSessions`).

Docs first (commit `471d1ff`): `docs/DATABASE.md` gained `users/{uid}/private/profile.dateOfBirth`; `docs/API_SPEC.md` gained a new §3.9 with `validateAge` (non-persisting, rate-limited 20/hr/uid) and `completeAccountSetup` (rate-limited 5/hr/uid); `docs/SCREEN_SPECIFICATIONS.md` Screens 4/5/6 now name both endpoints explicitly instead of describing unnamed bundled behavior.

Writing `completeAccountSetup`'s contract surfaced a real F1 security gap, corrected in the same milestone rather than carried forward silently (commit `fdc2c79`): the F1 rule for `users/{uid}` and `private/profile`'s `allow create` was `if isSignedIn() && request.auth.uid == userId` — it checked *whose* uid was writing but never *what* it wrote, so a signed-in client could create their own `users/{uid}` document with `verificationTierPublic` already set to a verified tier, before any real Tier 2 identity check ever ran. Fixed to `if false` (Functions-only, via `completeAccountSetup`), with `dateOfBirth` added to `private/profile`'s client-update-denied field list. The rules tests were updated to match: the two create tests flip from `assertSucceeds` to `assertFails`, and a new test asserts the owner can't set their own `dateOfBirth` via a direct update.

New Cloud Functions domain, `functions/src/users/` (commit `d82c24d`): `ageGate.ts` (`isWellFormedDateOfBirth`/`computeAgeAsOf`/`isEligibleAge`), `residency.ts` (`deriveResidencyRegion`, E.164 calling-code lookup defaulting to `IN`), `validation.ts` (server-side mirrors of Screen 5/6's client validation), and the three `onCall` callables. `completeAccountSetup` is deliberately **not** built on the generic `idempotencyKeys` mechanism (`docs/API_SPEC.md` §2) — since its target document id is always the deterministic `users/{uid}`, it's idempotent by construction (pre-check for an existing doc, batch-create if absent, re-check-and-succeed if the batch commit races another retry), avoiding standing up Milestone F4's generic idempotency-key store early just to serve one endpoint.

Real unit tests for the new pure logic (commit `dc521f0`): 54/54 passing, 100% line / 96.46% branch / 100% function coverage overall, 100/100/100 on the three new modules specifically. Writing these tests found and fixed a real bug unrelated to the logic itself: `functions/package.json`'s test scripts used the shell glob `lib-test/test/*.test.js`, which is single-level and silently skipped the new `lib-test/test/users/` subdirectory — `npm test` reported only the 4 pre-existing tests passing with the 3 new files never executing. Fixed both `test` and `test:coverage` scripts to use `node --test $(find lib-test/test -name '*.test.js')`.

First Flutter application code in this repository (commit `625b51a`): `app/lib/core/auth_state.dart`, three `@riverpod` providers (`authStateChanges`/`isSignedIn`/`currentUid`) wrapping `FirebaseAuth.instance.authStateChanges()`, deliberately scoped to raw sign-in state only — not "has this user finished onboarding," which needs the still-empty Firestore repository layer in `app/lib/data/`. Also fixed a stale claim in `app/lib/data/README.md`, left over from F1: it said the data/repository layer would be "populated starting in Milestone F1," but F1 turned out to be Firestore rules/schema/seed-scripts only, with no Flutter repository code — corrected to state the directory is still empty by design and repositories start landing Milestone F4 onward, once a client feature actually has something to call.

**What changed:** Following up on the "code complete, verification pending" entry below, the founder ran `npm install` in `firestore/test/rules/` and `scripts/` (real lockfiles committed, `cffbd6c`) and executed the rules-emulator tests for real for the first time: `firebase emulators:exec --only firestore "npm --prefix firestore/test/rules test" --project tablecrew-dev` (firebase-tools 15.25.1). 1. **A cross-file race condition.** Node's built-in test runner executes the 5 `*.rules.test.js` files as separate concurrent processes by default, but all 5 shared one `RulesTestEnvironment`/Firestore emulator instance. 2. **`tables.rules.test.ts`'s "denies the host writing reportFlags directly"** asserted setting `reportFlags.isSuppressed` to `false` — its already-seeded fixture default. No value actually changed, so Firestore's `diff()` correctly saw no affected key and allowed the (no-op) write; the rule was never actually exercised. Fixed to assert against `true`, a genuine change.
3. **`users.rules.test.ts`'s "denies the owner clearing their own deletedAt tombstone"** had the identical bug shape — `deletedAt` defaults to `null`, and the test tried setting it to `null` again. ## 2026-08 — Architecture readiness review: API gaps closed in `docs/API_SPEC.md`

**What changed:** A full cross-reference audit of `docs/API_SPEC.md` against every one of the 36 screens in `docs/SCREEN_SPECIFICATIONS.md` was completed. All six previously-tracked API gaps (see `TASKS.md`'s 2026-08 and 2026-07 updates) are now formally specified with full request/response/auth/error/idempotency detail, matching the existing document's format: `triggerDuressSignal` and `createLocationShare`/`revokeLocationShare` (§3.4 — the latter landed as a per-Table opt-in, reconciled against a concurrent Security-review pass's `docs/SECURITY.md`/`docs/DATABASE.md` model rather than the persistent-profile "trusted contact" originally imagined), `flagSplitPaymentDispute` (§3.6, landed via the same concurrent pass), `exportUserData`/`deleteAccount`/`cancelPendingDeletion` and `revokeSessions` (§3.8, new "Account Data & Privacy" domain), and `createCheckoutSession`/`cancelSubscription`/`stripeSubscriptionWebhook` (§3.6). Beyond the six tracked items, the audit surfaced and closed several previously-unflagged gaps: a missing `completeIdentityVerification` endpoint (§3.7, new "Identity Verification" domain) — the highest-severity finding, since Tier 2 verification gates every Open/Discover Table action and had no formal contract anywhere despite `docs/SECURITY.md` presupposing one exists; a missing `updateCrew` endpoint (§3.2) for editing a Crew's name/photo, which no document anywhere had named as a gap; a missing `endTableEarly` endpoint (§3.1) for the Live Table Screen's host-only early-end control; a stale `capacity.max` ceiling of 12 in `createTable`'s request schema, corrected to 8 everywhere else in the knowledge base back in the Series A diligence pass but never propagated to `docs/API_SPEC.md`; and missing `idempotencyKey` fields on `createTable`, `createCrew`, `scheduleRecurringTable`, and `submitRating` — all four already assumed by `docs/SCREEN_SPECIFICATIONS.md`'s own offline-behavior sections to carry one. Several existing endpoints (`addMember`, `removeMember`/`leaveCrew`, `blockUser`) gained explicit "idempotent by construction" notes and previously-missing `Errors`/`Server behavior` fields to close a documentation-completeness gap relative to the rest of the document's own standard.

**Why:** this repository's standard treats a previously-identified gap as something to resolve, not track indefinitely — three of the six originally-tracked gaps (duress signal, account deletion, payment dispute) are safety- or legal-critical, and `docs/SCREEN_SPECIFICATIONS.md`'s own offline-behavior sections had already assumed idempotency mechanics for several endpoints that `docs/API_SPEC.md` never actually specified, which is exactly the kind of cross-document drift `CLAUDE.md` treats as a correctness bug rather than cleanup for later.

**Follow-up noted above is now resolved** — see the next entry.

## 2026-08 — Architecture readiness review completed: `docs/ARCHITECTURE_READINESS_REVIEW.md` added, cross-review contradiction reconciled

**What changed:** Completed the full seven-dimension pre-engineering readiness review (product alignment, data/feature coverage, API completeness, security, analytics, notifications, offline behavior, error states), run as five parallel reviews and synthesized into the new `docs/ARCHITECTURE_READINESS_REVIEW.md`. Beyond the API-gap closure recorded in the previous entry, this pass: fixed a stale 12-person headcount ceiling that survived in `docs/PRD.md` (FR-T17, §7) and `docs/ARCHITECTURE.md` despite being corrected to 8 everywhere else; fixed a real internal contradiction in `docs/PRD.md` (FR-T13 vs. FR-T28) over whether the host reliability signal is ever publicly shown (it is not); closed seven `docs/DATABASE.md` data-model gaps with no backing feature reference until now (TableCrew+ subscription fields, bill-split dispute schema, simultaneous-reveal rating fields, duress-signal and location-share subcollections, the missing `off_platform_stalking` report reason code and `severity` field, missing Table fields for cost band/cover photo/accessibility notes/TBD-location, and finer-grained notification-mute preferences); added session-lifecycle/device-compromise documentation and a moderation escalation-and-appeals section to `docs/SECURITY.md`; closed a 16-event gap between `docs/SCREEN_SPECIFICATIONS.md`'s per-screen analytics fields and `docs/FIREBASE.md`'s canonical event table, plus fixed two outright bugs (Table cancellation and the duress signal both lacked any analytics event before this pass); reconciled three mismatched notification-category taxonomies (`docs/FIREBASE.md`, `docs/DATABASE.md`, `docs/SCREEN_SPECIFICATIONS.md` Screen 35 each implied a different one) into a single source of truth in `docs/FIREBASE.md` §2.4; fixed an offline-behavior inconsistency where Discover Table Preview and Table Detail handled the identical `requestSeat` action differently; and closed four error states that had a defined backend error code but no documented user-facing recovery path (`SEAT_REQUEST_CONTENTION`, a generic Persona verification failure, a host cancelling while attendees are already en route, and a missing "Failed" payment status).

**The one real cross-review contradiction, and how it was resolved:** the API-readiness and Security-readiness reviews, run in parallel, independently converged on the same design for location sharing — a per-Table, explicit, revocable opt-in (`createLocationShare`/`revokeLocationShare`), never a persistent "always share" profile setting, since a forgotten standing toggle is itself a privacy risk. But `docs/SCREEN_SPECIFICATIONS.md` Screen 29 ("Trusted Contact Setup") still described the old model: one saved contact, edited in Settings, with a default-on auto-share toggle. This synthesis pass rewrote Screen 29 to match the per-Table model (it now has an in-Table create/revoke mode and a no-Table explainer/active-shares-list mode), updated its corresponding wireframe in `docs/WIREFRAMES.md`, renamed the stale `trusted_contact_*` analytics events to `location_share_created`/`location_share_revoked` in `docs/FIREBASE.md` (retiring the now-inapplicable toggle-changed event), and rewrote `docs/SCREEN_SPECIFICATIONS.md`'s own "API Gaps Surfaced" rollup section, which still described several gaps as open after they'd actually been closed.

**Why:** the goal of this review was narrower than the earlier Series A diligence pass — not "would this survive investor scrutiny" but "would an engineer starting Phase 0 tomorrow hit a documented gap, a contradiction between two docs, or a silent assumption." Running five reviews in parallel against a shared, cross-referencing document set is efficient but risks exactly the kind of disagreement found here; the synthesis pass exists specifically to catch that, rather than trusting that five independent passes will always agree.

**Open items carried forward, not silently resolved (tracked in `TASKS.md`):** India DPDP Act consent/breach-notification specifics and Persona's Aadhaar coverage confirmation (both pre-existing, reconfirmed still open); the moderation appeals "different reviewer" target, stated as an aspiration rather than a guarantee given founding-team size; the 14-day account-deletion grace period and 3-attempt/24h identity-verification retry cap, both reasoned defaults flagged for Trust & Safety/legal sign-off before launch.
