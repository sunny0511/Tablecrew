# Changelog

This is the dated record of material changes to the TableCrew knowledge base and, later, the product itself. Every entry states what changed and why — not just what, because the "why" is what keeps future decisions consistent with past reasoning. Entries are in reverse chronological order.

## 2026-08 — Milestone F0 follow-up: real `npm install` surfaces and fixes 3 deploy-breaking bugs

**What changed:** The founder ran a real `npm install` in `functions/` (real npm registry access, unavailable in the sandbox that originally scaffolded Milestone F0), producing a genuine `functions/package-lock.json` (363 packages, lockfileVersion 3) and a real `node_modules/`. This closed one of F0's two disclosed manual blockers and, for the first time, made it possible to actually run `tsc`, `eslint`, and `node --test` against the Cloud Functions code instead of relying on hand-review and syntax-checking. Doing so surfaced three real bugs no amount of hand-review had caught: (1) an unused-parameter lint error (`req` never read) in the `healthCheck` stub; (2) `tsconfig.json` had `rootDir: "."`, so `tsc` emitted `lib/src/index.js`, but `package.json`'s `main` field pointed at `lib/index.js` — every future Cloud Functions deploy would have found no entry point; (3) `firebase.json`'s `functions.ignore` list literally included `"lib"`, excluding the compiled output from the deploy upload bundle entirely — combined with bug 2, `firebase deploy --only functions` would have shipped an empty, non-functional bundle. Fixed by splitting the build into `tsconfig.json` (production-only, `rootDir: "src"`, clean `lib/index.js` output) and a new `tsconfig.test.json` (extends the base config, `rootDir: "."`, outputs to a separate `lib-test/` that is excluded from both `.gitignore` and the deploy bundle). `package.json`'s scripts were updated to match (`build`/`build:test` split, `test`/`test:coverage` now glob explicit test files rather than passing a bare directory to `node --test`, which does not recursively discover tests the way its no-argument form does). Re-verified end to end: `npm run lint` clean, `npm run build` clean with the correct output shape, `npm test` 4/4 passing, `npm run test:coverage` at 100% line / 90% branch / 100% function coverage on the one real business-logic module (`isWellFormedIdempotencyKey`) — comfortably above `docs/TESTING.md`'s 85% threshold.

**Why:** the original F0 entry below disclosed that the Cloud Functions build had only ever been syntax-checked, never actually compiled or linted, precisely because no npm registry access existed in that environment — this entry is the resolution of that disclosed gap, not new scope. It's recorded separately rather than folded into the entry below because real tool execution found real, previously-undetectable defects, which is exactly the kind of thing this changelog exists to record distinctly from "as-planned" scaffolding work.

**Documents touched:** `functions/tsconfig.json`, `functions/tsconfig.test.json` (new), `functions/package.json`, `functions/src/index.ts`, `firebase.json`, `.gitignore`, `functions/package-lock.json` (new), `TASKS.md`, this file. See commit `ae50ac3`.

**Why:** per `CLAUDE.md`, application code may only be written once a founder or engineering lead explicitly instructs it in a specific conversation — that instruction was given, milestone by milestone, starting with F0 per the approved implementation plan.

**Disclosed environment limitations (not silent gaps):** the sandbox this work was done in had no Flutter/Dart SDK and no network access to install one, and no npm registry access to install any Node package (both confirmed via direct testing, not assumed) — so `flutter pub get`/`analyze`/`test`/`build`, `tsc`, and `eslint` could not actually be run here. What *was* verified directly: all TypeScript files pass `node --experimental-strip-types --check` (syntax-valid); the one piece of real logic written (`isWellFormedIdempotencyKey`) passes 4 unit tests actually executed with Node's built-in test runner; all JSON config files parse; the GitHub Actions workflow YAML parses and passes structural checks (via PyYAML, since GitHub Actions itself can't run here either). A real `.gitignore` bug was found and fixed in the same pass (a negation pattern that would have silently excluded `functions/.env.example` from version control) — caught only because it was checked with `git check-ignore` rather than assumed correct.

**Outstanding, blocking Milestone F1:** the `tablecrew-dev`/`-staging`/`-prod` Firebase projects do not exist yet — creating them requires real GCP/Firebase console access no agent sandbox has. `functions/package-lock.json` also does not exist yet, since `npm install` requires registry access unavailable here; CI's `npm ci` steps will fail until someone with real network access generates and commits it. Both are manual, one-time, non-code action items, not design gaps.

Also see the git history in the repository itself (`app/`, `functions/`, `firebase.json`, `.firebaserc`, `firestore/`, `.github/workflows/ci.yml`, `docs/adr/`) for the actual scaffolding, which is the primary deliverable of this entry, not a documentation change.

## 2026-08 — Pre-implementation verification: bill-splitting scope contradiction resolved, Firebase region decided

**What changed:** Ahead of starting Phase 0 engineering, a three-track verification pass (engineering/infra readiness, product scope buildability, open-blocker audit) was run to confirm the "frozen" v1.0 knowledge base is actually implementable, not just internally consistent. It surfaced one genuine, previously-uncaught contradiction and a few smaller gaps, all resolved with the founder's explicit direction:

- **Bill-splitting/payments Phase 0-vs-later contradiction, resolved in favor of deferral.** `docs/ROADMAP.md`, `docs/PRD.md` (§8 Launch Criteria), and `docs/FEATURES.md` all previously listed bill-splitting (FR-T22–T25a) as a Phase 0 (Must-P0) launch blocker, while `TASKS.md`'s founder-confirmed build order sequenced payments after Discover — i.e., much later. The founder confirmed the build order is authoritative: bill-splitting now ships in Phase 1, alongside Discover and the introduction of monetization more broadly. Fixed in `docs/ROADMAP.md` (moved from Phase 0 to Phase 1's feature list), `docs/PRD.md` (§8's launch-blocker list now explicitly excludes FR-T22–T25a, with a new reconciliation note explaining how `TASKS.md`'s early smoke-test milestone, this section's closed-beta exit criterion, and `docs/ROADMAP.md`'s actual Phase 0→1 advancement gate relate as three sequential checkpoints rather than three competing definitions of the same gate — a related, smaller inconsistency the same pass found), and `docs/FEATURES.md` (three bill-splitting rows reclassified Must-P0 → Must-P1).
- **Firebase production region decided:** `docs/ARCHITECTURE.md` §7 previously said only that Firestore launches in "a primary multi-region location matched to our initial launch market," without ever naming one — a real gap, since `TASKS.md` names "found the Firebase project" as the literal first, blocking Phase 0 step. No India-inclusive multi-region Firestore location exists, so `tablecrew-prod` (and, for parity, `-dev`/`-staging`) is now pinned to the regional location `asia-south1` (Mumbai). This also required correcting §8's RPO/RTO discussion, which had implicitly assumed multi-region Firestore's regional-outage resilience — a regional location doesn't have that property, so a full `asia-south1` outage would take Firestore down too, compounding with the pre-existing single-region Cloud Functions gap rather than providing independent protection against it. `docs/LEGAL.md` §11 updated to match.
- **Minor clarification, not a scope change:** `docs/SCREEN_SPECIFICATIONS.md` Screen 12 (Invite & Share Sheet) was ambiguous about how `docs/PRD.md` FR-T6's "inviting specific contacts" clause is satisfied for a Closed-Table host with no Crew yet. Clarified: sharing the already-specified private, capped, time-limited invite link directly to one contact via native share satisfies this — no separate in-app contact-picker UI is needed, and none is being added.

**Why:** `CLAUDE.md` treats cross-document consistency as a correctness property and "frozen" v1.0 as a stable baseline for implementation, not immunity from fixing a discovered defect — shipping an implementation plan against a knowledge base with a live, uncaught scope contradiction would have meant re-litigating "is bill-splitting in Phase 0" mid-build, which is exactly the kind of costly-to-discover-late problem this pre-implementation pass exists to catch early.

**Documents touched:** `docs/ROADMAP.md`, `docs/PRD.md`, `docs/FEATURES.md`, `docs/ARCHITECTURE.md`, `docs/LEGAL.md`, `docs/SCREEN_SPECIFICATIONS.md`, `TASKS.md`.

## 2026-07-31 — Knowledge base v1.0: initial company documentation established

**What changed:** Created the complete TableCrew documentation set from scratch: company foundation (`docs/MISSION.md`, `docs/VISION.md`, `docs/VALUES.md`, `docs/PRODUCT.md`), product definition (`docs/PRD.md`, `docs/USER_PERSONAS.md`, `docs/USER_RESEARCH.md`, `docs/ROADMAP.md`, `docs/FEATURES.md`, `docs/SUCCESS_METRICS.md`), engineering (`docs/ARCHITECTURE.md`, `docs/DATABASE.md`, `docs/API_SPEC.md`, `docs/FIREBASE.md`, `docs/ENGINEERING_GUIDELINES.md`, `docs/SECURITY.md`, `docs/TESTING.md`, `docs/DEPLOYMENT.md`, `docs/CI_CD.md`), design and brand (`docs/DESIGN_SYSTEM.md`, `docs/BRAND_GUIDELINES.md`, `docs/COPY_GUIDELINES.md`), growth (`docs/MARKETING.md`, `docs/SEO.md`, `docs/INVESTOR_OVERVIEW.md`), and company operations (`README.md`, `CLAUDE.md`, `TASKS.md`, this file, and `EXECUTIVE_SUMMARY.md`). No application code was written, per the explicit instruction that this phase is documentation-only.

**Why:** TableCrew needed a single, internally consistent source of truth before any code is written, so that engineering, design, and go-to-market decisions all derive from the same product definition, personas, and values rather than being reconstructed ad hoc by whoever builds each piece first.

**Key decisions made and recorded in this pass** (see the relevant document for full justification):
- Product is organized around three concepts — Table, Crew, Discover — with Table as the atomic unit (`docs/PRODUCT.md`).
- Tech stack is Flutter + Firebase (Firestore, Auth, Cloud Functions, Cloud Messaging, Storage, App Check, Remote Config, Crashlytics), chosen for founding-team velocity over a bespoke backend, with an explicit, planned migration path off pure-Firestore as scale requires it (`docs/ARCHITECTURE.md`).
- State management is Riverpod (`docs/ENGINEERING_GUIDELINES.md`); search/matching for Discover uses Typesense rather than Firestore's native geo-queries (`docs/ARCHITECTURE.md`).
- Monetization is subscription (TableCrew+) plus venue partnerships plus a later B2B2C offering (TableCrew for Teams) — explicitly not advertising (`docs/PRODUCT.md`, `docs/INVESTOR_OVERVIEW.md`).
- Sequencing is Crew-first, then Discover, then international/venue partnerships, then B2B2C (`docs/ROADMAP.md`), because Discover carries materially higher trust-and-safety requirements (`docs/SECURITY.md`) and because marketplace liquidity requires city-level density before breadth (`docs/MARKETING.md`).
- Brand palette is terracotta/ink-charcoal/linen-cream, deliberately distinct from the pink/purple/neon palette common to dating and large social apps, because a recurring persona anxiety is "is this secretly a dating app?" (`docs/DESIGN_SYSTEM.md`, `docs/BRAND_GUIDELINES.md`, `docs/USER_PERSONAS.md`).

**Known follow-ups, not yet resolved:** the specific anchor city for Phase 0 launch has not been chosen; the age-gating policy (13+ vs 18+) has not been finalized; the ID-verification vendor for Discover is recommended (Persona) but not contractually confirmed. These are tracked in `TASKS.md`.

## 2026-08 — Series A adversarial diligence review: contradictions found and fixed, LEGAL.md added

**What changed:** A full adversarial documentation review was conducted from the perspective of a skeptical VP of Product (Airbnb) and Principal Engineer (Google) doing Series A diligence, covering product vision, UX, business model, competition, scalability, engineering, security, database, APIs, analytics, monetization, trust & safety, legal, privacy, accessibility, and internationalization. Every document was read and, where a real issue was found, fixed directly rather than just flagged. Full detail is in the new `docs/SERIES_A_DILIGENCE_REVIEW.md`. Highlights: corrected a real contradiction in `VISION.md` (claimed Crews ship "Year 2–3," contradicting `ROADMAP.md` where Crews are the point of Phase 0/Year 1); named and bounded the tension between `MISSION.md`'s "anyone, anywhere" promise and `SECURITY.md`'s ID-verification requirement for Discover; drew an enforceable line in `VALUES.md` between disallowed advertising and allowed, labeled, capped, matching-walled-off Featured Venue placement; bounded the "real deletion" promise against statutory financial-recordkeeping retention; created `docs/LEGAL.md` from scratch (previously missing entirely) covering entity structure, host/venue liability and insurance, alcohol liability, U.S. dating-service-statute risk, background-check-vs-identity-verification precision, content-moderation liability, multi-regime data protection, an 18+ age-floor recommendation, and arbitration/IP items; fixed a real Firestore security-rules bug in `docs/DATABASE.md` (a flat `users` document would have leaked private fields to any signed-in user); added idempotency keys to every payment/capacity-critical API endpoint; added missing emergency/duress-response product and security requirements; added previously-absent unit-economics, app-store-policy, and payment-processor-risk sections to `docs/INVESTOR_OVERVIEW.md`.

**Why:** the original knowledge base was internally consistent by construction (it was authored in coordinated passes against shared canonical facts), but internal consistency is not the same as correctness or completeness — a real diligence process has to actively try to break the documents, not just check that they agree with each other.

**Also folded into this pass, from live founder direction received mid-review:** (1) TableCrew is now consistently described as a **platform**, not narrowly "a mobile app" — the mobile app is its primary current surface, corrected in `docs/PRODUCT.md`, `docs/INVESTOR_OVERVIEW.md`, `docs/MARKETING.md`, `docs/SEO.md`, and `EXECUTIVE_SUMMARY.md`; (2) the Phase 0 anchor city is **Hyderabad, India** — an India-first company, not a U.S.-first one, propagated into `docs/ROADMAP.md`, `docs/LEGAL.md` (new §11), `docs/MARKETING.md`, and `docs/TASKS.md`, with a flagged follow-up to re-derive `docs/INVESTOR_OVERVIEW.md`'s unit economics and `docs/API_SPEC.md`'s payment-rail design (UPI, not just cards) for that market; (3) Table headcount is now a 2–8 hard range with activity-dependent *recommended* sizes (coffee/mentorship smaller, dinner/founder-dinners mid-range, board games/hiking toward the ceiling) rather than one fixed default, propagated across `docs/PRODUCT.md` (new recommendation table), `docs/PRD.md`, `docs/FEATURES.md`, `docs/DATABASE.md`, `docs/BRAND_GUIDELINES.md`, and `README.md`; (4) `docs/PRODUCT.md` gained a Product Principles section, a Product Decision Test, a "How We Measure Success" callout, and a "What We Will Not Build" section, and `docs/ROADMAP.md`/`docs/MARKETING.md` had a master-brand-line inconsistency ("Pull up a chair." vs. `README.md`'s "Real Conversations. **Known follow-ups, not yet resolved (tracked in `TASKS.md`):** India-first unit-economics and UPI payment-rail re-derivation; Persona's Aadhaar/India-ID vendor coverage confirmation; Indian entity-structure decision with counsel; a `Venue.accessibilityInfo` schema addition; confirming the Mixpanel + Firebase Analytics split is intentional rather than redundant spend.

## 2026-08 — Design contract completed: SCREEN_SPECIFICATIONS.md, COMPETITOR_ANALYSIS.md, and WIREFRAMES.md added

**What changed:** Three new documents complete the pre-implementation design contract. `docs/SCREEN_SPECIFICATIONS.md` specifies all 36 screens in the app end to end (purpose, primary user, entry/exit points, UI components, API calls, validation rules, loading/empty/offline states, analytics events, accessibility notes, future enhancements) — the binding contract between Product, Design, and Engineering. `docs/COMPETITOR_ANALYSIS.md` is a product-facing (not investor-facing) teardown of Meetup, Timeleft, Bumble For Friends, Geneva, Partiful, and OpenTable (reservation-flow only), grounded in real user reviews, so the team has a concrete reference for which specific competitor failure modes to avoid rebuilding. `docs/WIREFRAMES.md` provides low-fidelity ASCII layout wireframes for all 36 screens, derived directly from each screen's spec, with a per-screen Notes callout naming a specific, real UX or implementation risk worth resolving before any Flutter work starts (e.g., the Live Table Screen's safety control must render before data loads and can never move behind a menu or confirmation step; the Report Flow's off-platform-stalking option must be visually and semantically separated, not buried among generic reasons; the Bill Split mode selector must have no pre-selected default and equal visual weight across all three options).

**Why:** writing the screen-by-screen spec before any code exists is what surfaces API and UX gaps while they're still cheap to fix — five real `docs/API_SPEC.md` gaps were found this way (see below) — and wireframing before high-fidelity design catches layout and information-architecture mistakes at the cheapest possible point in the process, per the founder's explicit direction.

**API gaps surfaced by `SCREEN_SPECIFICATIONS.md` (tracked in `TASKS.md`, not yet built):** a dedicated duress-signal endpoint (distinct from `reportUser`/`reportTable`, since a live-Table emergency can't route through the standard non-urgent report pipeline); a `disputeSplitPayment`-style endpoint; `exportUserData` and `deleteAccount`/`requestAccountDeletion` endpoints (needed to make the GDPR/CCPA-style rights already promised in `docs/SECURITY.md` and `docs/VALUES.md` actually implementable); a subscription checkout/billing-session endpoint; a trusted-contact CRUD endpoint.

**Documents touched:** `docs/SCREEN_SPECIFICATIONS.md` (new), `docs/COMPETITOR_ANALYSIS.md` (new), `docs/WIREFRAMES.md` (new), `README.md` (document index), `TASKS.md`.

## 2026-08 — Architecture readiness review: API gaps closed in `docs/API_SPEC.md`

**What changed:** A full cross-reference audit of `docs/API_SPEC.md` against every one of the 36 screens in `docs/SCREEN_SPECIFICATIONS.md` was completed. All six previously-tracked API gaps (see `TASKS.md`'s 2026-08 and 2026-07 updates) are now formally specified with full request/response/auth/error/idempotency detail, matching the existing document's format: `triggerDuressSignal` and `createLocationShare`/`revokeLocationShare` (§3.4 — the latter landed as a per-Table opt-in, reconciled against a concurrent Security-review pass's `docs/SECURITY.md`/`docs/DATABASE.md` model rather than the persistent-profile "trusted contact" originally imagined), `flagSplitPaymentDispute` (§3.6, landed via the same concurrent pass), `exportUserData`/`deleteAccount`/`cancelPendingDeletion` and `revokeSessions` (§3.8, new "Account Data & Privacy" domain), and `createCheckoutSession`/`cancelSubscription`/`stripeSubscriptionWebhook` (§3.6). Beyond the six tracked items, the audit surfaced and closed several previously-unflagged gaps: a missing `completeIdentityVerification` endpoint (§3.7, new "Identity Verification" domain) — the highest-severity finding, since Tier 2 verification gates every Open/Discover Table action and had no formal contract anywhere despite `docs/SECURITY.md` presupposing one exists; a missing `updateCrew` endpoint (§3.2) for editing a Crew's name/photo, which no document anywhere had named as a gap; a missing `endTableEarly` endpoint (§3.1) for the Live Table Screen's host-only early-end control; a stale `capacity.max` ceiling of 12 in `createTable`'s request schema, corrected to 8 everywhere else in the knowledge base back in the Series A diligence pass but never propagated to `docs/API_SPEC.md`; and missing `idempotencyKey` fields on `createTable`, `createCrew`, `scheduleRecurringTable`, and `submitRating` — all four already assumed by `docs/SCREEN_SPECIFICATIONS.md`'s own offline-behavior sections to carry one. Several existing endpoints (`addMember`, `removeMember`/`leaveCrew`, `blockUser`) gained explicit "idempotent by construction" notes and previously-missing `Errors`/`Server behavior` fields to close a documentation-completeness gap relative to the rest of the document's own standard.

## 2026-08 — Architecture readiness review completed: `docs/ARCHITECTURE_READINESS_REVIEW.md` added, cross-review contradiction reconciled

**What changed:** Completed the full seven-dimension pre-engineering readiness review (product alignment, data/feature coverage, API completeness, security, analytics, notifications, offline behavior, error states), run as five parallel reviews and synthesized into the new `docs/ARCHITECTURE_READINESS_REVIEW.md`. Beyond the API-gap closure recorded in the previous entry, this pass: fixed a stale 12-person headcount ceiling that survived in `docs/PRD.md` (FR-T17, §7) and `docs/ARCHITECTURE.md` despite being corrected to 8 everywhere else; fixed a real internal contradiction in `docs/PRD.md` (FR-T13 vs. FR-T28) over whether the host reliability signal is ever publicly shown (it is not); closed seven `docs/DATABASE.md` data-model gaps with no backing feature reference until now (TableCrew+ subscription fields, bill-split dispute schema, simultaneous-reveal rating fields, duress-signal and location-share subcollections, the missing `off_platform_stalking` report reason code and `severity` field, missing Table fields for cost band/cover photo/accessibility notes/TBD-location, and finer-grained notification-mute preferences); added session-lifecycle/device-compromise documentation and a moderation escalation-and-appeals section to `docs/SECURITY.md`; closed a 16-event gap between `docs/SCREEN_SPECIFICATIONS.md`'s per-screen analytics fields and `docs/FIREBASE.md`'s canonical event table, plus fixed two outright bugs (Table cancellation and the duress signal both lacked any analytics event before this pass); reconciled three mismatched notification-category taxonomies (`docs/FIREBASE.md`, `docs/DATABASE.md`, `docs/SCREEN_SPECIFICATIONS.md` Screen 35 each implied a different one) into a single source of truth in `docs/FIREBASE.md` §2.4; fixed an offline-behavior inconsistency where Discover Table Preview and Table Detail handled the identical `requestSeat` action differently; and closed four error states that had a defined backend error code but no documented user-facing recovery path (`SEAT_REQUEST_CONTENTION`, a generic Persona verification failure, a host cancelling while attendees are already en route, and a missing "Failed" payment status).

**The one real cross-review contradiction, and how it was resolved:** the API-readiness and Security-readiness reviews, run in parallel, independently converged on the same design for location sharing — a per-Table, explicit, revocable opt-in (`createLocationShare`/`revokeLocationShare`), never a persistent "always share" profile setting, since a forgotten standing toggle is itself a privacy risk. But `docs/SCREEN_SPECIFICATIONS.md` Screen 29 ("Trusted Contact Setup") still described the old model: one saved contact, edited in Settings, with a default-on auto-share toggle. This synthesis pass rewrote Screen 29 to match the per-Table model (it now has an in-Table create/revoke mode and a no-Table explainer/active-shares-list mode), updated its corresponding wireframe in `docs/WIREFRAMES.md`, renamed the stale `trusted_contact_*` analytics events to `location_share_created`/`location_share_revoked` in `docs/FIREBASE.md` (retiring the now-inapplicable toggle-changed event), and rewrote `docs/SCREEN_SPECIFICATIONS.md`'s own "API Gaps Surfaced" rollup section, which still described several gaps as open after they'd actually been closed.

**Why:** the goal of this review was narrower than the earlier Series A diligence pass — not "would this survive investor scrutiny" but "would an engineer starting Phase 0 tomorrow hit a documented gap, a contradiction between two docs, or a silent assumption." Running five reviews in parallel against a shared, cross-referencing document set is efficient but risks exactly the kind of disagreement found here; the synthesis pass exists specifically to catch that, rather than trusting that five independent passes will always agree.

**Open items carried forward, not silently resolved (tracked in `TASKS.md`):** India DPDP Act consent/breach-notification specifics and Persona's Aadhaar coverage confirmation (both pre-existing, reconfirmed still open); the moderation appeals "different reviewer" target, stated as an aspiration rather than a guarantee given founding-team size; the 14-day account-deletion grace period and 3-attempt/24h identity-verification retry cap, both reasoned defaults flagged for Trust & Safety/legal sign-off before launch.
