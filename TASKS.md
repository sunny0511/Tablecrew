## Update — 2026-08 SCREEN_SPECIFICATIONS.md and COMPETITOR_ANALYSIS.md added

4. **Subscription checkout/billing session endpoint** (TableCrew+ Subscription) — either a Stripe Checkout session creator or a documented platform-billing (App Store/Play Billing) integration contract.
5. **Trusted-contact CRUD endpoint** (Trusted Contact Setup) — needed if server-side phone validation or contact notification is wanted beyond a simple client-direct profile write.
6. **`revokeSessions` endpoint** (Settings > Security, surfaced during the Security-readiness architecture review, 2026-07) — invokes the Firebase Admin SDK's `revokeRefreshTokens` for the caller's own UID so a user can invalidate every signed-in session at once (lost/stolen device, or forgetting to sign out on a shared device). `docs/SECURITY.md`'s new "Authentication: Session Lifecycle, Token Handling, and Device Compromise" section specifies the requirement and the support-triggered fallback path; this endpoint itself still needs a formal `API_SPEC.md` contract before it can be built. ## Build order (founder-confirmed, 2026-08)

This is the authoritative near-term build sequence, superseding any implicit ordering in the numbered list below where the two disagree — the numbered list still holds the *what*, this holds the *in what order*:

1. **Marketing site + waitlist.** Before any app code — get discoverable, start collecting Hyderabad-market demand signal, and give `docs/MARKETING.md`'s and `docs/SEO.md`'s content strategy something to point at from day one.

6. **Invitations & RSVPs.** Closes the loop on "does a Table actually fill and happen."
7. **Notifications.** RSVP reminders, day-of nudges — necessary for the coordination loop to actually beat a group chat, not a nice-to-have added later.
8. **Discover — only after Trust & Safety infrastructure is in place**, not before. This explicitly re-confirms `docs/ROADMAP.md`'s and `docs/VALUES.md`'s "Safety is a feature, not a department" sequencing: Tier 2 identity verification, the reporting/blocking pipeline, and the duress/emergency mechanism in `docs/SECURITY.md` must all be live and tested against real Crew-first-era report volume before Discover introduces strangers into the product.

The milestone below is the correct **earliest** checkpoint — proof the core loop works at all — not the gate for advancing to Phase 1. See `docs/PRD.md` §8's reconciliation note for how this milestone, the closed-beta exit criterion, and `ROADMAP.md`'s actual advancement gate relate as three sequential checkpoints, not competing definitions.

**Earliest milestone (this document's near-term target):** at least 3 Crews in the anchor city have each created and attended 2 or more Tables within a 6-week window, with a no-show rate under the guardrail threshold set in `docs/SUCCESS_METRICS.md`. Reaching this milestone does not by itself mean Phase 0 is complete or that Phase 1 is greenlit — see `docs/PRD.md` §8 and `docs/ROADMAP.md` for the actual closed-beta and advancement gates.

## How to add to this list

Add new tasks under "Immediate next steps" with an owner and, where relevant, a citation to the document that specifies the requirement. When a task is finished, move a one-line summary of it into `CHANGELOG.md` rather than just deleting it — the changelog is where we keep the record of what actually happened.
