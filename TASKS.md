## Update — 2026-08 SCREEN_SPECIFICATIONS.md and COMPETITOR_ANALYSIS.md added

`docs/SCREEN_SPECIFICATIONS.md` now specifies all 36 screens in the app end to end. Writing it surfaced five real `docs/API_SPEC.md` gaps that need formal endpoint definitions before the corresponding screens can be built as specified — these are launch-relevant, not someday items, since three of them (duress signal, account deletion, payment dispute) are safety/legal-critical:

1. **Duress-signal endpoint** (Live Table Screen) — a dedicated, high-priority endpoint distinct from `reportUser`/`reportTable`, since a safety emergency during a live Table cannot route through the normal non-urgent report pipeline.
2. **`disputeSplitPayment`-style endpoint** (Split Request / Payment Detail) — disputing a bill-split charge currently has no backend call to route through.
3. **`exportUserData` and `deleteAccount` endpoints** (Data Export / Delete Account) — required for the GDPR/CCPA-style rights already promised in `docs/SECURITY.md` and `docs/VALUES.md` to actually be implementable, not just promised in copy. (Naming note, resolved 2026-07: `docs/SECURITY.md` previously called these `requestDataExport`/`requestAccountDeletion`, a different name than `docs/DATABASE.md`'s `exportUserData`/`deleteAccount` for the same two callables — `docs/SECURITY.md` now uses `DATABASE.md`'s names as canonical. The endpoints themselves still need a real `docs/API_SPEC.md` entry; only the naming drift is fixed.)
4. **Subscription checkout/billing session endpoint** (TableCrew+ Subscription) — either a Stripe Checkout session creator or a documented platform-billing (App Store/Play Billing) integration contract.
5. **Trusted-contact CRUD endpoint** (Trusted Contact Setup) — needed if server-side phone validation or contact notification is wanted beyond a simple client-direct profile write.
6. **`revokeSessions` endpoint** (Settings > Security, surfaced during the Security-readiness architecture review, 2026-07) — invokes the Firebase Admin SDK's `revokeRefreshTokens` for the caller's own UID so a user can invalidate every signed-in session at once (lost/stolen device, or forgetting to sign out on a shared device). `docs/SECURITY.md`'s new "Authentication: Session Lifecycle, Token Handling, and Device Compromise" section specifies the requirement and the support-triggered fallback path; this endpoint itself still needs a formal `API_SPEC.md` contract before it can be built. A stronger per-device session list (name, last-active time, individual revoke) is a follow-on enhancement, not required for the initial fix.

**RESOLVED — 2026-08 API readiness pass.** All six items above are now formally specified in `docs/API_SPEC.md`: #1 as `triggerDuressSignal` (§3.4), #2 as `flagSplitPaymentDispute` (§3.6, landed via a concurrent Security-review pass), #3 as `exportUserData`/`deleteAccount`/`cancelPendingDeletion` (§3.8), #4 as `createCheckoutSession`/`cancelSubscription`/`stripeSubscriptionWebhook` (§3.6), #5 as `createLocationShare`/`revokeLocationShare` (§3.4 — landed as a per-Table opt-in rather than a persistent saved-contact CRUD, reconciled against `docs/SECURITY.md`'s and `docs/DATABASE.md`'s concurrently-specified model; **follow-up needed:** `docs/SCREEN_SPECIFICATIONS.md` Screen 29 "Trusted Contact Setup" still describes a single persistent saved contact with an auto-offer toggle, which now contradicts this model and needs to be rewritten to match the per-Table opt-in shape), and #6 as `revokeSessions` (§3.8). The same pass also found and closed several previously-unflagged gaps while cross-referencing every screen in `docs/SCREEN_SPECIFICATIONS.md` against `docs/API_SPEC.md`: a missing `completeIdentityVerification` endpoint (§3.7, arguably higher-severity than any of the six above since it underpins the entire Tier 2/Discover trust gate and wasn't even informally named anywhere before this pass); a missing `updateCrew` endpoint (§3.2) for editing a Crew's name/photo; a missing `endTableEarly` endpoint (§3.1) for the Live Table Screen's host-only early-end control; a stale `createTable` capacity ceiling of 12 that had been corrected to 8 everywhere else in the knowledge base but never propagated to `docs/API_SPEC.md`; and missing `idempotencyKey` fields on `createTable`, `createCrew`, `scheduleRecurringTable`, and `submitRating`, all four of which `docs/SCREEN_SPECIFICATIONS.md` already assumed existed. Full detail in `docs/API_SPEC.md` §7 and `docs/CHANGELOG.md`.

Also produced: `docs/COMPETITOR_ANALYSIS.md`, a product-facing (not investor-facing) teardown of Meetup, Timeleft, Bumble For Friends, Geneva, Partiful, and OpenTable, grounded in real user reviews, so the team has a concrete "don't rebuild this specific failure mode" reference alongside the screen specs; and `docs/WIREFRAMES.md`, low-fidelity ASCII layout wireframes for all 36 screens with a per-screen Notes callout naming a real, specific UX/implementation risk (e.g., the Live Table Screen's duress control must render before data loads and can never move behind a menu; the Report Flow's off-platform-stalking option must stay visually separated from the generic reasons; the Bill Split mode selector must ship with no pre-selected default) — meant to be walked through and resolved before the corresponding screen's Flutter build starts, per the founder's direction to catch UX issues while cheap to change.

## Build order (founder-confirmed, 2026-08)

This is the authoritative near-term build sequence, superseding any implicit ordering in the numbered list below where the two disagree — the numbered list still holds the *what*, this holds the *in what order*:

1. **Marketing site + waitlist.** Before any app code — get discoverable, start collecting Hyderabad-market demand signal, and give `docs/MARKETING.md`'s and `docs/SEO.md`'s content strategy something to point at from day one.
2. **Authentication & onboarding.** Phone verification (Tier 1), DOB/age gate, the foundation everything else sits on.
3. **Profile & interests.** Identity a user presents to others, and the interest-tag taxonomy that later drives Discover matching and Create Table's smart headcount defaults.
4. **Create a Table.** The single most important journey in `docs/PRD.md` — ships Closed/Crew-originated Tables first, per `docs/ROADMAP.md` Phase 0's Crew-first sequencing.
5. **Crew management.** Persistent friend groups, Crew chat, the retention-critical layer.
6. **Invitations & RSVPs.** Closes the loop on "does a Table actually fill and happen."
7. **Notifications.** RSVP reminders, day-of nudges — necessary for the coordination loop to actually beat a group chat, not a nice-to-have added later.
8. **Discover — only after Trust & Safety infrastructure is in place**, not before. This explicitly re-confirms `docs/ROADMAP.md`'s and `docs/VALUES.md`'s "Safety is a feature, not a department" sequencing: Tier 2 identity verification, the reporting/blocking pipeline, and the duress/emergency mechanism in `docs/SECURITY.md` must all be live and tested against real Crew-first-era report volume before Discover introduces strangers into the product.
9. **Payments / venue partnerships.** Bill-splitting and the venue-commission revenue line come after the core coordination and trust loops are proven, consistent with `docs/ROADMAP.md` Phase 1/Phase 3 sequencing.
